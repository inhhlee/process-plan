## 1. 근거와 해석

원문 요구, 기존 설계, 새 제안, 사용자 추가·변경을 구분한다. 원문에 없는 상세값을 원문의 확정 요구로 표현하지 않는다. 프로젝트별 원본 식별과 적용 범위는 해당 요구사항 문서에서 관리한다.

명세·규칙·데이터를 작성하거나 보완할 때 필요한 근거는 다음과 같다.

| 항목 | 기록할 내용 |
| --- | --- |
| 근거 문서와 위치 | 파일명·버전, 페이지·절·표·기능 ID 등 다시 찾을 수 있는 위치 |
| 원문 요지 | 자료에 실제로 적힌 요구 또는 기존 설계의 의미 |
| 추가한 해석 | 구현을 위해 구체화하거나 새로 제안한 부분 |
| 근거 구분 | 원문 요구 / 기존 초안의 설계 / 새 설계 제안 / 사용자 추가·변경 |
| 결정·검토 상태 | 임시값·미정 정책, 검토 범위·남은 확인과 관련 결정 항목 |

문서 간 기능 연결과 원본 근거를 구분한다. 작성 중인 항목으로 되돌아오는 링크는 원본 근거를 대신하지 않는다. 원문 위치를 확인하지 못한 경우 `근거 위치 미확인`과 후속 확인을 기록한다.

## 2. 상태 표시

| 구분 | 사용하는 상태 | 의미 |
| --- | --- | --- |
| 설계 결정 | 미정 / 제안 / 임시 채택 / 확정 | 결정 여부와 적용 범위 |
| 작업 진행 | 미착수 / 진행 중 / 완료 | 실제 수행 범위 |
| 실행 검증 | 미검증 / 검증 중 / 통과 / 실패 | 실제 시험 여부와 판정 |
| 문서 검토 | 미검토 / 검토 중 / 검토 완료 | 검토자·검토 범위·결과를 함께 기록. 사용자 검토 대기 여부도 구분 |

문서 초안 작성 상태는 작업 진행 상태를 사용한다. 문서 작성, 사용자 검토, 설계 결정, 구현, 실행 검증을 각각 표시한다. 기존 기록의 당시 표현·판정은 보존한다.

`미정`은 결정할 내용, `미작성`은 아직 작성하지 않은 내용, `미선정`은 작업을 선택하지 않은 상태다. 무엇을 언제 확인·작성할지 연결한다. `해당 없음`은 적용 대상이 아닐 때 이유와 함께 사용한다. 미확인 기한은 미정으로 두며 제안 일정과 확정 일정을 구분한다.

## 3. 사실과 완료 판단

- 예정 작업·설명용 예시·실제 결과를 구분하고 사용자 보고와 직접 확인한 결과의 출처를 표시한다.
- 진행 중인 작업에는 수행한 범위와 남은 작업을 기록한다. 일부 수행한 체크 항목은 완료로 표시하지 않는다.
- 완료 표시에는 결과물 또는 확인 근거를 연결한다. 일일 작업 완료와 과제 전체 완료를 구분한다.

| 판단 | 필요한 근거 |
| --- | --- |
| 초안 작성 완료 | 요청 범위와 필수 항목을 작성하고 남은 문제·미정 사항을 후속 작업에 연결 |
| 내용 검토 완료 | 원문·문서 대조의 범위, 검토자, 결과와 남은 조치 기록. AI 검토와 사용자 검토 구분 |
| 설계 확정 | 해당 범위의 결정 근거·결정 주체·적용 내용을 확인. 일부 확정은 해당 항목에만 표시 |
| 구현 완료 | 해당 기능의 구현 결과물과 수행 범위 확인 |
| 검증 통과 | 시험 조건·입력·예상·실제·판정 근거가 있고 해당 완료 기준을 충족 |
| 과제 전체 완료 | 과제계획의 산출물과 완료 기준을 충족하고 관련 검증 근거 연결 |

파일이나 시험 계획이 있다는 사실만으로 내용 검토·구현·실행 검증이 완료되지는 않는다. Mock·대역 시험과 실제 모듈 연결 시험, 개별 과제와 전체 통합 시험의 범위를 표시한다.

## 4. 검증 결과 기록

실행별 결과는 [검증결과 양식](양식/검증결과.md)으로 기록한다. 기능 ID, 환경·코드·계약 버전, 입력·조건, 수행 절차, 예상 결과, 실제 결과, 판정과 증거가 서로 연결되어야 한다. 정책값이 필요한 시험에는 실제 적용한 값과 결정 근거를 연결한다.

재시험은 새 실행 ID와 증거로 남기고 이전 실패·미실행 기록을 보존한다. 실행하지 못한 항목에는 미검증 표시, 이유와 재개 조건을 적는다. 계획·형식·링크 확인과 제품 동작 시험의 결과는 구분한다. 인증정보는 기록하지 않는다.

## 5. 변경과 결과 연결

- 상세 내용은 담당 문서 한 곳에서 관리하고 다른 문서에는 필요한 요약과 링크를 작성한다. 기록 위치는 README의 문서 역할 안내를 따른다.
- 정의가 충돌하면 원본 위치, 서로 다른 내용과 영향을 기록한다. 결정이 필요한 항목에는 선택지·제안 이유·영향·후속 작업을 남긴다.
- 결정·피드백을 반영한 결과에는 변경 전후 내용, 이유, 결정 주체와 확인 근거를 남긴다. 제안·임시값을 확정으로 바꿀 때는 해당 근거가 필요하다.
- 목표·범위·기한·상태에 영향이 있으면 관련 계획·일정에 반영한다. 별도 설명·제출이 필요한 변경은 [변경보고 작성 규칙](보고%20작성%20기준.md#change-report)을 따른다.
- 오탈자·링크·안내 등 일반 수정은 기존 문서를 갱신하고 필요하면 일일업무에 요약한다. 수정마다 별도 변경보고를 만들지 않는다.
- 수정 원본은 같은 파일을 갱신하며 버전은 본문에 기록한다. 제출본·실행별 시험 근거는 구분해 보관한다. 보관 문서는 당시 이력이며 현재 작업의 기본 기준으로 사용하지 않는다.
- 후속 작업에는 수정 대상, 수행할 행동, 확인 방법과 완료 조건을 적는다. 현재 결과와 남은 작업을 구분한다.
- 일일·주간·계획에는 상세 산출물·시험 결과를 요약해 연결한다. 같은 진도를 별도 `PLAN.md`에 이중 관리하지 않는다.

AI의 작업 순서는 [기본 지침](../AGENTS.md)에서 연결하는 작업별 스킬에서 관리한다. 이 문서는 문서에 남겨야 할 공통 기준을 정의한다.
