## 1. 기본 원칙

개발 전에 무엇을, 어떤 순서로, 어디까지 만들고 어떻게 확인할지 정리한다. [공통 작성 규칙](공통%20작성%20규칙.md)과 [업무 문서 역할 안내](../README.md#document-map)를 함께 적용한다.

이 문서는 계획 문서의 작성 기준이다. 작성한 명세·계획으로 Issue를 나누고 Codex 구현·시험·PR을 진행하는 방법은 [개발 진행 절차](개발%20진행%20절차.md)를 따른다.

- [개발계획서 양식](양식/개발계획서.md)을 복사하여 사용한다. 기존 과제계획은 파일명과 경로를 유지한다.
- 원문 요구, 기존 설계, 새 제안과 미정 사항을 구분한다. 양식 채택은 기술 선택이나 설계 전체의 확정을 뜻하지 않는다.
- 기능 수와 개발 단계 수는 과제에 맞게 정한다. 실습 예제의 Vue·Vite·저장 방식·단계 수는 가져오지 않는다.
- 간단한 수정은 기존 계획의 관련 항목만 갱신한다. AI의 권한·작업 범위 적용은 [AGENTS.md](../AGENTS.md)에서 관리한다.

## 2. 고정 구성

아래 8개 대제목과 순서를 사용한다. 적용 대상이 아니면 `해당 없음`과 이유를 적는다. 아직 결정·작성·선택하지 않은 내용은 아래 기준에 따라 `미정`·`미작성`·`미선정`과 후속 작업을 적는다.

| 순서 | 대제목 | 필수 내용 |
| --- | --- | --- |
| 1 | 문서 개요 | 문서명·목적·작성자·작성일·수정일·버전·대상 독자, 계획 작성/검토·개발·검증 상태, 일정과 관련 문서 |
| 2 | 배경과 목적 | 해결할 문제, 필요한 이유, 과제 완료 시 가능한 일 |
| 3 | 용어 설명 | 이 계획을 읽는 데 필요한 용어와 쉬운 설명 |
| 4 | 기능 범위 | 포함할 기능과 ID, 이번 범위에서 다루지 않는 항목과 담당 과제, 예정 산출물 |
| 5 | 사용할 기술 | 구성 요소·선택 또는 후보·용도와 이유·근거 및 선택 상태 |
| 6 | 개발 로드맵 | 선행 조건, 작업 순서·관련 ID·작업 내용·완료 확인 조건, 구현 직전 구체화할 작업 단위 |
| 7 | 완료 기준 | 관찰 가능한 결과의 체크리스트, 시험 조건과 예상 결과, 실제 결과를 기록할 위치 |
| 8 | 참고 사항·제약 | 관련 R·C·D와 원문 근거, 미정 정책·제약, 다음 작업과 기록 위치, 변경 이력 |

- 다른 과제에서 구현하는 항목을 프로젝트 전체의 제외 기능으로 표현하지 않는다.
- 기존 기능 ID·산출물·시험 항목은 양식 변경 과정에서 누락하지 않는다.
- 명세의 상세 필드·정책값은 담당 명세로 연결한다. 계획서에 별도 정의를 만들어 관리하지 않는다.

### 하위 구성과 표의 고정 기준

[빈 양식](양식/개발계획서.md)의 하위 제목·순서, 표의 열 이름·순서와 문서 개요 항목을 공통 기준으로 사용한다. 본문 내용·표의 행 수·기능 수·체크 수는 과제에 맞게 작성한다.

| 절 | 고정 하위 제목과 순서 |
| --- | --- |
| 1. 문서 개요 | 하위 제목 없음 — 기본 정보 표 |
| 2. 배경과 목적 | 하위 제목 없음 — 설명 문단 |
| 3. 용어 설명 | 하위 제목 없음 — 용어 표 |
| 4. 기능 범위 | 포함하는 기능 → 제외·연계 범위 → 예정 산출물 |
| 5. 사용할 기술 | 하위 제목 없음 — 기술 표 |
| 6. 개발 로드맵 | 선행 조건과 단계 흐름 → 전체 작업 순서 → 이번 구현 작업 단위 |
| 7. 완료 기준 | 과제 전체 완료 체크 → 전체 시험 계획 → 이번 작업 시험 → 상세 실행 절차 |
| 8. 참고 사항·제약 | 근거와 미정 사항 → 다음 작업·기록 위치 → 변경 이력 |

| 표의 위치 | 고정 열 이름과 순서 |
| --- | --- |
| 문서 개요 | 항목 / 내용 |
| 용어 설명 | 용어 / 쉬운 설명 |
| 포함하는 기능 | 기능 ID / 기능명 / 제공할 동작 |
| 제외·연계 범위 | 항목 / 이유·담당 과제 |
| 예정 산출물 | 산출물 / 위치 / 현재 상태 |
| 사용할 기술 | 구성 요소 / 선택 또는 후보 / 용도와 이유 / 근거·선택 상태 |
| 전체 작업 순서 | 순서 / 관련 항목 / 수행할 작업 / 완료 확인 조건 |
| 이번 구현 작업 단위 | 기능 ID / 대상 파일·모듈 / 변경 내용 / 선행 결정 / 시험 입력·예상 결과 |
| 전체 시험 계획 | 기능 / 시험 조건 / 예상 확인 결과 |
| 이번 작업 시험 | 시험 ID / 입력·조건 / 성공 기준 / 실패 판단 |
| 변경 이력 | 일자 / 버전 / 변경 내용·근거 |

- 문서 개요는 빈 양식의 26개 항목과 순서를 그대로 사용한다. `버전`은 해당 문서의 변경 이력이고 `양식 버전`은 적용한 공통 구조의 버전이다. 현재 양식 버전은 v1.1이다.
- 하위 제목과 표를 없애거나 다른 위치로 옮기지 않는다. 추가 설명·명령·증거 관리 안내는 해당 하위 제목 안에서 문단·목록·굵은 소제목으로 작성한다.
- 미정·미작성·미선정·해당 없음과 상태·완료의 의미는 [공통 작성 규칙](공통%20작성%20규칙.md#statuses)을 적용한다.
- 과제 전체의 완료 기준·시험과 이번에 선택한 작업의 시험을 구분한다. 실행 명령·순서는 7절 마지막의 `상세 실행 절차`에 둔다. 실제 시험 결과는 검증결과에 기록한다.
- 공통 구조를 바꿀 때는 빈 양식·이 규칙·적용 중인 과제계획을 함께 갱신한다. 양식을 채우기 위해 미정 정책이나 완료 상태를 임의로 확정하지 않는다.

## 3. 구현 전 계획 항목

이번 구현 작업 단위에는 기능 ID, 실제 대상 파일·모듈, 변경 내용, 선행 결정, 시험 입력·예상 결과를 작성한다. 코드 위치를 모르는 단계에서는 미정과 확인할 작업을 기록하고, 구현 직전에는 실제 저장소와 대조한다. 과제 전체의 계획과 이번 작업의 범위를 구분한다.

계획을 작성·검토하는 AI 절차는 [plan-development](../.agents/skills/plan-development/SKILL.md), 실제 관제 기능을 구현·시험하는 절차는 [amr-implement-verify](../.agents/skills/amr-implement-verify/SKILL.md)에서 관리한다. 이 문서는 계획의 구성과 작성 기준을 정의한다.

## 4. 계획과 실적의 기록 위치

| 예제의 역할 | 현재 프로젝트에서 사용하는 문서 |
| --- | --- |
| 기획서: 무엇을 만들지 | 요구사항정의·공통규칙·공통데이터명세·기능명세 |
| 개발계획서: 어떻게 만들지 | 각 과제의 `과제계획.md` |
| PLAN.md: 어디까지 했는지 | 전체일정의 상태 요약 + 주간·일일 기록 + 검증 결과의 실제 근거 |

계획과 실제 기록의 연결·중복 관리 기준은 [공통 작성 규칙](공통%20작성%20규칙.md#changes)을 따른다. 계획에는 현재 범위의 상태 요약과 실제 결과의 링크를 둔다.

## 5. 파일과 보기 형식

- 수정 기준은 Markdown 원본이다. 루트의 `보기본/`에 생성된 HTML과 원본의 대응 경로는 [도구 안내](../도구/README.md)를 따른다.
- HTML은 참고 ZIP의 짙은 남색 표지, 목차, 번호가 있는 절, 표, 단계 흐름, 완료 체크리스트 구성을 따른다.
- 생성 대상·사전 형식 검사·실행 명령은 [도구 사용 안내](../도구/README.md)에서 관리한다. HTML을 직접 고치지 않고 원본을 수정해 다시 생성한다.

## 6. 형식 확인 기준

- 8개 절·13개 하위 제목·11개 표의 열·개요 26개 항목이 빈 양식과 같은 순서이며, 비개발 독자도 기능과 용어를 이해할 수 있다.
- 범위·산출물·작업 순서·완료 기준·시험 계획이 서로 연결된다.
- 미정 값은 미정으로 표시하고 연결된 후속 작업이 있다.
- 관련 문서와 기능 ID 링크가 실제 내용으로 연결된다.
- 계획 작성 완료와 개발 완료·검증 통과를 구분한다.
- HTML의 표·목차·완료 체크가 원본과 일치하며 작은 화면에서도 내용을 읽을 수 있다.
