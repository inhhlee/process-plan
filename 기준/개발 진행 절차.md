# Codex와 GitHub 기반 관제 프로젝트 개발 진행 절차

- 작성자: 이인호 연구원
- 수정일: 2026-10-07
- 버전: v0.4 — 사용자의 요청·확인 순서로 정리하고 직접 연결 설정을 부록으로 이동
- 대상 독자: Codex를 사용해 관제 프로젝트를 진행하는 사용자

이 문서는 **사용자가 Codex에 무엇을 요청하고, 나온 결과에서 무엇을 확인하면 되는지** 안내합니다. 각 단계의 요청문을 해당 프로젝트의 채팅에 입력하고 결과를 확인한 뒤 다음 작업을 요청합니다.

이 문서 저장소에서는 계획을 정리하고 GitHub Issue를 만듭니다. Issue는 개발할 작업의 목적·범위·완료조건을 적은 작업표입니다. 실제 코드는 별도의 코드 프로젝트에서 작업하며, 변경 내용을 검토하는 PR(Pull Request)을 거쳐 반영합니다.

코드 작업과 Issue·PR의 대상은 [inhhlee/amr-control-system-demo](https://github.com/inhhlee/amr-control-system-demo)입니다. 문서 폴더와 코드 폴더의 위치·확인 상태는 [개발환경](../관제시스템%20과제%20진행/개발환경.md)에서 관리합니다.

### 어디서 무엇을 하나요?

| 순서 | 사용자가 열 곳 | 사용자가 할 일 | 받을 결과 |
| --- | --- | --- | --- |
| 1 | 이 문서 저장소의 Codex 채팅 | 진행할 과제·기능을 말하고 Issue 초안 요청 | 작업 목록과 Issue 초안 |
| 2 | 같은 채팅 | 초안을 확인하고 GitHub에 생성 요청 | 실제 Issue URL |
| 3 | 코드 프로젝트의 Codex 채팅 | Issue URL과 명세·계획을 전달하고 구현 요청 | 변경 코드와 실제 시험 결과 |
| 4 | 같은 코드 채팅 | 변경 검토·PR 생성·병합 요청 | PR URL과 반영 결과 |
| 5 | 이 문서 저장소의 채팅으로 돌아오기 | 개발 결과를 전달하고 업무 기록 요청 | 갱신한 기록과 남은 작업 |

**처음에는 [1단계의 작업 정리](#work-selection)와 [2단계의 Issue 생성](#issue-creation)부터 진행하면 됩니다.** GitHub가 이미 연결되어 있다면 별도의 PAT 입력·MCP 등록 명령은 필요하지 않습니다. 연결 상태를 모르면 아래 [연결 확인](#github-check)을 먼저 요청하세요.

요청문의 대괄호에는 실제 과제명·Issue URL·PR URL을 넣습니다. 설명용 요청문은 작업이 수행되었다는 기록이 아니며, 실제 결과는 Issue·PR과 업무 기록에서 확인합니다.

## 0. 사전 준비

### 사용할 프로젝트 확인

지금은 이 문서 저장소의 채팅을 엽니다. 나중에 구현을 시작할 때 `inhhlee/amr-control-system-demo`의 코드 폴더를 별도의 Codex 프로젝트로 엽니다.

두 프로젝트를 오갈 때는 **Issue URL과 필요한 문서 위치를 직접 전달**합니다. 코드 프로젝트에서도 이 채팅의 내용과 로컬 문서를 읽을 수 있는지는 전달할 때 확인합니다. 기존 `C:\practice`의 코드·시험 결과는 새 저장소에서 적용 여부를 확인할 참고 자료입니다.

<a id="github-check"></a>

### GitHub 연결 확인

연결 여부를 모르면 이 문서 저장소의 채팅에 아래 요청을 입력합니다.

```text
inhhlee/amr-control-system-demo의 기존 Issue와 PR을 조회해줘.
이 채팅에서 Issue를 생성할 도구가 있는지도 확인해줘.
조회한 결과와 아직 확인하지 못한 권한을 알려줘.
```

사용자는 조회 결과에 표시된 저장소가 `inhhlee/amr-control-system-demo`인지 확인합니다. 조회가 성공하고 생성 도구가 제공되면 Issue 초안 작성을 진행합니다. 실제 생성 성공은 2단계에서 받은 Issue URL로 확인합니다.

연결 문제가 있으면 Codex가 알려주는 준비 항목을 확인합니다. 직접 PAT로 MCP를 연결해야 할 때만 [문서 끝의 추가 설정](#manual-github-setup)을 사용합니다. MCP는 Codex가 GitHub 도구를 사용할 수 있게 연결하는 방식이며, 직접 설정 명령을 알아야 요청할 수 있는 것은 아닙니다.

## 1. 진행할 작업 정하기

**사용자가 할 일:** 이 문서 저장소의 채팅에서 진행할 과제나 기능을 말합니다. 첫 작업을 고르기 어렵다면 후보와 추천 순서를 요청합니다.

```text
[과제 또는 기능]을 진행하려고 해.
기존 명세와 과제계획을 보고 첫 작업 후보와 추천 순서를 알려줘.
각 작업의 목적·범위·선행 조건·완료조건·시험 방법을 정리해줘.
새 저장소에서 구현 여부를 확인해야 할 부분도 표시해줘.
이번에는 작업 목록을 확인할게.
```

Codex는 기존 명세·과제계획과 접근 가능한 구현·검증 근거를 대조해 작업을 정리합니다. 코드에 접근하지 못한 내용은 코드 프로젝트에서 확인할 항목으로 표시합니다.

**사용자가 확인할 내용:**

- 먼저 진행할 작업이 원하는 목표와 맞는지 확인합니다.
- 이번에 만들 범위와 다른 작업에서 담당할 범위를 확인합니다.
- 완료조건을 실제 동작으로 확인할 수 있는지 봅니다.
- 먼저 결정하거나 완료해야 할 항목을 확인합니다.

선택한 작업이 기존 계획과 달라졌다면 같은 채팅에서 계획 반영을 요청합니다.

```text
[선택한 작업]을 진행할게.
검토한 내용을 기존 과제계획에 반영하고 변경 내용과 남은 결정을 알려줘.
```

명세와 계획은 [명세 문서 안내](../README.md#specifications)와 [과제별 계획](../README.md#task-plans)에서 찾아볼 수 있습니다. 이미 정한 기능 ID와 정책은 그대로 연결합니다.

## 2. Issue 초안 확인하고 생성하기

### 2-1. Issue 초안 요청

선택한 작업을 이 문서 저장소의 채팅에서 Issue 초안으로 만들어 달라고 요청합니다.

```text
[선택한 작업]을 inhhlee/amr-control-system-demo의 Issue 초안으로 만들어줘.
목적, 관련 명세·기능 ID, 작업 범위, 선행 조건,
완료조건 체크리스트, 시험 방법과 예상 결과를 넣어줘.
같은 작업의 기존 Issue·PR이 있는지 확인하고 초안을 보여줘.
아직 GitHub에 게시하지 마.
```

**사용자가 확인할 내용:** 제목과 작업 범위가 의도와 맞는지, 완료조건과 시험 방법이 구체적인지 확인합니다. 바꿀 내용이 있으면 같은 채팅에서 수정을 요청합니다. 공유할 문서는 실제 URL 또는 문서명·버전·관련 ID로 연결하고, 다른 PC에서도 필요한 자료를 읽을 수 있는지 확인합니다.

### 2-2. GitHub에 생성 요청

초안을 확인한 뒤 같은 채팅에 다음과 같이 입력합니다.

```text
확인한 초안대로 inhhlee/amr-control-system-demo에 Issue를 생성해줘.
중복 여부를 다시 확인하고 생성한 Issue의 제목·번호·URL을 알려줘.
```

받은 URL을 열어 저장소·제목·본문·완료조건을 확인합니다. 일부만 생성되었으면 성공한 항목과 실패한 항목을 구분해 확인합니다. Issue 번호는 생성 결과의 실제 값을 사용합니다.

### 2-3. 코드 프로젝트로 전달

이제 별도 코드 프로젝트의 Codex 채팅을 열고 **전체 Issue URL**과 명세·계획의 접근 가능한 위치를 전달합니다. 다음 3단계의 요청문을 사용하면 됩니다.

공유 가능한 문서 URL이 없으면 문서명·버전·관련 ID와 구현에 필요한 내용을 함께 전달합니다. 코드 프로젝트에서 문서를 읽지 못하면 자료를 제공한 뒤 구현 기준을 확인합니다.

## 3. 코드 프로젝트에서 작업 준비하기

**사용자가 할 일:** `inhhlee/amr-control-system-demo`의 코드 폴더를 Codex 프로젝트로 열고 작업 준비를 요청합니다.

```text
문서 프로젝트에서 만든 [전체 Issue URL]을 작업하려고 해.
기준 문서는 [접근 가능한 명세·계획 위치, 문서명·버전·관련 ID]야.
이 코드 저장소의 지침·기존 구현·실행 방법을 확인해줘.
원격 저장소가 inhhlee/amr-control-system-demo인지 확인하고
기존 변경을 보존하면서 필요한 작업과 선행 조건을 알려줘.
자료에 접근하지 못하거나 추가 결정이 필요하면 구체적으로 알려줘.
```

**사용자가 확인할 내용:** 대상 저장소, 기존 변경, 선행 조건, 사용할 시험 방법을 확인합니다. 문서의 요구와 코드가 다르면 차이를 보고 이번에 적용할 기준을 정합니다.

Codex는 코드 저장소의 `AGENTS.md`와 기존 협업 규칙을 확인합니다. 필요한 설정 보완이 있으면 변경 대상과 이유를 확인하고 반영을 요청합니다.

별도 규칙이 없다면 작업 브랜치는 `codex/<이슈번호>-<짧은-영문-설명>`, 커밋 메시지는 `<타입>: <한글 요약> (#이슈번호)`를 사용합니다. PR에는 관련 Issue·변경 내용·실제 시험 결과·남은 작업을 연결합니다.

문서 저장소의 스킬은 기준 문서를 상대 링크로 참조합니다. 코드 프로젝트에서 해당 스킬이 보이지 않으면 코드 저장소의 지침과 전달한 명세·계획으로 작업하며, 스킬 폴더만 복사하지 않습니다.

## 4. 구현·시험·PR 진행하기

아래 요청은 모두 코드 프로젝트의 채팅에 입력합니다. 한 Issue를 구현·시험한 뒤 PR로 검토하는 것을 기본 단위로 사용합니다.

### 구현과 시험 요청

```text
[전체 Issue URL]을 기준으로 구현해줘.
기존 작업 브랜치·PR이 있으면 확인하고, 없으면 저장소 규칙에 맞는
작업 브랜치를 준비해줘. 기존 사용자 변경은 보존해줘.
Issue 범위의 기능을 구현하고 완료조건에 맞춰 시험해줘.
변경 내용, 실제 시험 결과·증거, 미검증 항목과 직접 확인할 절차를 알려줘.
커밋·푸시·PR 생성은 결과를 확인한 뒤 요청할게.
```

**사용자가 확인할 내용:** 구현한 범위가 Issue와 맞는지, 어떤 시험을 실제 수행했는지, 직접 확인하거나 남겨 둔 항목이 무엇인지 확인합니다. 직접 시험할 때는 안내받은 절차와 예상 결과를 사용합니다.

문제가 있으면 입력·기대 결과·실제 현상·증거를 같은 채팅에 전달합니다.

```text
[환경과 입력]으로 확인했을 때 [실제 현상]이 발생했어.
기대 결과는 [완료조건]이고 증거는 [로그·화면 위치]야.
원인을 확인하고 수정한 뒤 영향받는 시험 결과를 알려줘.
```

### 커밋·PR 생성과 검토 요청

변경과 시험 결과를 확인하면 다음을 요청합니다.

```text
이번 Issue에 해당하는 변경만 확인해 커밋·푸시하고 PR을 만들어줘.
PR에는 관련 Issue, 변경 내용, 실제 시험 결과와 증거,
미검증 항목·남은 작업을 넣어줘. PR URL을 알려줘.
병합은 검토한 뒤 요청할게.
```

받은 PR URL을 열어 **Files changed**의 변경과 **Conversation**의 설명을 확인합니다. Issue를 전부 완료한 PR에는 `Closes #번호`를 연결하고, 일부만 다루는 PR에는 남은 범위를 적습니다. [GitHub Issue와 PR 연결 안내](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

보조 코드 리뷰를 받으려면 같은 채팅에 요청합니다.

```text
[PR URL]을 검토하고 버그 가능성·요구 누락·시험 누락이 있으면 알려줘.
각 문제의 위치·발생 조건·영향과 수정 방향을 설명해줘.
```

필요한 수정이 끝나면 영향받는 시험 결과와 같은 PR의 변경을 다시 확인합니다. 저장소에서 요구하는 사람의 승인과 자동 검사도 확인합니다.

### 병합과 결과 정리 요청

먼저 준비 상태를 확인합니다.

```text
[PR URL]의 Issue 완료조건, 시험 근거, 남은 리뷰 지적,
필수 승인·검사와 충돌 상태를 확인하고 병합 준비 상태를 알려줘.
```

사용자가 결과를 확인하고 병합하기로 결정하면 다음을 요청합니다.

```text
확인한 [PR URL]을 저장소에서 허용하는 방식으로 병합해줘.
실행 직전에도 필수 승인·검사·충돌을 확인하고 차단 조건이 있으면 알려줘.
병합 결과와 관련 Issue 상태를 확인하고,
문서 프로젝트에 전달할 PR URL·코드 버전·시험 결과·증거·남은 작업을 정리해줘.
```

**사용자가 확인할 내용:** PR의 **Merged** 상태와 Issue의 완료 범위를 확인합니다. 브랜치 정리가 필요하면 병합되었고 보존할 변경이 없는 해당 브랜치만 정리하도록 별도로 요청합니다.

## 5. 동시 작업과 충돌 해결

여러 작업을 함께 진행하거나 다른 변경을 반영해야 할 때 참고합니다. 한 Issue를 처음 진행하는 동안에는 해당 작업의 개발 사이클을 따라가면 됩니다.

동시 작업 전에는 공유 파일·선행 조건·병합 순서를 검토해 달라고 요청합니다. 독립적으로 작업할 때는 각 코드 작업 디렉터리를 따로 사용합니다.

```text
[Issue A]와 [Issue B]를 함께 진행할 수 있는지 검토해줘.
겹치는 파일·데이터 계약·선행 조건과 권장 작업·병합 순서를 알려줘.
```

진행 중인 브랜치에 다른 변경을 반영해야 하면 다음을 요청합니다.

```text
현재 작업과 기존 변경을 보존하면서 최신 기본 브랜치를 반영해줘.
충돌이 생기면 양쪽 변경의 목적과 영향을 확인해 해결해줘.
사용자 결정이 필요한 내용은 선택지와 영향을 알려줘.
반영 후 영향받는 기능을 시험하고 실제 결과와 남은 항목을 정리해줘.
```

사용자는 충돌 해결에서 달라진 동작과 재시험 결과를 확인합니다. 두 작업의 완료조건을 충족했는지 확인한 뒤 같은 PR의 검토·병합 절차를 이어갑니다.

## 6. 마무리와 업무 기록

**사용자가 할 일:** 이 문서 저장소의 채팅으로 돌아와 코드 프로젝트에서 받은 결과를 전달합니다.

```text
코드 프로젝트의 작업 결과는 [Issue URL·PR URL·코드 버전·시험 결과·증거 위치]야.
이 결과를 확인하고 해당 날짜의 일일업무와 관련 주간 기록에 반영해줘.
실제 완료 범위, 미검증 항목, 남은 문제와 다음 작업을 적어줘.
전달받은 보고와 직접 확인한 근거를 구분하고 갱신한 파일을 알려줘.
```

**사용자가 확인할 내용:** 업무 기록의 완료 범위와 상태, Issue·PR·검증 근거 링크를 확인합니다. 이번 Issue의 완료를 과제 전체 완료로 확대하지 않았는지도 확인합니다.

상세 시험 결과는 [검증결과 양식](양식/검증결과.md)과 [공통 검증 기록 기준](공통%20작성%20규칙.md#verification-records)에 맞춰 연결합니다. 실행하지 못한 항목은 미검증과 재개 조건을 기록합니다.

## 7. 문제 해결

문제가 생기면 실패한 단계와 오류 내용을 같은 채팅에 전달합니다.

| 사용자가 겪는 문제 | 요청하거나 확인할 내용 |
| --- | --- |
| GitHub 저장소를 조회할 수 없음 | 대상 저장소와 연결 계정·접근 권한을 확인해 달라고 요청 |
| Issue 생성 실패 | 오류 원인과 필요한 권한 확인 요청. 성공한 Issue가 있으면 URL을 확인한 뒤 실패한 항목만 다시 요청 |
| 코드 프로젝트가 명세를 읽지 못함 | 접근 가능한 문서 URL·파일 또는 필요한 내용을 전달 |
| 구현 결과가 기대와 다름 | 시험 입력·기대 결과·실제 현상·로그나 화면을 전달 |
| 푸시·PR 생성 실패 | 대상 저장소·Git 인증·기존 PR·브랜치 규칙 확인 요청 |
| PR 병합 불가 | 필수 승인·검사·충돌·남은 지적을 확인해 달라고 요청 |
| 다음에 할 일을 모르겠음 | 현재 결과와 남은 작업을 보여 주고 다음 작업 후보 요청 |

## 부록. 직접 GitHub MCP를 설정할 때

**기존 연결을 사용할 수 있다면 이 부록을 실행할 필요가 없습니다.** 직접 연결을 준비할 때 필요한 PAT 권한과 CLI 실행 방법입니다. PAT는 GitHub 접근을 허용하는 개인 토큰입니다.

<a id="github-pat"></a>
<a id="0-2-github-연결과-pat-권한-준비"></a>

### PAT 권한 준비

**기존 GitHub 연결을 사용하는 경우 아래 PAT 설정은 건너뛴다.** 연결 확인이 필요하면 [GitHub 연결 확인](#github-check)에서 대상 저장소 조회와 Issue 생성 도구 제공 여부를 확인한다. 아래 설정은 직접 GitHub MCP를 등록하는 경우에 사용한다.

[GitHub 토큰 설정](https://github.com/settings/personal-access-tokens)에서 기존 Fine-grained PAT를 편집하거나 새로 만든다. `Resource owner`와 `Repository access`에서 **Issue를 등록할 코드 저장소**가 포함되어 있는지 확인한 뒤 `Repository permissions`를 설정한다.

| 권한 | 문서 공간용: 코드·PR 조회와 Issue 관리 | 코드 공간용: 푸시·PR·병합 및 Issue 관리 |
| --- | --- | --- |
| Contents | Read-only | Read and write |
| Issues | Read and write | Read and write |
| Pull requests | Read-only | Read and write |

Issue 생성에 필요한 쓰기 권한은 `Issues`다. 문서 공간의 `Contents`와 `Pull requests` 읽기 권한은 구현 근거와 기존 PR을 조회하기 위한 구성이다. 코드 공간에서는 실제 수행할 작업에 맞춰 권한을 추가한다. [GitHub Issue 생성 권한](https://docs.github.com/en/rest/issues/issues#create-an-issue) · [Fine-grained PAT 작업별 권한](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)

한 PAT를 두 공간에서 함께 사용할 수도 있다. 공간별로 권한을 제한하려면 각각의 PAT를 준비하고 각 CLI 터미널에 해당 작업용 PAT를 입력한다. 폴더를 바꾸는 것만으로 같은 PAT의 권한이 줄어들지는 않는다. 만료·저장소 접근·조직 승인 상태도 확인하며, PAT 권한이 있어도 저장소의 필수 리뷰·검사·병합 규칙은 적용된다.

<a id="github-cli"></a>
<a id="0-3-토큰-입력-후-codex-cli-실행--직접-mcp를-연결할-때"></a>

### 토큰 입력 후 Codex CLI 실행

**Codex 앱의 기존 GitHub 연결을 사용한다면 이 절의 명령은 실행하지 않아도 된다.** 연결 확인이 필요하면 [GitHub 연결 확인](#github-check), 이미 확인했다면 [1단계](#work-selection)로 진행한다. 다음은 CLI가 설치된 환경에서 **문서 폴더를 열고 실행하는 방법**이다. CLI 로그인은 안내에 따라 진행하며, GitHub PAT는 GitHub MCP 인증에 사용한다.

**Git Bash:** 문서 저장소 폴더에서 한 줄씩 실행한다. `read`에서 토큰을 붙여넣고 Enter를 누른다. 입력 내용은 화면에 표시되지 않는다.

```bash
cd /c/process-plan
read -r -s -p "GitHub PAT: " GITHUB_PAT
export GITHUB_PAT
codex --version
codex mcp list
```

목록에 `github`가 없으면 아래 명령으로 한 번 등록한다. 토큰 값 대신 환경 변수 이름을 지정한다. 기존 항목이 있으면 URL과 사용하는 환경 변수 이름이 이번 연결과 일치하는지 확인한다.

```bash
codex mcp add github --url https://api.githubcopilot.com/mcp/ --bearer-token-env-var GITHUB_PAT
```

같은 Git Bash에서 Codex를 실행한다.

```bash
codex
```

**PowerShell을 사용한다면:** Git Bash의 `read`·`export` 대신 아래를 사용한다. 경로는 실제 문서 폴더에 맞춘다.

```powershell
Set-Location 'C:\process-plan'
$githubPatInput = Read-Host 'GitHub PAT' -AsSecureString
$env:GITHUB_PAT = [System.Net.NetworkCredential]::new('', $githubPatInput).Password
Remove-Variable githubPatInput
codex --version
codex mcp list
```

이후 위의 `codex mcp add ...`를 필요한 경우에만 실행하고, 같은 PowerShell에서 `codex`를 실행한다. 등록 구문은 [OpenAI 명령 안내](https://learn.chatgpt.com/docs/developer-commands)와 [GitHub의 Codex MCP 설치 안내](https://github.com/github/github-mcp-server/blob/main/docs/installation-guides/install-codex.md)를 따른다.

- `codex mcp list`는 직접 등록한 MCP 설정을 확인하는 명령이다. 실제 연결 성공·Issue 쓰기 권한·앱의 모든 연결을 확인하는 명령은 아니다. 시작한 CLI에서 `/mcp`와 연결 확인 요청으로 확인한다.
- 환경 변수는 입력한 터미널과 그 터미널에서 실행한 프로세스에 적용된다. 이미 실행 중인 Codex 앱·다른 터미널에 자동 전달되지 않는다. 새 터미널에서 이 방식을 쓰려면 토큰을 다시 입력한다. [OpenAI MCP 설정 안내](https://learn.chatgpt.com/docs/extend/mcp)
- 토큰 값을 문서·프롬프트·커밋에 넣지 않는다. CLI 종료 후 같은 셸에서 Git Bash는 `unset GITHUB_PAT`, PowerShell은 `Remove-Item Env:GITHUB_PAT`로 지울 수 있다.
- 이 저장소의 `.agents/skills/`에 있는 스킬을 사용한다. Claude Code 실습의 `.claude/skills/prd-feature` 복사는 필요하지 않다. 코드 공간에서는 해당 공간의 지침과 스킬 접근을 별도로 확인한다.
- GitHub MCP 인증과 코드 공간의 `git push` 인증은 별개로 확인한다. PAT를 MCP에 입력했다고 Git 인증까지 설정되는 것은 아니다.
