# Codex와 GitHub MCP 기반 관제 프로젝트 개발 진행 절차

- 작성자: 이인호 연구원
- 버전: v0.0 — 기존 파일명 기준, 2026-10-06 저장 위치 정리

기존에 준비한 PRD 역할의 요구사항·기능명세와 과제계획을 바탕으로, 앞으로의 개발 작업을 **GitHub Issue 단위로 나누고 Codex를 활용해 구현·검증·리뷰까지 진행**한다.

PRD 작성에 해당하는 준비는 기존 문서와 스킬을 활용한다. 다음 단계에서는 현재 코드와 명세를 대조해 남은 작업을 정리하고, 각 작업의 변경 내용과 시험 결과를 Issue와 PR에 연결한다. 우선 작업 하나에 아래 절차를 적용한 뒤 나머지 작업에도 반복한다.

```text
기존 PRD·명세 확인 → 작업 나누기(Issue) → 협업 규칙 확인
→ [브랜치 → Codex 구현 → 시험 → 커밋 → PR → 리뷰 → 병합] 반복
→ Issue 종료 및 일일·주간 업무 기록
```

- 적용 대상은 현재 진행 중인 가상 AMR 관제 프로젝트다.
- `text` 블록은 해당 단계에서 Codex에 입력할 요청문이다. 대괄호로 표시한 작업·Issue·PR 번호는 실제 대상으로 바꾼다.
- `powershell` 블록은 실제 코드 저장소의 터미널에서 확인할 명령이다.
- 각 단계의 결과를 확인하고 다음 단계로 진행한다. 아래 요청문은 앞으로 사용할 절차이며, 실제 진행 상태는 기존 업무 기록에서 관리한다.
- 문서 작성·구현·실행 검증을 구분한다. 명세가 준비되어 있다는 사실만으로 기능 구현이나 시험을 완료한 것으로 표시하지 않는다.

### 진행 단계

| 단계 | 내용 | 확인할 결과 |
| --- | --- | --- |
| 0 | 개발환경과 GitHub 연결 확인 | 실제 코드 저장소, 기본 브랜치, 사용 가능한 도구·권한 |
| 1 | 기존 PRD·명세와 현재 구현 확인 | 구현·보완·검증이 필요한 작업과 선행 조건 |
| 2 | 작업 단위로 Issue 생성 | 목적·범위·완료조건·시험 방법이 있는 Issue |
| 3 | 기존 협업 규칙 확인·보완 | 프로젝트 지침, 브랜치·커밋 규칙, PR 양식 |
| 4 | Issue 하나의 개발 사이클 수행 | 구현 코드, 시험 근거, PR과 리뷰 결과 |
| 5 | 다른 작업의 변경 반영과 충돌 해결 | 최신 변경을 반영한 코드와 재시험 결과 |
| 6 | 병합 결과 확인과 업무 기록 | Issue·PR·검증 결과가 연결된 진행 기록 |

Issue 개수와 일정은 실제 작업 범위와 의존성에 맞춰 정한다. 작업 순서는 Issue 번호가 아닌 우선순위와 선행 작업을 기준으로 선택한다.

## 0. 사전 준비

### 0-1. 기존 문서와 개발 도구 확인

문서 저장소는 현재 열어 둔 이 저장소의 작업 폴더다. 제품 코드를 변경할 위치는 [개발환경 및 코드 저장 위치](../관제시스템%20과제%20진행/개발환경.md)에서 확인한다. Issue와 PR의 대상은 실제 코드 저장소를 기준으로 확인하며, 문서 저장소의 `origin`을 그대로 사용하지 않는다.

| 확인 대상 | 사용할 자료·도구 | 확인할 내용 |
| --- | --- | --- |
| 기존 PRD에 해당하는 문서 | [명세 문서 안내](../README.md#specifications) | 요구사항·공통규칙·데이터·기능·결정사항의 위치 |
| 개발계획 | 과제별 `과제계획.md` | 이번 작업의 범위, 선행 조건, 완료 기준 |
| AI 작업 규칙 | 문서 저장소와 실제 코드 저장소의 `AGENTS.md` | 각 저장소에서 적용할 지침 |
| 작업별 스킬 | 문서 저장소의 `.agents/skills/` | 명세·계획·구현 검증·업무 기록 절차 |
| 개발 도구 | Codex | 대상 프로젝트에서 파일 확인과 명령 실행이 가능한지 |
| GitHub 연동 | GitHub MCP 등 현재 연결된 GitHub 도구 | 대상 저장소 접근과 Issue·PR 관련 작업 가능 여부 |
| 버전 관리 | Git | 현재 브랜치, 기존 변경, 원격 저장소, 기본 브랜치 |

Codex는 프로젝트 지침에 `AGENTS.md`를 사용하고, 저장소 스킬은 `.agents/skills/`에서 읽는다. 현재 문서 저장소의 지침과 스킬을 활용하되, 실제 코드 작업에는 코드 저장소의 지침도 함께 적용한다. [OpenAI AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [OpenAI 스킬 안내](https://learn.chatgpt.com/docs/build-skills)

### 0-2. GitHub 연결과 인증 확인

GitHub MCP는 저장소 조회와 Issue·PR 관리에 사용할 수 있다. 실제 가능한 작업은 연결된 도구, 인증 계정, 저장소 권한에 따라 확인한다. [GitHub MCP 공식 안내](https://github.com/github/github-mcp-server)

| 작업 | 사전에 확인할 내용 |
| --- | --- |
| 저장소·Issue·PR 조회 | 계정이 대상 저장소에 접근할 수 있는지 |
| Issue 생성·수정 | 연결된 도구와 계정이 Issue 쓰기 작업을 지원하는지 |
| PR 생성·리뷰 등록 | PR 쓰기 권한과 필요한 도구가 있는지 |
| PR 병합 | 병합 권한, 필수 리뷰·검사와 저장소 병합 규칙 |
| 로컬 커밋·원격 푸시 | 로컬 Git 설정과 원격 저장소에 대한 Git 인증 |

Codex 앱에서는 연결된 GitHub 도구의 상태를 확인한다. Codex CLI를 함께 설치한 환경에서는 다음 명령으로 CLI 버전과 직접 등록한 MCP 서버 목록을 확인할 수 있다. 이 목록만으로 앱의 모든 연동 기능이나 쓰기 권한까지 확인한 것으로 보지는 않는다. [OpenAI MCP 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

```powershell
codex --version
codex mcp list
```

토큰이 필요한 연결은 해당 연결 방식에 맞게 설정한다. 토큰 값을 문서·프롬프트·커밋에 넣지 않는다. GitHub 도구의 인증과 터미널의 `git push` 인증은 각각 확인한다.

### 0-3. Codex로 환경 점검

```text
관제 프로젝트의 Issue 기반 개발을 시작하기 전에 환경을 점검해줘.
1. 현재 문서 저장소의 개발환경 안내에서 실제 코드 저장소 위치를 확인하고,
   문서 저장소와 코드 저장소의 경로·역할을 구분해줘.
2. 실제 코드 저장소의 AGENTS.md, 실행 안내, origin,
   기본 브랜치, 현재 브랜치와 변경 파일을 확인해줘.
3. 현재 문서 저장소의 기존 명세·과제계획과 사용할 스킬의 위치를 확인해줘.
4. 연결된 GitHub 도구로 코드 저장소의 열린 Issue와 PR을 조회하고,
   조회 성공 여부와 생성·리뷰·병합 도구 및 권한의 확인 상태를 구분해줘.
5. 기존 변경은 보존하고, 연결되지 않은 항목은 필요한 준비만 알려줘.
파일 수정, Issue 생성, 브랜치 전환은 하지 말고 결과를 표로 보여줘.
```

현재 브랜치가 기본 브랜치와 다르거나 변경 파일이 있으면 먼저 그 작업과의 관계를 확인한다. 기존 변경을 지우거나 임의로 커밋해 정리하지 않는다.

## 1. 기존 PRD와 현재 구현 확인

**왜 하나?** 이미 작성한 명세와 현재 코드를 연결해 이번에 할 일을 고르기 위해서다. 기존에 구현된 기능은 현재 동작을 확인하고 필요한 보완·검증 작업을 구분한다.

이 프로젝트에서 PRD의 역할은 다음 문서가 나누어 담당한다.

| 역할 | 기존 문서 |
| --- | --- |
| 목적·요구사항·기본 범위 | [요구사항정의](../관제시스템%20과제%20진행/명세/요구사항정의.md) |
| 공통 처리 기준 | [공통규칙](../관제시스템%20과제%20진행/명세/공통규칙.md) |
| 데이터와 메시지 계약 | [공통데이터명세](../관제시스템%20과제%20진행/명세/공통데이터명세.md) |
| 기능별 입력·처리·출력·확인 방법 | [기능명세](../관제시스템%20과제%20진행/명세/기능명세.md) |
| 정책과 선행 결정 | [검토 및 결정사항](../관제시스템%20과제%20진행/명세/검토%20및%20결정사항.md) |
| 작업 순서와 완료 기준 | [과제별 계획 안내](../README.md#task-plans) |

```text
$plan-development 기존 요구사항·기능명세와 과제계획을 기준으로
[이번에 진행할 과제 또는 기능]의 후속 작업을 정리해줘.
1. 관련 요구사항·기능 ID·결정사항과 과제계획을 읽어줘.
2. 실제 코드와 기존 검증 기록을 확인해 이미 구현된 부분,
   보완할 부분, 미검증 범위를 구분해줘.
3. 각 작업의 목적·대상 모듈·선행 조건·완료조건·시험 방법을 정리해줘.
4. 완료조건은 입력·조건에 따른 관찰 가능한 결과로 써줘.
5. 기존 결정은 유지하고, 이번 작업에 영향을 주는 미정 항목만 알려줘.
새 PRD를 만들지 말고 기존 문서의 기능 ID와 근거를 연결해줘.
이번에는 작업 목록만 보여줘. 파일 수정과 구현은 하지 마.
```

작업 목록에서 아래 내용을 확인한다.

- 포함할 작업과 다른 과제에서 담당하는 범위가 구분되어 있는가.
- 기존 구현과 새로 수행할 작업이 구분되어 있는가.
- 완료조건을 실제 시험으로 확인할 수 있는가.
- 선행 결정과 다른 기능의 의존성이 표시되어 있는가.

계획 보완이 필요한 항목은 기존 과제계획에 반영한다.

```text
검토한 작업 목록을 기존 과제계획의 해당 항목에 반영해줘.
기존 경로·기능 ID·결정사항을 유지하고 상세 명세는 링크로 연결해줘.
대응 HTML이 있으면 저장소 도구 안내에 따라 다시 생성해줘.
변경한 내용과 남은 결정을 알려줘. 제품 구현은 아직 하지 마.
```

## 2. 작업 나누기와 Issue 생성

**왜 하나?** 구현·검증·리뷰가 가능한 크기로 작업을 나누고, 무엇을 해야 완료인지 공유하기 위해서다. **Issue 하나를 브랜치 하나와 PR 하나에 연결**하는 것을 기본 단위로 삼는다. 기능 크기와 의존성에 따라 작업 수를 정한다.

### 2-1. Issue 초안 작성

```text
앞에서 검토한 작업 목록을 GitHub Issue 초안으로 정리해줘.
Issue는 한 번의 구현·검증·리뷰로 확인할 수 있는 크기로 나눠줘.
신규 구현, 기존 기능 보완, 검증 작업을 실제 범위에 맞춰 구분해줘.

각 Issue 본문에 다음을 넣어줘.
- 목적
- 관련 과제·기능 ID·명세와 계획의 근거
- 이번 작업 내용과 제외·연계 범위
- 선행 Issue 또는 결정사항
- 완료조건 체크리스트
- 시험 조건·입력·예상 결과
- 산출물과 검증 결과를 기록할 위치

실제 코드 저장소의 기존 Issue와 PR을 먼저 확인하고,
같은 제목뿐 아니라 내용이 겹치는 작업이 있는지도 확인해줘.
작업 순서는 우선순위와 의존성으로 정하고, 라벨은 기존 라벨에서 골라줘.
공유 가능한 명세 URL이 있으면 연결하고, 없으면 문서명·버전·기능 ID를 적어줘.
로컬 PC 경로를 GitHub에서 열 수 있는 링크처럼 쓰지 마.
생성할 Issue의 제목·본문·작업 순서를 보여줘. 아직 게시하지 마.
```

### 2-2. 검토한 Issue 생성

```text
확인한 초안대로 실제 코드 저장소에 GitHub Issue를 생성해줘.
연결된 GitHub 도구를 사용하고, 생성 전 중복 여부를 다시 확인해줘.
이미 같은 Issue가 있으면 새로 만들지 말고 기존 항목과의 관계를 알려줘.
일부 생성에 실패하면 성공한 Issue를 다시 만들지 말고 실패한 항목을 구분해줘.
Issue 번호·제목·URL·선행 작업을 표로 보여줘. 구현은 아직 하지 마.
```

GitHub의 **Issues** 탭에서 제목·본문·라벨·완료조건을 확인한다. 번호와 URL은 생성 결과로 받은 실제 값을 사용한다.

## 3. 협업 규칙 확인과 보완

**왜 하나?** Codex와 사람이 같은 범위·작성 방식·검토 기준을 적용하도록 하기 위해서다. 기존 프로젝트 지침을 먼저 확인하고, 빠진 협업 항목만 보완한다.

| 파일 | 역할 |
| --- | --- |
| `AGENTS.md` | 저장소에서 Codex가 따를 작업 지침 |
| `.agents/skills/` | 명세·계획·구현 검증·업무 기록에 사용하는 절차 |
| `.github/pull_request_template.md` | 관련 Issue·변경 내용·검증 결과·남은 항목을 담는 PR 양식 |
| `.gitignore` | 인증정보·개인 설정·불필요한 생성물의 커밋 제외 |

다음은 적용할 협업 규칙안이다. 코드 저장소에 기존 규칙이 있으면 먼저 대조한다.

- 실제 기본 브랜치의 최신 상태에서 작업 브랜치를 만든다. 기본 브랜치에 직접 커밋하지 않는다.
- 별도 규칙이 없다면 브랜치 이름은 `codex/<이슈번호>-<짧은-영문-설명>`으로 한다.
- 커밋 메시지는 `<타입>: <한글 요약> (#이슈번호)` 형식으로 작성한다.
- 타입은 `feat`(기능), `fix`(버그), `docs`(문서), `test`(시험), `refactor`(구조 개선), `chore`(설정)를 작업 목적에 맞게 사용한다.
- 한 브랜치에서는 선택한 Issue와 그 완료에 필요한 변경을 다룬다. 범위를 넓혀야 하면 기존 Issue 보완이나 별도 Issue가 필요한지 구분한다.
- PR에는 관련 Issue와 실제 시험 결과를 연결한다. 미검증 항목은 완료 체크하지 않는다.
- 초기 설정도 작업 브랜치와 PR로 검토한다. 강제 푸시는 하지 않는다.

```text
실제 코드 저장소의 AGENTS.md와 기존 협업 규칙을 확인해줘.
현재 문서 저장소의 지침·스킬을 그대로 복사하지 말고,
코드 저장소에서 필요한 규칙과 참조 경로를 확인해줘.

위 협업 규칙안과 비교해 빠진 항목만 보완안을 만들어줘.
PR 양식에는 관련 Issue, 변경 내용, 검증 환경·방법·결과,
증거 링크, 미검증·남은 항목, 완료조건 체크리스트를 포함해줘.
.gitignore는 실제 추적 파일과 개인 설정 위치를 확인해 필요한 항목만 제안해줘.
기존 규칙과 충돌하는 부분은 구체적으로 설명해줘.
변경할 파일과 내용을 먼저 보여줘. 아직 저장하거나 커밋하지 마.
```

```text
검토한 보완안을 해당 저장소의 작업 브랜치에 반영해줘.
기존 사용자 변경과 지침을 보존하고, 이번에 변경한 파일만 확인해줘.
설정 변경을 커밋·푸시하고 기존 PR이 있으면 보완하거나 새 PR을 만들어줘.
변경 결과와 PR URL을 보여줘. 병합은 아직 하지 마.
```

문서 저장소의 스킬을 코드 저장소에서 사용할 때는 필요한 문서에 실제로 접근할 수 있는지 확인한다. 스킬 폴더만 복사하고 내부 참조가 끊긴 상태로 사용하지 않는다.

## 4. 기능 개발 사이클

선택한 Issue 하나를 기준으로 아래 여섯 단계를 진행한다.

```text
① 브랜치 생성 → ② 구현 → ③ 시험·직접 확인
→ ④ 커밋·푸시 → ⑤ PR 생성·리뷰 → ⑥ 병합·정리
```

### ① 브랜치 생성

**왜 하나?** 작업 중인 변경을 기본 브랜치와 분리하고, 시험과 검토를 마친 결과를 반영하기 위해서다.

```text
이번에는 [Issue 번호 또는 URL]을 작업할 거야.
실제 코드 저장소와 Issue의 대상이 같은지 확인하고,
Issue의 선행 작업·결정사항이 충족되었는지 확인해줘.
현재 브랜치와 변경 파일을 확인해 기존 작업을 보존해줘.
같은 Issue의 작업 브랜치나 PR이 있으면 이어서 작업할 수 있는지 확인해줘.
새 브랜치가 필요하면 원격 기본 브랜치의 최신 내용을 확인한 뒤,
저장소 규칙에 맞는 작업 브랜치를 만들어줘.
Issue 번호·제목, 저장소, 기준 브랜치와 작업 브랜치 이름을 보여줘.
구현은 아직 하지 마.
```

실제 코드 저장소의 터미널에서 확인한다.

```powershell
git branch --show-current
git status --short
```

### ② Codex로 구현

**왜 하나?** Issue에 정리한 요구와 완료조건을 실제 코드에 반영하기 위해서다. 구현 전에 현재 코드와 실행 방법을 확인하고, 기존 기능을 활용해 필요한 변경을 수행한다.

```text
$amr-implement-verify 현재 작업 브랜치의 Issue와 연결된
기존 명세·과제계획을 기준으로 구현·보완해줘.
1. 코드 저장소의 지침과 현재 구현, 실행·시험 방법을 확인해줘.
2. 기존 동작과 검증 근거를 확인하고 이번 Issue에 필요한 부분을 변경해줘.
3. 관련 완료조건에 맞는 시험을 수행하고 실제 결과를 기록해줘.
4. 변경 파일, 구현한 범위, 시험 결과와 증거,
   실행하지 못한 항목과 이유를 알려줘.
5. 내가 직접 확인해야 할 항목은 실행 순서와 기대 결과로 안내해줘.
다른 Issue의 기능은 미리 구현하지 말고, 범위 확대가 필요하면 이유를 알려줘.
커밋·푸시·PR 생성은 아직 하지 마.
```

사용할 스킬이 현재 Codex 작업에서 보이지 않으면 0단계에서 확인한 스킬 위치와 참조 문서 접근을 먼저 해결한다. 확인되지 않은 스킬 호출을 성공한 것으로 기록하지 않는다.

### ③ 시험과 직접 확인

실제 프로그램의 실행 방법에 따라 완료조건을 하나씩 확인한다. 서버·가상 AMR·GUI 등 해당 기능의 대상 환경을 사용하고, 자동 시험과 직접 확인한 내용을 구분한다.

| 확인 항목 | 기록할 내용 |
| --- | --- |
| 대상 | 과제·기능 ID·Issue 번호 |
| 환경 | 코드 버전, 실행 환경, 사용한 계약·설정 |
| 입력·조건 | 메시지, 사용자 동작, 연결 상태 등 시험에 사용한 조건 |
| 예상 결과 | Issue와 명세의 완료조건 |
| 실제 결과 | 관찰한 출력·동작·오류 |
| 판정·증거 | 통과·실패·미검증과 로그·화면·결과 파일 |

상세 결과는 [검증결과 양식](양식/검증결과.md)에 맞춰 해당 과제의 산출물로 남긴다. Mock·대역 시험과 실제 모듈 연동 시험은 구분한다.

문제가 있으면 관찰한 내용을 전달한다.

```text
[실행 환경과 시험 입력]으로 확인했을 때 [관찰한 현상]이 발생했어.
기대 결과는 [Issue의 완료조건]이고, 관련 로그·화면은 [증거 위치]야.
원인을 확인하고 이번 Issue 범위에서 수정해줘.
영향받는 항목을 다시 시험하고, 이전 결과와 새 결과를 구분해 기록해줘.
내가 재확인할 절차와 남은 미검증 항목을 알려줘. 커밋은 아직 하지 마.
```

변경 내용도 확인한다.

```powershell
git status --short
git diff
```

### ④ 커밋과 푸시

**왜 하나?** 검토할 수 있는 단위로 변경 이력을 남기고 원격 저장소에 공유하기 위해서다. 코드 저장소와 문서 저장소가 다르면 각각 관련 변경만 커밋한다.

```text
이번 Issue와 관련된 변경과 시험 결과를 확인해줘.
기존 사용자 변경·개인 설정·인증정보가 포함되지 않도록
커밋 대상 파일과 변경 내용을 확인해줘.
코드와 검증 문서가 다른 저장소에 있으면 각각 구분해줘.
저장소 규칙에 맞는 커밋 메시지를 제안하고,
대상 파일과 아직 미검증인 항목을 보여줘. 커밋은 아직 하지 마.
```

```text
확인한 파일만 스테이징하고, 제안한 메시지로 커밋한 뒤
해당 작업 브랜치를 origin에 푸시해줘.
일부 파일에 다른 작업의 변경이 섞여 있으면 해당 변경을 보존해줘.
저장소·브랜치·커밋 ID와 푸시 결과를 보여줘. PR은 아직 만들지 마.
```

### ⑤ PR 생성과 리뷰

**왜 하나?** 구현 내용과 검증 근거를 함께 검토하고 기본 브랜치에 반영할지를 판단하기 위해서다. PR은 작업 브랜치의 변경을 합치기 위한 검토 요청이다.

```text
연결된 GitHub 도구로 이번 작업 브랜치의 PR을 만들어줘.
대상 브랜치는 저장소의 실제 기본 브랜치와 협업 규칙을 확인해 선택해줘.
같은 작업의 열린 PR이 있으면 새로 만들지 말고 기존 PR을 보완해줘.
기존 PR 양식에 따라 다음을 작성해줘.
- 관련 Issue와 명세·기능 ID
- 해결할 문제와 변경 내용
- 검증 환경·방법·실제 결과·증거
- 완료조건 체크리스트
- 미검증 항목, 남은 문제와 후속 작업
시험을 실제 수행했거나 내가 확인 결과를 전달한 항목만 체크하고,
Codex가 수행한 시험과 내가 확인한 결과의 출처를 구분해줘.
이 PR로 Issue 전체를 완료하고 기본 브랜치에 병합할 경우 Closes #번호를 넣어줘.
일부 작업만 다루면 관련 Issue 링크만 넣고 남은 범위를 적어줘.
PR 번호와 URL을 보여줘. 병합은 하지 마.
```

`Closes #번호`는 같은 저장소의 Issue를 연결하는 형식이다. 다른 저장소의 Issue는 `Closes OWNER/REPO#번호`로 지정한다. 자동 종료는 PR의 대상과 병합 브랜치가 기본 브랜치인 조건 등을 확인한다. [GitHub Issue와 PR 연결 안내](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

Codex에 보조 코드 리뷰를 요청한다.

```text
[이번 PR 번호 또는 URL]을 리뷰어 관점에서 검토해줘.
관련 명세와 Issue의 완료조건, 버그 가능성,
기존 동작에 미치는 영향, 시험 누락, 범위를 벗어난 변경을 확인해줘.
문제마다 위치·발생 조건·영향·수정 방향을 설명해줘.
실제 시험으로 확인한 사실과 코드 검토에 따른 판단을 구분해줘.
결과를 이 대화에 보여주고 GitHub PR에도 리뷰 코멘트로 남겨줘.
이번 요청에서는 코드를 수정하지 마.
```

GitHub에서 **Files changed**와 **Conversation**을 확인한다. 저장소에서 요구하는 사람의 리뷰와 필수 검사를 충족했는지도 확인한다. Codex의 검토 결과만으로 실행 시험이나 필수 승인이 완료된 것으로 판단하지 않는다.

- 수정이 필요하면 같은 브랜치에서 ②~④를 반복한다.
- 수정 후 영향받는 항목을 다시 확인하고 같은 PR에 결과를 갱신한다.
- 해결한 지적과 남은 지적을 구분한다.

### ⑥ 병합과 정리

먼저 병합에 필요한 조건을 확인한다.

```text
[이번 PR 번호 또는 URL]의 병합 준비 상태를 확인해줘.
Issue 완료조건과 검증 근거, 해결되지 않은 리뷰 지적,
필수 승인·자동 검사 결과, 충돌 여부를 확인해줘.
병합 가능한 항목과 아직 해결해야 할 항목을 구분해서 보여줘.
이번에는 병합하거나 브랜치를 삭제하지 마.
```

병합할 준비가 된 PR에 대해 다음과 같이 진행한다.

```text
확인한 PR을 저장소에서 허용하는 병합 방식으로 병합해줘.
실행 직전에도 필수 승인·검사와 충돌 상태를 확인하고,
차단 조건이 있으면 우회하지 말고 해당 결과를 알려줘.
병합 후 관련 Issue가 완료 범위에 맞게 닫혔는지 확인해줘.
로컬의 기존 변경을 보존하면서 기본 브랜치의 최신 내용을 반영해줘.
병합이 확인되고 미반영 변경이 없는 이번 작업 브랜치만
로컬과 origin에서 정리해줘. 공유 중이거나 보존이 필요한 브랜치는 남겨줘.
PR·Issue 상태, 병합 결과와 브랜치 정리 결과를 보여줘.
```

GitHub와 로컬에서 아래를 확인한다.

- PR이 **Merged** 상태이며 의도한 브랜치에 반영되었는가.
- Issue가 실제 완료조건에 맞게 종료되고 PR과 연결되어 있는가.
- 기본 브랜치에서 반영된 변경과 커밋 기록을 확인할 수 있는가.
- 병합 과정에서 실행 결과에 영향을 주는 변경이 생겼다면 필요한 재시험을 했는가.

다음 Issue는 선행 작업과 우선순위를 확인해 선택하고 ①~⑥을 반복한다.

## 5. 동시 작업과 충돌 해결

다른 작업이 먼저 병합되면 진행 중인 브랜치에 최신 변경을 반영해야 한다. 처음에는 Issue 하나의 개발 사이클을 확인하고, 이후 작업을 나누어 진행할 필요가 있을 때 적용한다.

### 5-1. 작업 간 의존성 확인

```text
[Issue A]와 [Issue B]를 나누어 진행할 수 있는지 검토해줘.
공유하는 파일·모듈·데이터 계약과 선행 조건을 확인하고,
독립적으로 가능한 부분과 먼저 완료해야 할 부분을 구분해줘.
병합 순서와 함께 재시험해야 할 기능을 제안해줘.
지금은 작업 방식만 보여줘. 브랜치 생성과 구현은 하지 마.
```

동시 작업의 허용 범위는 실제 코드 저장소의 지침을 따른다. 독립적인 작업은 각각의 브랜치에서 4단계 절차를 수행한다. 동시에 실행하는 작업은 작업 디렉터리를 분리하고, 같은 디렉터리에서 서로 브랜치를 전환하지 않는다. 의존성이 있는 작업은 선행 결과를 반영한 뒤 진행한다.

### 5-2. 최신 변경 반영

A의 PR이 병합된 뒤 B 브랜치에 최신 기본 브랜치를 반영하는 요청 예시다.

```text
[Issue B]의 작업 브랜치와 현재 변경을 확인해줘.
기존 변경을 보존한 상태에서 원격 기본 브랜치의 최신 내용을 가져와
저장소 규칙에 따라 B 브랜치에 반영해줘.
충돌이 나면 충돌 파일과 양쪽 변경의 목적·영향을 비교하고,
두 작업의 요구사항을 충족하는 해결안을 먼저 보여줘.
정책 판단이 필요한 항목은 관련 명세·결정사항에 연결해줘.
충돌이 없으면 반영 결과와 필요한 재시험을 알려줘.
충돌 수정과 푸시는 아직 하지 마.
```

### 5-3. 충돌 해결과 재시험

```text
확인한 해결안대로 충돌을 수정해줘.
A와 B의 완료조건 및 공통 기능 중 영향받는 항목을 다시 시험해줘.
실제 결과와 증거를 기록하고, 미검증 항목은 구분해줘.
실패가 있으면 원인과 수정 결과를 확인한 뒤 다음 단계로 진행해줘.
변경이 준비되면 관련 파일만 커밋하고 현재 브랜치를 푸시해줘.
강제 푸시는 하지 말고 기존 PR의 변경·검증 결과를 갱신해줘.
병합은 아직 하지 마.
```

충돌은 같은 부분의 수정이나 파일 삭제·수정처럼 Git이 자동으로 합칠 수 없는 변경이 만날 때 발생한다. 충돌 표시를 제거한 뒤에도 요구한 동작이 유지되는지 확인해야 한다. [GitHub 충돌 해결 안내](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line)

재시험 후에는 4단계 ⑤의 리뷰와 ⑥의 병합 절차로 마무리한다.

## 6. 마무리와 업무 기록

### 결과 확인

- [ ] Issue에 관련 명세·기능 ID·작업 범위·완료조건이 연결되어 있다.
- [ ] 이번 작업의 변경 코드와 산출물을 확인할 수 있다.
- [ ] 실제 시험의 환경·입력·예상·결과·판정·증거가 기록되어 있다.
- [ ] 미검증 항목과 남은 작업이 완료 항목과 구분되어 있다.
- [ ] PR에 관련 Issue·변경 내용·시험 결과·리뷰 조치가 연결되어 있다.
- [ ] 병합한 PR과 종료한 Issue의 상태가 실제 완료 범위와 일치한다.
- [ ] 일일·주간 기록에서 Issue·PR·검증 결과를 찾아갈 수 있다.

### 업무 기록 반영

```text
$record-work 이번 Issue에서 실제 수행하고 확인한 결과를
현재 문서 저장소의 해당 날짜 일일업무와 관련 주간 기록에 반영해줘.
Issue·PR URL, 변경 범위, 검증 결과와 증거 위치를 요약해서 연결해줘.
내가 보고한 확인 결과와 Codex가 직접 실행한 결과를 구분해줘.
미검증 항목, 남은 문제, 다음에 수행할 작업도 함께 적어줘.
이번 Issue 완료를 과제 전체 완료로 확대하지 말고,
과제계획과 전체일정의 상태는 해당 완료 기준과 실제 근거로 판단해줘.
상세 내용은 담당 산출물에 두고 업무 기록에는 요약과 링크를 남겨줘.
갱신한 파일과 반영 결과를 보여줘.
```

### 도구별 역할

| 도구·문서 | 역할 | 적용 기준 |
| --- | --- | --- |
| 기존 PRD·명세 | 무엇을 어디까지 만들지 정의 | 기존 요구·기능 ID·결정사항 유지 |
| 과제계획 | 작업 순서와 시험·완료 기준 정리 | 이번 작업과 과제 전체 범위 구분 |
| Codex | 문서·코드 확인, 구현·시험·검토 지원 | 저장소 지침과 선택한 Issue 범위 적용 |
| GitHub MCP | Issue·PR 조회와 관리 | 실제 연결된 기능·권한 확인 후 사용 |
| Issue | 개별 작업의 목적·범위·완료조건 공유 | 구현·검증·리뷰가 가능한 작업 크기 |
| Branch | 작업 변경 분리 | 저장소 규칙과 최신 기준 브랜치 적용 |
| Commit | 의미 있는 변경 이력 기록 | 관련 파일만 포함하고 Issue 연결 |
| PR | 변경과 검증 근거 검토 | 리뷰 지적·필수 검사 확인 후 병합 |
| 업무 기록 | 실제 진행과 다음 작업 보고 | 산출물·Issue·PR·검증 근거 연결 |

첫 적용은 **작업 하나의 명세 → Issue → 코드 → 시험 → PR → 업무 기록이 연결되는지** 확인하는 범위로 진행한다. 이후 같은 절차로 작업을 이어간다.

## 7. 문제 해결

| 증상 | 확인 순서 |
| --- | --- |
| 기존 스킬이 보이지 않음 | 현재 프로젝트와 `.agents/skills/` 위치 → 스킬 이름과 `SKILL.md` → 참조 문서 접근 여부 |
| `codex` 명령을 찾을 수 없음 | CLI 설치 여부와 PATH 확인. 앱을 사용하는 경우 앱에서 작업 가능 여부를 별도로 확인 |
| GitHub 조회 실패 | 연결 상태 → 인증 계정 → 대상 저장소 접근 권한 → 조직의 접근 정책 |
| 조회는 되지만 Issue·PR 생성 실패 | 쓰기 도구 제공 여부 → 해당 작업 권한 → 기존 항목 중복 여부 |
| `git push` 실패 | 실제 원격 저장소 → 로컬 Git 인증 → 저장소 쓰기 권한 → 브랜치 보호 규칙 |
| PR 생성 실패 | 작업 브랜치의 푸시 여부 → 대상 브랜치와 변경 차이 → 기존 PR → 생성 권한 |
| PR 병합 불가 | 미해결 지적 → 필수 승인 → 자동 검사 → 충돌 → 허용 병합 방식 |
| 병합 후 Issue가 열려 있음 | 완료 범위 → PR의 연결 문구 → 대상 저장소·Issue 번호 → 기본 브랜치 병합 여부 |
| 시험은 실행하지 못했는데 완료로 표시됨 | 체크 해제 → 미검증 이유와 재개 조건 기록 → 시험 후 실제 근거로 갱신 |
| Codex가 요청 범위를 넘어 진행함 | 현재 작업 중지 → 변경 내역 확인 → 수행할 단계와 중단 지점을 명시 |

기본 브랜치에서 커밋 전 작업을 시작한 경우에는 변경을 보존해 작업 브랜치로 옮긴다.

```text
기본 브랜치에서 작업하다가 아직 커밋하지 않은 변경이 생겼어.
현재 브랜치·변경 파일·작업 내역을 먼저 확인하고,
[이번 Issue 번호 또는 URL]에 해당하는 변경과 기존 변경을 구분해줘.
변경을 잃지 않도록 저장소 규칙에 맞는 작업 브랜치로 옮겨줘.
다른 작업과 섞여 있어 이동 방법을 결정해야 하면 구체적인 선택지를 알려줘.
브랜치와 보존된 변경 목록을 보여줘. 커밋은 아직 하지 마.
```

해결되지 않으면 대상 저장소, 수행한 명령, 오류 메시지와 실패 단계를 정리한다. 인증정보는 공유하지 않는다.

### 자주 쓰는 확인 명령

| 명령 | 실행 위치 | 용도 |
| --- | --- | --- |
| `git remote -v` | 실제 코드 저장소 터미널 | 원격 저장소 확인 |
| `git status --short` | 실제 코드 저장소 터미널 | 변경 파일 확인 |
| `git diff` | 실제 코드 저장소 터미널 | 스테이징 전 변경 내용 확인 |
| `git diff --cached` | 실제 코드 저장소 터미널 | 스테이징한 변경 내용 확인 |
| `git branch --show-current` | 실제 코드 저장소 터미널 | 현재 브랜치 확인 |
| `git log --oneline -10` | 실제 코드 저장소 터미널 | 최근 커밋 기록 확인 |
| `codex --version` | Codex CLI를 설치한 터미널 | CLI 버전 확인 |
| `codex mcp list` | Codex CLI를 설치한 터미널 | 직접 등록한 MCP 서버 목록 확인 |
