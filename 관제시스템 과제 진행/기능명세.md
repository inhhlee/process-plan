## 과제1 통신 서버와 클라이언트

### COM-01 실시간 메시지 송수신

- 목적: 가상 AMR과 관제 간 MQTT 양방향 송수신을 제공한다.
- 입력: Broker 접속 설정, 구독 Topic, AMR 발행 메시지, 관제 명령.
- 처리: Broker에 접속하여 정의된 Topic을 구독하고 메시지 유형·대상에 따라 전달한다. 명령은 해당 AMR의 Topic으로 발행한다. AMR별 큐와 스레드 방식은 구현 설계에서 정한다.
- 출력: 수신 메시지, 발행 결과, 송수신 Log.
- 확인 방법: 서로 다른 AMR ID로 Telemetry와 Command를 보내 대상과 유형이 구분되는지 콘솔에서 확인한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-01](공통규칙.md#c-01-장비-식별), [C-05](공통규칙.md#c-05-메시지-계약); 원문 과제1 및 기존 [COM-01](#com-01-실시간-메시지-송수신)
- 상세 정의 구분: 원문 기능 범위를 기존 기능명세로 구체화한 설계 제안
- 결정할 항목: [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)

- 2026-10-05 이번 작업 연결: [과제1 작업 단위](과제1/과제계획.md#com01-work)에서 기존 Heartbeat 한 유형의 송수신 확인·필요한 보완을 수행한다. [임시 계약과 예제](공통데이터명세.md#heartbeat-contract)를 적용하며, 이 부분의 확인만으로 위 COM-01 전체를 완료하지 않는다.

### COM-02 개별 AMR Heartbeat 감시

- 목적: AMR별 Heartbeat 중단과 복구를 구분한다.
- 입력: 검증된 Heartbeat, 대상 AMR, 관제 수신 시각, 감시 설정.
- 처리: AMR별 마지막 정상 수신 시각을 관리하여 감시 기준을 비교한다. 담당 모듈과 상태 값은 D-09에서 결정한다. 통신 이상을 운행 FAULT와 동일하게 처리하지 않는다.
- 출력: AMR별 감시 상태와 변화 통지.
- 확인 방법: Broker는 유지한 채 한 AMR의 Heartbeat만 중단하고, 다른 AMR과 구분되는지 및 재개 후 복구 조건을 확인한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-03](공통규칙.md#c-03-시간), [C-04](공통규칙.md#c-04-상태의-의미), [C-09](공통규칙.md#c-09-통신-감시); 기존 [COM-02](#com-02-개별-amr-heartbeat-감시)
- 상세 정의 구분: 원문 기능 범위를 기존 기능명세로 구체화한 설계 제안
- 결정할 항목: [D-03](검토%20및%20결정사항.md#d-03-시간-계약), [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)

### COM-03 Broker 연결 상태 감시

- 목적: MQTT Client와 Broker의 연결 이상을 감지한다.
- 입력: 접속 결과, 연결·끊김 통지, KeepAlive 관련 설정.
- 처리: Broker 연결 상태를 관리하고 변화와 오류 원인을 제공한다. 복구 동작은 COM-06에 연결한다.
- 출력: Broker 연결 상태, 연결·끊김 Log.
- 확인 방법: Broker 종료·재시작 시 상태 변화가 보이고 개별 AMR의 Heartbeat 상태와 구분되는지 확인한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-04](공통규칙.md#c-04-상태의-의미), [C-09](공통규칙.md#c-09-통신-감시); 기존 [COM-03](#com-03-broker-연결-상태-감시)
- 상세 정의 구분: 원문 기능 범위를 기존 기능명세로 구체화한 설계 제안
- 결정할 항목: [D-08](검토%20및%20결정사항.md#d-08-재접속과-복구), [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)

### COM-04 메시지 유효성 검증

- 목적: 비정상 메시지가 Core의 업무 상태를 변경하지 않도록 한다.
- 입력: 수신 Topic·Payload, 공통 메시지 계약.
- 처리: 유형, JSON 형식, 필수 필드, 자료형, 허용값과 대상 ID 일치 여부를 검사한다. 유효한 데이터만 전달하고 실패 원인은 기록 후 폐기하는 안을 적용 대상으로 정리한다.
- 출력: 검증된 메시지 또는 실패 사유 Log.
- 확인 방법: 정상 입력과 JSON 오류·필수 필드 누락·자료형 오류·허용값 오류·ID 불일치를 구분한다. 비정상 입력이 전달되지 않고 그 뒤 정상 입력은 처리되는지 확인한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-01](공통규칙.md#c-01-장비-식별), [C-05](공통규칙.md#c-05-메시지-계약), [C-06](공통규칙.md#c-06-입력-검증), [C-10](공통규칙.md#c-10-기록); 기존 [COM-04](#com-04-메시지-유효성-검증)
- 상세 정의 구분: 원문 기능 범위를 기존 기능명세로 구체화한 설계 제안
- 결정할 항목: [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책), [D-10](검토%20및%20결정사항.md#d-10-loghistory-저장과-조회)

- 2026-10-05 이번 작업 연결: 기존 검증기의 Heartbeat 정상·시각 누락·ID 불일치·오류 후 정상 처리를 [HB-02~05](과제1/과제계획.md#com01-test)에서 확인한다. 실제 Core는 콘솔 출력 대역이며 운영 업무 상태의 검증으로 확대하지 않는다.

### COM-05 Command와 ACK 전달

- 목적: 원래 요청의 식별자를 유지하며 명령과 응답을 전달한다.
- 입력: 대상 AMR, CommandId가 연결된 명령, AMR의 ACK.
- 처리: Command를 대상 Topic으로 전달하고 ACK를 검증하여 Core로 전달한다. CommandId 생성 주체는 D-06에서 결정하며 통신에서 중복 생성하지 않는 안을 제안한다. 발행 결과와 AMR 동작 결과는 구분한다.
- 출력: 명령 발행 결과, 원래 식별자가 유지된 ACK.
- 확인 방법: 여러 요청의 ACK를 순서를 바꾸어 수신해도 ID와 대상이 보존되는지 확인한다. 최종 요청 상태 판단은 CORE-04에서 확인한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-08](공통규칙.md#c-08-명령과-결과); 기존 [COM-05](#com-05-command와-ack-전달)
- 상세 정의 구분: 원문 기능 범위를 기존 기능명세로 구체화한 설계 제안
- 결정할 항목: [D-06](검토%20및%20결정사항.md#d-06-commandid-생성-책임), [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외)

### COM-06 재접속과 구독 복구

- 목적: 연결 끊김 후 정의된 정책으로 MQTT 송수신을 복구한다.
- 입력: 연결 끊김, 재시도 설정, 구독 목록, 복구 대기 상태.
- 처리: 정해진 간격·횟수로 재접속하고 필요한 Topic을 다시 구독한다. 대기 중 명령의 폐기·보류·재전송과 중복 수행 방지는 D-07~08에서 결정한다.
- 출력: 재접속·재구독 결과, 복구 Log.
- 확인 방법: Broker를 중단했다가 복구하고 재접속·재구독 이후 송수신이 재개되는지 확인한다. 복구 실패와 대기 명령 처리 결과도 기록한다.
- 근거와 연결: [R-04](요구사항정의.md#r-04); [C-05](공통규칙.md#c-05-메시지-계약), [C-08](공통규칙.md#c-08-명령과-결과), [C-09](공통규칙.md#c-09-통신-감시); 원문 과제1 재접속 요구
- 상세 정의 구분: 재접속은 원문 요구이며 이번 초안에서 COM-06으로 분리한 기능; 처리 상세는 설계 제안
- 결정할 항목: [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책), [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외), [D-08](검토%20및%20결정사항.md#d-08-재접속과-복구)

## 과제2 가상 AMR

### AMR-01 설정 로드와 AMR 생성

- 목적: 설정 파일로 독립 시뮬레이터의 시험 조건을 구성한다.
- 입력: AMR 수량·ID·초기 좌표·속도·이동 경로·장애 시나리오 설정.
- 처리: 설정을 읽고 각 AMR을 생성한다. 중복 ID·잘못된 좌표·속도 등 설정 오류의 처리 기준은 D-12에서 정한다. 기존 2대 가정은 시험 예시로 다룬다.
- 출력: 생성된 AMR 목록, 초기 상태, 사용 설정 및 설정 오류.
- 확인 방법: 코드 수정 없이 수량·초기 위치·속도·경로·장애 조건을 바꾸어 실행하고 설정 반영을 확인한다.
- 근거와 연결: [R-02](요구사항정의.md#r-02), [R-03](요구사항정의.md#r-03); [C-01](공통규칙.md#c-01-장비-식별), [C-02](공통규칙.md#c-02-좌표와-속도), [C-11](공통규칙.md#c-11-설정과-시험-데이터); 기존 [AMR-01](#amr-01-설정-로드와-amr-생성)

### AMR-02 Command 수신과 동작 수행

- 목적: MOVE·STOP·RESET 후보 명령을 시뮬레이션한다.
- 입력: 대상과 식별자가 포함된 명령, 현재 위치·State·Alarm, 이동 설정.
- 처리: State·Alarm 및 입력 조건에 따라 수행 가능 여부를 판단한다. MOVE는 위치를 갱신하고 STOP은 이동 정지를 요청하며 RESET은 정의된 복구 조건을 확인한다. 허용 상태·정지 후 재출발·도착 오차는 미정이다.
- 출력: 위치·운행 상태 변화, 수행 결과 또는 거부 이유.
- 확인 방법: MOVE의 이동·도착, 이동 중 STOP, 장애 원인 해소 전후 RESET 및 허용되지 않은 요청을 개별 시험한다.

### AMR-03 State와 Alarm 관리

- 목적: 설정한 장애 조건에 따른 알람 발생·해제와 운행 상태 변화를 생성한다.
- 입력: 현재 시뮬레이션 상태, 장애 설정, 장애 발생·해제 조건, RESET 요청.
- 처리: 장애 조건을 평가해 AlarmCode·Level·발생/해제 상태를 생성하고 상태 전이표에 따라 State를 갱신한다. 예시 거리·횟수를 확정 정책으로 사용하지 않는다.
- 출력: State 변화, Alarm 이벤트, 해제·복구 결과.
- 확인 방법: 설정한 장애 발생·해제 조건을 재현하고 State·Alarm이 결정된 전이 기준을 따르는지 확인한다.

### AMR-04 명령 처리 결과와 ACK 생성

- 목적: 수신한 요청에 대응하는 수행 결과를 반환한다.

- 확인 방법: 성공·거부·실패 결과의 식별자가 요청과 같은지 확인하고, 발행 성공만으로 동작 완료가 되지 않는지 확인한다.

### CORE-02 최신 상태 관리

- 목적: AMR별 최신 위치·속도·운행·연결 상태를 관리한다.
- 입력: 검증된 Telemetry, 연결 상태 통지, 발생·수신 시각, 장비 정보.
- 처리: 장비별 상태를 갱신하여 공급자에 제공한다. 최신 데이터 선택 기준과 미등록 처리 정책을 정한다. State 변경은 History 저장 대상으로 연결하고 주기 좌표 저장 범위는 D-10에서 결정한다.

### CORE-04 Command 요청과 결과 관리

- 확인 방법: 다중 요청의 역순 ACK, 다른 대상의 ACK, 알 수 없는 ID, Timeout·중복·늦은 ACK를 시험한다. 한 요청의 결과가 다른 요청에 반영되지 않는지 확인한다.

## 시험 기록 기준

각 과제의 검증 결과에는 시험한 기능 ID, 설정·입력, 수행 절차, 예상 결과, 실제 결과, 판정 및 근거를 기록한다. 아직 실행하지 않은 시험은 미검증으로 표시한다. 재접속 횟수·Timeout·좌표 오차처럼 정책이 미정인 항목은 결정한 값과 적용 버전을 시험 조건에 함께 기록한다.

예상 결과가 작성되었다는 이유로 시험을 통과로 표시하지 않는다. 결과물 작성 완료, 사용자 검토 완료, 설계 확정, 개발 완료 및 검증 통과는 별도로 관리한다.
