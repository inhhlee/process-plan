## 1. 결정 항목과 후속 작업

이 항목들은 구현 전에 필요한 범위부터 검토한다. 원문에 있는 기능을 유지하면서 상세 정책을 선택한다. 제안은 현재 결정으로 간주하지 않으며 관련 과제계획에 후속 작업을 연결한다.

### D-01 미등록 AMR 처리

- 현재 근거와 문제: v0.3 공통 기준은 Heartbeat·Telemetry 자동 등록을 기술하지만 CORE-02는 미등록 Telemetry를 제외한다. v0.0은 결정 항목으로 남긴다.
- 후속 작업과 선택 범위: 설정 등록만 허용 / 검증된 Heartbeat·Telemetry로 자동 등록. 유형별 등록 권한과 거부 기록을 정한다.
- 영향 기능: [COM-04](기능명세.md#com-04-메시지-유효성-검증), [CORE-01](기능명세.md#core-01-장비-등록과-조회)~03, [INT-01](기능명세.md#int-01-정상-운행과-표시-검증)
- 결정 상태: 미정

### D-02 좌표·속도·화면 대응

- 현재 근거와 문제: X/Y와 속도 분리는 기존 초안에 있다. 좌표 단위·범위·축 방향·원점·Map 변환은 명시가 부족하다.
- 후속 작업과 선택 범위: 단위, 유효 범위, 축 방향, 화면 변환, 도착 허용 오차를 정의한다.
- 영향 기능: [AMR-01](기능명세.md#amr-01-설정-로드와-amr-생성)~02, [GUI-02](기능명세.md#gui-02-map-view와-선택-amr-정보), [CORE-02](기능명세.md#core-02-최신-상태-관리), [INT-01](기능명세.md#int-01-정상-운행과-표시-검증)
- 결정 상태: 미정

### D-03 시간 계약

- 현재 근거와 문제: Int64 Unix Timestamp는 기존 초안의 정의이다. v0.0의 밀리초는 임시 채택이고 v0.3 Payload 예시에는 단위가 표기되지 않는다.
- 후속 작업과 선택 범위: 발생·수신 시각의 필드, 단위, GUI 시간대 및 예시 값을 일치시킨다.
- 영향 기능: 모든 메시지, GUI, History
- 결정 상태: 밀리초 임시 채택; 나머지 미정

2026-10-05 COM-01 준비 반영: 기존 내부 계약과 발행 코드를 대조하여 **이번 Heartbeat의 `ts`는 송신 시 생성한 UTC Unix 밀리초, signed Int64 JSON 정수**로 유지한다. 상세 적용 범위와 예제는 [Heartbeat 계약](공통데이터명세.md#heartbeat-contract)에서 관리한다. 근거는 코드 저장소 `CONTRACT.md`의 Topic과 Payload 절 및 `Amr.TestClient/Program.cs`의 `ToUnixTimeMilliseconds()`이다. 기존 임시 결정을 이번 문서에 연결한 것이며 GUI 표시 시간대·수신 시각 필드·시계 오차·생존 판정은 해당 기능 전에 정한다.

### D-04 메시지 필드와 전달 정책

- 현재 근거와 문제: v0.3에 Topic 예시와 JSON 예시가 있다. AMR ID 표기에 armId·id·amrId 등이 섞이며 필수 여부·자료형·범위·QoS가 완결되지 않았다.
- 후속 작업과 선택 범위: 유형별 스키마, 대상 ID 규칙, QoS·Retain, 미지원 Topic·유형·추가 필드 처리와 입력 제한을 정한다.
- 영향 기능: [COM-01](기능명세.md#com-01-실시간-메시지-송수신), [COM-04](기능명세.md#com-04-메시지-유효성-검증)~06, [AMR-04](기능명세.md#amr-04-명령-처리-결과와-ack-생성)~05
- 결정 상태: 이번 Heartbeat 실습은 기존 내부 계약을 임시 적용; 다른 유형과 운영 전달 정책은 미정

2026-10-05 COM-01 준비 반영: 기존 `CONTRACT.md`, `Amr.TestClient/Program.cs`, `MqttSubscriber.cs`에 이미 적용된 Topic·필드·QoS·Retain을 [Heartbeat 계약](공통데이터명세.md#heartbeat-contract)에 연결했다. 대안은 전체 유형의 운영 스키마를 먼저 확정하는 것이지만, 이번에는 기존 한 유형의 최소 송수신을 재현하기 위해 적용 범위를 제한한다. 코드의 동작 계약과 spec_revision은 변경하지 않았다.

- 근거 구분: 기존 내부 임시 설계·코드의 문서 연결. 원문이 Topic·JSON 필드·QoS를 확정했다고 해석하지 않음
- 결정 주체와 근거: 코드 저장소의 DN-01/02 및 기존 구현을 유지. Codex는 사용자의 ‘여섯 준비 항목에 맞춰 먼저 정리’ 요청 범위에서 해당 결정을 문서에 연결
- 적용 이유: 발행자와 수신 검증기가 이미 같은 Heartbeat 계약을 사용하므로 불필요한 계약 변경 없이 재현 가능
- 재검토 시점: Telemetry·Alarm·Command/ACK 추가, 실제 Core·장비 연동, QoS·스키마 변경 요구 발생 시

### D-05 State·Alarm·명령 전환

- 현재 근거와 문제: IDLE/BUSY/STOPPED/FAULT 및 MOVE/STOP/RESET은 기존 후보이다. STOPPED 재출발, Alarm 해제와 RESET, STOP 허용 상태가 불명확하다.
- 후속 작업과 선택 범위: 상태 전이표와 명령 허용표를 작성한다. Alarm 발생·해제 조건, 중복·재발생 처리, 운행 상태에 미치는 영향을 정한다.
- 영향 기능: [AMR-02](기능명세.md#amr-02-command-수신과-동작-수행)~04, [CORE-03](기능명세.md#core-03-수신-alarm-관리)~04, [GUI-04](기능명세.md#gui-04-amr-상세와-command-요청), [INT-02](기능명세.md#int-02-command-전체-흐름-검증)~03
- 결정 상태: 미정

### D-06 CommandId 생성 책임

- 현재 근거와 문제: v0.3 COM-05는 통신에서 생성하고 CORE-04 및 INT-02는 Core에서 생성한다.
- 후속 작업과 선택 범위: Core가 생성하고 통신은 보존·전달하는 안을 제안한다. 생성 형식과 유일성 범위를 결정한다.
- 영향 기능: [COM-05](기능명세.md#com-05-command와-ack-전달), [CORE-04](기능명세.md#core-04-command-요청과-결과-관리), [AMR-04](기능명세.md#amr-04-명령-처리-결과와-ack-생성), [INT-02](기능명세.md#int-02-command-전체-흐름-검증)
- 결정 상태: 제안; 미확정

### D-07 ACK 의미와 명령 예외

- 현재 근거와 문제: 발행 완료와 동작 완료는 구분해야 한다. SUCCESS의 의미, Timeout 값, 중복·늦은 ACK 및 BUSY 중 요청 정책은 정해지지 않았다.
- 후속 작업과 선택 범위: 접수·진행·최종 결과 단계, 명령별 응답 시점, Timeout, 잘못된 대상·미지 요청·중복·늦은 ACK와 재전송 시 중복 수행 정책을 정한다.
- 영향 기능: [COM-05](기능명세.md#com-05-command와-ack-전달)~06, [AMR-02](기능명세.md#amr-02-command-수신과-동작-수행)~04, [CORE-04](기능명세.md#core-04-command-요청과-결과-관리), [GUI-04](기능명세.md#gui-04-amr-상세와-command-요청), [INT-02](기능명세.md#int-02-command-전체-흐름-검증)
- 결정 상태: 미정

### D-08 재접속과 복구

- 현재 근거와 문제: 재접속은 원문 요구이다. 간격·횟수·Backoff·재구독·대기 중 명령 처리는 미정이다.
- 후속 작업과 선택 범위: 복구 시 구독 목록, 재시도 조건, 실패 표시, 대기 명령 폐기·보류·재전송 여부를 결정한다.
- 영향 기능: [COM-03](기능명세.md#com-03-broker-연결-상태-감시), [COM-06](기능명세.md#com-06-재접속과-구독-복구), [CORE-04](기능명세.md#core-04-command-요청과-결과-관리), [INT-04](기능명세.md#int-04-통신-이상과-복구-검증)
- 결정 상태: 미정

2026-10-05 확인: 현재 문서는 COM-06을 과제1 범위에 포함하지만 코드 추적기는 COM-01~05를 관리하고 DN-04는 자동 재접속을 후속 INT-04로 미룬다. 이 범위 차이는 COM-06 착수 전 또는 과제1 전체 완료 판정 전에 맞춘다. 이번 정상 Heartbeat 시험에서는 장애 복구를 다루지 않으며, 이 차이를 모든 코딩의 선행 차단 항목으로 삼지 않는다.

### D-09 Heartbeat 판정과 담당

- 현재 근거와 문제: v0.0은 Timeout 5초·확인 주기 0.5초를 임시 채택했다. v0.3은 Communication 또는 Core로 담당을 열어 두고 MqttAlive를 후보로 둔다.
- 후속 작업과 선택 범위: 감시 담당, Heartbeat 송신 주기, 연결 상태 값, 경계 판정, 복구 조건 및 추가 Ping/Pong 필요 여부를 정한다.
- 영향 기능: [COM-02](기능명세.md#com-02-개별-amr-heartbeat-감시)~03, [AMR-05](기능명세.md#amr-05-시뮬레이션-데이터-생성과-송신), [CORE-02](기능명세.md#core-02-최신-상태-관리), [GUI-01](기능명세.md#gui-01-대시보드), [INT-04](기능명세.md#int-04-통신-이상과-복구-검증)
- 결정 상태: 5초·0.5초 임시 채택; 나머지 미정

이번 최소 송수신에서는 기존 시험 발행자의 약 1초 간격을 유지한다. 이는 시험 입력의 발생 간격이며 위 Timeout·감시 주기와 다르다. 개별 AMR의 중단·복구 판정은 COM-02 구현 전에 결정한다.

### D-10 Log·History 저장과 조회

- 현재 근거와 문제: 원문은 상태 변경·알람·명령 결과·운행 이력의 SQLite 저장을 요구한다. v0.3 CORE-05는 알람 중심이며 필수 필드 누락 Log 여부도 검증 설명과 표가 다르다.
- 후속 작업과 선택 범위: 운행 이벤트와 좌표·경로 샘플의 범위, 테이블·키·중복 방지·조회 조건·보관 기간 및 저장 실패 처리를 정한다. 검증 실패 Log 정책도 일치시킨다.
- 영향 기능: [COM-04](기능명세.md#com-04-메시지-유효성-검증), [CORE-01](기능명세.md#core-01-장비-등록과-조회)~05, [GUI-03](기능명세.md#gui-03-alarm과-history-조회), [INT-02](기능명세.md#int-02-command-전체-흐름-검증)~03
- 결정 상태: 미정

이번 Heartbeat 실습의 검증 실패는 코드 저장소 DN-01과 기존 `IValidationLog` 방식으로 기록한다. Topic·오류 Code·Field·Reason을 출력하고 정상 수신자에게 전달하지 않으며 원문 Payload를 오류 로그에 넣지 않는다. 기존 실험 동작을 유지하는 범위이고 SQLite History·보관·조회 정책은 계속 미정이다.

### D-11 DataProvider와 화면 계약

- 현재 근거와 문제: Mock 화면과 DataProvider 인터페이스는 원문 결과물이다. 메서드·이벤트·조회·명령 반환형과 화면 갱신 방식은 미정이다.
- 후속 작업과 선택 범위: Mock·Core 공급자가 공유할 목록·상태·알람·이력 조회와 명령 요청 계약, 오류·빈 결과·Mock 표시를 정한다.
- 영향 기능: [GUI-01](기능명세.md#gui-01-대시보드)~05, [CORE-01](기능명세.md#core-01-장비-등록과-조회)~05
- 결정 상태: 미정

### D-12 시뮬레이터 설정과 재현

- 현재 근거와 문제: 수량·초기 좌표·속도·경로·장애 시나리오의 설정 변경은 원문 요구이다. 기존 2대 가정·거리 임계값은 예시이다.
- 후속 작업과 선택 범위: 설정 형식·유효성·기본값, 시뮬레이션·Telemetry 주기와 장애 발생·해제 조건, 시험 조건 저장 방법을 정한다.
- 영향 기능: [AMR-01](기능명세.md#amr-01-설정-로드와-amr-생성)~05, [INT-01](기능명세.md#int-01-정상-운행과-표시-검증)~04
- 결정 상태: 미정

## 2. 우선 검토 순서

1. D-04의 최소 메시지 계약과 D-03의 시간 단위를 검토하여 과제1·2의 송수신 시험 입력을 맞춘다.
2. D-06~D-07의 요청 ID 책임과 ACK 의미를 정리하여 통신·AMR·Core의 처리 경계를 맞춘다.
3. D-01·D-05·D-09의 장비 등록, 상태 전이 및 감시 정책을 검토한다.
4. GUI 구현 전 D-11의 DataProvider 계약을, History 구현 전 D-10의 저장 범위를 구체화한다.
5. D-12의 설정·장애 재현 조건을 개별 및 통합 시험에 연결한다.

## 3. 이번 COM-01 작업에 미치는 영향

목표는 기존 Heartbeat 한 유형의 정상 송수신·입력 거부·후속 정상 처리 확인이다. 준비 시점의 실제 계약·코드 대조 결과를 아래에 기록하며, 제품 시험 결과로 사용하지 않는다.

| 항목 | 이번에 필요한 범위 | 현재 처리 | 나머지를 정할 시점 |
| --- | --- | --- | --- |
| D-03 시간 | Heartbeat `ts` 자료형·생성 시점·단위 | 기존 Int64 Unix 밀리초 계약을 연결하여 준비 완료 | 감시·GUI·이력 구현 전 |
| D-04 메시지 | Heartbeat Topic·방향·필드·QoS·Retain·정상/오류 예제 | 기존 계약과 코드 일치 확인, 시험 예제 준비 완료 | 다른 메시지 유형·전달 보장 기능 구현 전 |
| D-01 등록 | 이번 수신자는 콘솔 출력 대역 | 장비 등록·DB 조회를 하지 않으므로 등록 정책 미정이 이번 시험을 막지 않음 | 실제 Core 등록·연동 전 |
| D-02·D-05 | 좌표·운행 상태·명령 전환 | Heartbeat의 `id`, `ts`에 포함하지 않음 | Telemetry·이동·상태·명령 구현 전 |
| D-06·D-07 | CommandId·ACK | 이번에 명령을 발행하지 않음 | COM-05·Core 명령 구현 전 |
| D-08 / COM-06 | 재접속·구독 복구 | 정상 연결 시험에 한정. 실패 시 기록하고 수동 재실행 | COM-06 착수 또는 과제1 전체 완료 판정 전 |
| D-09 | 시험 송신 간격과 생존 감시 구분 | 기존 약 1초 발행 유지. Timeout·중단 감시는 이번에 구현하지 않음 | COM-02 구현 전 |
| D-10 | 이번 입력 오류의 기록 | 기존 DN-01·검증 로그 경계 유지, 세부 규칙은 기본 코딩 규칙 참조 | 업무 History·DB 저장 구현 전 |
| D-11·D-12 | GUI 공급자·시뮬레이터 전체 설정 | 기존 단일 시험 클라이언트 사용 | 해당 GUI·시뮬레이터 기능 구현 전 |

이번 범위에서 추가 사용자 정책 결정이 있어야만 시작할 항목은 발견하지 않았다. 실제 송수신 결과는 아직 미검증이며 [작업 계획](과제1/과제계획.md#com01-test)의 시험으로 확인한다. 범위를 늘리거나 기존 계약과 다른 요구가 들어오면 이 판단도 재검토한다.

### 코드와 문서의 후속 정리

- `C:\practice\README.md` 끝 요약 및 `claude-progress.md` 상단 상태가 최신 추적기·S015와 다르다. 구현을 이어가는 세션에서 현재 Git 변경과 `feature_list.json`을 확인하고 요약을 맞춘다. 이번 문서 준비에서 코드 저장소의 기록을 덮어쓰지 않았다.
- 최신 기능 상태는 코드 추적기, 과제 전체의 계획 범위는 현재 과제계획에서 확인한다. 같은 기능 ID라도 계약·범위 차이는 위 D 항목에 근거를 남기고 조정한다.

- 2026-10-06 문서 상태 정리: [요구사항정의](요구사항정의.md)·[공통규칙](공통규칙.md)의 ‘과제 1~5 모두 미착수’와 [기능명세](기능명세.md)의 ‘각 기능 개발 미착수’가 [과제1 계획](과제1/과제계획.md)·[2026-10-05 검증결과](과제1/산출물/2026-10-05_개발환경_검증결과.md)의 부분 구현·환경 검증 기록과 달랐다. 사용자의 전체 보완 요청에 따라 해당 상태를 담당 일정·계획·검증결과로 참조하도록 정리했다. 변경 내역은 [일일업무](../일일업무/2026-10-06.md#document-links)에 연결한다. 위 코드 저장소의 후속 정리와 COM-06 범위 차이는 계속 남아 있다.
