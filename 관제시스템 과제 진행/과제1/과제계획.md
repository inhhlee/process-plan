## 2. 배경과 목적

Docker 기반 Mosquitto를 통해 가상 AMR과 관제 사이의 MQTT 통신 계층을 구성하고, 콘솔에서 송수신·연결 끊김·재접속 및 메시지 검증 결과를 확인한다.

## 3. 용어 설명

| 용어 | 쉬운 설명 |
| --- | --- |
| MQTT | 메시지를 발행하고 필요한 수신자가 구독하는 통신 방식이다. |
| Broker | 발행된 메시지를 구독자에게 전달하는 중계 서버다. 이 과제에서는 Mosquitto를 사용한다. |
| Topic / Payload | 메시지를 분류하는 주소와 실제 전달 내용이다. 구체적인 값은 공통데이터명세에서 정한다. |
| Heartbeat | AMR이 살아 있음을 주기적으로 알리는 메시지다. 감시 기준은 D-09에서 정한다. |
| Command / ACK | 동작 요청과 그 요청에 대한 응답이다. 응답이 뜻하는 단계는 D-07에서 정한다. |

**터미널 A — 관제 수신을 먼저 시작한다.**

```powershell
Set-Location C:\practice
.\init.cmd check
# Broker가 준비되지 않은 경우에만 실행
.\init.cmd broker
.\init.cmd start -Heartbeat
```

`Connected`, `Subscribed: amr/+/heartbeat, amr/+/telemetry, amr/+/alarm, amr/+/ack`를 확인한 뒤 터미널 A를 유지한다. `start`만 실행하면 연결 전용이므로 수신 시험에는 `-Heartbeat`가 필요하다. 이 모드는 DN-10 감시도 켜므로 발행을 멈추면 Timeout/Recovered 알림이 섞일 수 있다. HB-01~06은 Received·Rejected를 판정하며 이 알림만으로 COM-02 재검증을 완료하지 않는다. 연결 주소 `127.0.0.1:1883`와 실행별 evidence 경로도 기록한다.

**터미널 B — 기존 시험 클라이언트의 정상 발행을 확인한다.**

```powershell
Set-Location C:\practice
dotnet run --project .\src\Amr.TestClient -- AMR_001
```

발행자가 연결된 뒤 10초 이내에 최소 3건의 발행·수신이 대응하는지 ID·ts로 비교한다. 이는 로컬 기능 확인을 위한 관찰 조건이며 전송 보장이나 성능 기준이 아니다. 관찰 후 B의 발행자를 Ctrl+C로 정상 종료한다. A의 수신자는 계속 유지한다.

**터미널 B — 고정 예제와 오류 예제를 한 건씩 발행한다.**

```powershell
$exampleDir = 'C:\process-plan\관제시스템 과제 진행\과제1\산출물\COM-01_Heartbeat_예제'
Get-Content -Raw -LiteralPath (Join-Path $exampleDir 'heartbeat-valid.json') | docker exec -i amr-mosquitto mosquitto_pub -h 127.0.0.1 -p 1883 -V mqttv5 -q 0 -t amr/AMR_001/heartbeat -s
```

출력은 A에서 확인한다. 같은 명령의 파일명을 순서대로 `heartbeat-missing-ts.json`, `heartbeat-id-mismatch.json`, 마지막으로 다시 `heartbeat-valid.json`으로 바꾸어 실행한다. 각 입력 직후 기대 출력을 확인한 뒤 다음 입력을 보낸다. `-r`을 사용하지 않아 Retain=false를 유지한다. 명령의 비정상 종료나 수신 결과 누락은 기록하며, 발행 종료 코드만으로 성공 판정하지 않는다.

한 건 발행 시험은 명령 완료 후 최대 5초 관찰하여 해당 결과를 기록한다. 정상 발행자를 중지하고 한 건씩 시험해 출력의 대응을 확인한다. 여러 발행자가 섞여 판정할 수 없으면 통과로 기록하지 않고 원인을 남긴다.
