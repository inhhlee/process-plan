이 계획은 프로젝트의 과제1을 완료하기 위한 목표·작업 순서·산출물·확인 기준을 정리한다. 2026-10-05에 사용자가 알려준 기존 코드 C:\practice에서 부분 구현을 확인했다. 아래 작업 순서와 시험 항목은 전체 과제의 초기 계획이며, 기존 구현·내부 계약과 대조하여 이어서 수행할 범위를 정한다.

2배경과 목적

Docker 기반 Mosquitto를 통해 가상 AMR과 관제 사이의 MQTT 통신 계층을 구성하고, 콘솔에서 송수신·연결 끊김·재접속 및 메시지 검증 결과를 확인한다.

3용어 설명

용어 쉬운 설명
MQTT 메시지를 발행하고 필요한 수신자가 구독하는 통신 방식이다.
Broker 발행된 메시지를 구독자에게 전달하는 중계 서버다. 이 과제에서는 Mosquitto를 사용한다.
Topic / Payload 메시지를 분류하는 주소와 실제 전달 내용이다. 구체적인 값은 공통데이터명세에서 정한다.
Heartbeat AMR이 살아 있음을 주기적으로 알리는 메시지다. 감시 기준은 D-09에서 정한다.
Command / ACK 동작 요청과 그 요청에 대한 응답이다. 응답이 뜻하는 단계는 D-07에서 정한다.

포함하는 기능

기능 ID 기능명 제공할 동작

  • 접속 관리·송수신·Heartbeat·재접속·명령/응답·메시지 검증을 개별 시험으로 확인한다.
  • 결정한 메시지·감시·복구 정책과 적용 버전을 기록한다.
  • 비정상 입력 후 처리 지속 및 장애 복구 결과의 근거를 남긴다.
  • 실제 결과·판정·미해결 문제를 검증 결과에 기록한다.

위 체크는 실제 결과를 확인한 뒤 표시한다. 계획 초안 작성 완료와 과제 개발 완료를 구분한다.

전체 시험 계획

다음 표는 전체 과제의 예상 확인 결과이다. 기존 저장소의 일부 검증 기록과 이번 기본 환경 점검은 점검 결과에서 구분하여 확인한다. 아래 시험 표 전체를 현재 실행·통과한 것으로 처리하지 않는다.

기능 시험 조건 예상 확인 결과
COM-01 AMR ID가 다른 정상 메시지와 대상별 Command 정의된 Topic·방향·대상으로 수신·전달된다.
COM-04 JSON 오류·필드 누락·자료형·허용값 오류·ID 불일치 후 정상 메시지 비정상 입력은 상위 전달 없이 실패 기록되고 이후 정상 입력은 처리된다.
COM-02 Broker는 유지하고 한 AMR의 Heartbeat만 중단·재개 다른 AMR과 구분하여 감지하고 결정한 복구 조건을 적용한다.
COM-03 Broker 연결 끊김 Broker 연결 상태가 변경되고 AMR 운행 상태와 별도로 기록된다.
COM-05 다중 명령과 순서를 바꾼 ACK 요청 ID·대상이 보존되고 발행 성공과 동작 결과가 구분된다.
COM-06 Broker 중단·복구 및 대기 중 명령 재접속·재구독·송수신 재개와 대기 명령의 정책 적용을 확인한다.

실행 후에는 사용 설정·계약 버전, 입력, 절차, 예상 결과, 실제 결과, 판정 및 Log·화면·DB 등 근거를 검증 결과에 작성한다. 미정 정책에 의존하는 시험은 해당 결정 항목과 적용 값을 함께 기록한다.

이번 작업 시험

다음 표는 이번 Heartbeat 작업에서 실행할 계획이며 현재 재시험은 미실행이다. 상세 실행 순서는 다음 하위 절을 따른다.

시험 ID 입력·조건 성공 기준 실패 판단
HB-01 기존 TestClient 주기 발행 연결 후 관찰 10초 이내 최소 3건의 Published와 Received에 같은 ID·ts 발행·수신 불일치 또는 정상 수신 없음
HB-02 정상 고정 예제 1건 Received Heartbeat: AMR_001 ts=1791195767000 확인 ts 변경·거부·수신 없음
HB-03 ts 누락 예제 1건 Rejected, MissingField, $.ts. 해당 입력의 정상 전달 없음 정상 전달·예외로 수신 중단·거부 기록 없음
HB-04 ID 불일치 예제 1건 Rejected, IdMismatch, $.id. 해당 입력의 정상 전달 없음 잘못된 ID 전달·수신 중단·거부 기록 없음
HB-05 같은 수신 프로세스에 정상 예제 재발행 재시작 없이 정상 Received 확인 오류 이후 정상 처리가 되지 않음
HB-06 시험 후 A를 Ctrl+C로 종료 연결 정리·정상 종료 확인 미처리 예외·종료 실패

이번 작업의 증거와 완료 범위

실행 ID를 정해 수신·발행 출력, 실제 명령, 코드 버전·변경 상태, 입력 파일과 판정의 연결을 기록한다. 코드 저장소에는 evidence/COM-01/<실행ID>/로 로그를 보관하거나 기존 helper의 실행 로그 경로를 연결하고, 문서 저장소에는 검증결과 빈 양식을 복사해 실행별 결과를 남긴다. 보관 전 인증정보가 포함되지 않았는지 확인한다.

  • HB-01~06을 실제 수행하고 입력·예상·실제·판정·증거를 기록한다.
  • 코드를 수정했다면 관련 회귀와 init.cmd verify를 통과한다.
  • 실패·미실행 항목과 후속 작업을 남기고, 이번 Heartbeat 범위를 넘는 기능을 완료로 처리하지 않는다.

이번 작업의 준비가 끝났다는 것은 위 시험을 수행할 파일·입력·절차·판정 기준을 설명할 수 있다는 뜻이다. 위 체크는 실제 시험 후에만 표시한다.

상세 실행 절차

아래는 다음 실제 작업에서 실행할 계획이다. 이번 문서 준비에서 새로 수행한 시험 결과가 아니다. 정상 메시지의 기준은 계약 문서와 JSON 예제 파일을 사용한다.

선행 조건은 SDK·Docker·기존 amr-mosquitto 준비, 다른 AMR_001 발행 실험과 혼동되지 않는 실행 시간대, 두 개의 PowerShell 터미널이다. 다른 프로세스를 임의로 종료하지 않는다. MQTT Explorer는 필요하지 않으며 컨테이너에 있는 mosquitto_pub을 사용한다. 도움말의 -s, -V, -q, -t 옵션은 이번 준비 중 확인했다.

터미널 A — 관제 수신을 먼저 시작한다.

Set-Location C:\practice
.\init.cmd check
# Broker가 준비되지 않은 경우에만 실행
.\init.cmd broker
.\init.cmd start

Connected, Subscribed: amr/+/heartbeat를 확인한 뒤 터미널 A를 유지한다. 이번 시험은 기존 코드의 연결 주소가 127.0.0.1:1883인지 출력에서 확인한다. 다르면 설정 원인을 먼저 확인한다. init.cmd가 출력한 실행별 evidence 경로를 결과에 기록한다.

터미널 B — 기존 시험 클라이언트의 정상 발행을 확인한다.

Set-Location C:\practice
dotnet run --project .\src\Amr.TestClient -- AMR_001

발행자가 연결된 뒤 10초 이내에 최소 3건의 발행·수신이 대응하는지 ID·ts로 비교한다. 이는 로컬 기능 확인을 위한 관찰 조건이며 전송 보장이나 성능 기준이 아니다. 관찰 후 B의 발행자를 Ctrl+C로 정상 종료한다. A의 수신자는 계속 유지한다.

터미널 B — 고정 예제와 오류 예제를 한 건씩 발행한다.

$exampleDir = 'C:\양식 통일 규칙\관제시스템 과제 진행\과제1\산출물\COM-01_Heartbeat_예제'
Get-Content -Raw -LiteralPath (Join-Path $exampleDir 'heartbeat-valid.json') | docker exec -i amr-mosquitto mosquitto_pub -h 127.0.0.1 -p 1883 -V mqttv5 -q 0 -t amr/AMR_001/heartbeat -s

출력은 A에서 확인한다. 같은 명령의 파일명을 순서대로 heartbeat-missing-ts.json, heartbeat-id-mismatch.json, 마지막으로 다시 heartbeat-valid.json으로 바꾸어 실행한다. 각 입력 직후 기대 출력을 확인한 뒤 다음 입력을 보낸다. -r을 사용하지 않아 Retain=false를 유지한다. 명령의 비정상 종료나 수신 결과 누락은 기록하며, 발행 종료 코드만으로 성공 판정하지 않는다.

한 건 발행 시험은 명령 완료 후 최대 5초 관찰하여 해당 결과를 기록한다. 정상 발행자를 중지하고 한 건씩 시험해 출력의 대응을 확인한다. 여러 발행자가 섞여 판정할 수 없으면 통과로 기록하지 않고 원인을 남긴다.
