### 1인 개발 학습·확인 순서

관련 개념을 질문하고 사용자 답변을 확인한 뒤 다음 단계로 진행한다. 이해가 부족한 부분은 설명한 뒤 다시 확인한다. 학습 답변은 구현·시험 완료 근거로 사용하지 않는다. Broker 연결 상태는 COM-03, 개별 AMR의 Heartbeat 중단은 COM-02에서 감시한다. Broker 연결이 정상이고 다른 AMR의 메시지가 계속 들어오는데 특정 AMR의 Heartbeat만 멈춘 경우를 Broker 단절로 기록하지 않는다.

외부 선행은 #5의 실패·대기 제한·취소 처리 반영과 #4의 정상 접속·종료 근거다. C1 → C2 → C3a → C3b → C4는 **같은 #6 브랜치·PR 안에서 앞 단계의 구현·결과를 확인하는 순서**이며 단계마다 병합을 요구하지 않는다. 확정 기한은 없고 실제 수행 결과를 보고 다음 단계로 넘어간다. 무응답 도구의 구현이 전달·차단·정리 범위를 넘어가거나 작업이 커지면 남은 범위를 별도 Issue로 분리하고 중복·선행 조건을 확인한다.

<a id="com03-c1"></a>

### COM03-C1 — KeepAlive 연결 유지

먼저 익힐 내용은 MQTT KeepAlive, PINGREQ/PINGRESP와 Broker 진단 로그다. MQTTnet의 KeepAlive로 업무 메시지가 없어도 연결이 유지되는지 확인하며 별도 Ping 기능·AMR Heartbeat를 만들지 않는다.

- [ ] 선행 코드의 실제 KeepAlive 주기와 업무 메시지가 없는 실행 조건을 확인하고 README에 관찰 절차·설정·결과를 기록한다.
- [ ] 적용 주기의 2배 이상 실제 연결을 관찰한다. 개발 제안값 5초를 사용했다면 최소 10초이며, 이 관찰 시간을 모든 단절의 고정 감지 제한으로 사용하지 않는다.
- [ ] 같은 실행의 콘솔·Broker Client ID와 PING 교환 또는 대응 프로토콜 진단 근거를 연결한다. 필요하면 격리 시험용 Broker의 설정·로그를 준비하고 처음부터 패킷 분석 도구·자체 Ping 구현을 추가하지 않는다.
- [ ] 설정·관찰 시작/끝·Client ID·로그·판정을 남기고 #4의 Ctrl+C 정상 절차로 종료한다. Connected 한 줄만으로 유지 통과를 판정하지 않는다.
- [ ] 진단 근거를 얻지 못하면 실제 확인 범위·미검증 이유·다음 확인을 남긴다. 연결 유지 결과를 AMR 생존 상태로 확대하지 않는다.

Broker 종료·무응답 감지는 다음 단계에서 확인한다. 자동 재접속·업무 메시지·개별 AMR Heartbeat는 이 단계에 포함하지 않는다.

<a id="com03-c2"></a>

### COM03-C2 — 격리 Broker 종료·끊김 감지

선행은 같은 작업 안에서 C1의 유지 결과를 확인하는 것이다. 먼저 익힐 내용은 MQTT 단절 통지·상태 변화와 격리 시험용 Broker다.

- [ ] 기존 연결 코드·콘솔에 단절 상태·원인·시각 전달을 보완하고 예상치 못한 단절은 정리 후 비정상 종료하도록 한다.
- [ ] 생성 예정 `tools/COM-03/`에 기존 Docker 설정을 참고한 별도 프로젝트명·루프백 임시 포트·분리된 데이터/로그의 시험 Broker 설정을 준비한다. 기존 사용자 Broker·A1의 Broker와 관리 자원을 구분하고 설치된 Docker·Mosquitto 이미지를 재사용한다.
- [ ] 실제 라이브러리·설정을 근거로 관찰 상한을 먼저 정한다. 연결된 격리 Broker만 정상 종료하고 정한 범위 안에 연결 상실·원인·시각이 표시되며 자원 정리·비정상 종료하는지 확인한다.
- [ ] 단절 시험 대역 통지와 명시적 Ctrl+C 종료를 비교한다. 정상 종료와 예상치 못한 단절을 구분하고 같은 단절을 반복 상태 변화로 출력하지 않도록 한다.
- [ ] 격리 Broker 재기동 뒤 새 콘솔 프로세스·새 Client ID의 명시적 접속을 확인하고 기본 단절 자동 시험·관련 회귀 결과를 기록한다. Broker 재기동·새 실행 접속을 자동 복구 통과로 표시하지 않는다.

응답만 전달되지 않는 조건은 C3a~C3b, 중복 알림·종료 경합의 상세 시험은 C4에서 확인한다. 기존 서비스를 중단하거나 자동 재접속을 구현하지 않는다.

<a id="com03-c3a"></a>

### COM03-C3a — 무응답 시험 환경 준비

선행은 같은 작업 안에서 C2의 실제 단절 결과·격리 범위를 확인하는 것이다. 먼저 익힐 내용은 TCP 전달, 시험용 프록시와 접속 후 응답 차단이다. 환경 준비와 제품 감지 시간 판정을 나눠 확인한다.

- [ ] 사용 가능한 시험 도구를 먼저 확인하고 재사용 방법·출처를 기록한다. 도구가 없다면 생성 예정 `tools/COM-03/`에 최소 양방향 TCP 전달·응답 차단·종료 기능을 준비한다.
- [ ] 별도 루프백 프록시 포트에서 C2의 격리 Broker로 전달하도록 구성하고 정상 전달 포트·대상 Broker·생성 자원·실행 방법을 기록한다. 새 범용 네트워크 프레임워크·MQTT 처리기를 만들지 않는다.
- [ ] 기존 콘솔을 프록시 경유로 연결해 정상 전달 상태에서 실제 Broker 접속 승인을 먼저 확인하고 같은 세션 ID를 기록한다.
- [ ] 승인 뒤 Broker→Client 응답만 차단한다. TCP 연결을 즉시 닫지 않고 차단한 응답·차단 시작·연결 유지 상태를 도구 기록으로 확인한다. 기존 Broker에 영향이 없어야 한다.
- [ ] README에 시작·정상 전달·응답 차단·정리·재시작 절차를 남긴다. 생성한 도구·자원만 정리하며 새 도구 설치·PC 방화벽·보안 변경으로 조건을 만들지 않는다.

도구 준비만으로 무응답 감지 통과를 표시하지 않는다. 제품 감지 시간·허용 범위 판정은 C3b에서 확인하고, 도구가 최소 범위를 넘어가면 추가 작업으로 분리한다.

<a id="com03-c3b"></a>

### COM03-C3b — 무응답 감지 시간 측정

선행은 같은 작업 안에서 C3a의 실제 접속·응답 차단 조건을 확인하는 것이다. 먼저 익힐 내용은 장애 시작·감지 시각과 경과 시간, 감지 기준·허용 오차다.

- [ ] C3a 도구·기존 콘솔·격리 Broker로 실제 무응답 시험을 준비한다. 시험 전에 MQTTnet 버전·KeepAlive·서버 조건·라이브러리 진단을 근거로 예상 기준·관찰 상한·허용 오차를 기록한다.
- [ ] 정상 접속 승인·적용 설정을 기록한 뒤 응답 전달을 중단한다. 접속 완료 → 응답 차단 → 감지의 순서·시각과 같은 실행의 경과 시간을 연결한다.
- [ ] 사전 기준과 실제 감지 시간을 비교하고 감지 뒤 상태·이유 표시·자원 정리·비정상 종료를 확인한다. 필요한 경우 기존 연결 감시 코드만 보완하고 README·새 증거에 연결한다.
- [ ] 기존 Broker 종료 사례와 비교해 TCP 종료·연결 후 무응답·최초 접속 실패를 구분한다. 단위 대역으로 실제 시험을 대체하거나 KeepAlive 2배·최초 접속 제한 3초를 보편적인 단절 감지 제한으로 사용하지 않는다.
- [ ] 실패·미검증·감지 한계·재개 조건을 기록하고 시험 후 도구·격리 자원을 정리한다. 자동 재접속·운영 SLA·장비 안전성 판정은 추가하지 않는다.

시험 도구 준비는 C3a, 종료 경합과 최종 근거 정리는 C4에서 관리한다.

<a id="com03-c4"></a>

### COM03-C4 — 중복 단절·종료 경합·근거 정리

선행은 같은 작업 안에서 C3b의 시간 측정·판정 결과를 확인하는 것이다. 먼저 익힐 내용은 시험 대역의 알림 순서 제어, 중복 정리와 회귀 범위다.

- [ ] 기존 연결 코드·시험 프로젝트에서 필요한 중복 통지·종료 처리만 보완한다. 무작위 대기 대신 같은 세션 중복 단절, Ctrl+C→단절, 단절→Ctrl+C, 종료 후 늦은 단절 알림의 순서를 제어해 재현한다.
- [ ] 중복 단절은 한 번의 상태 변화로 처리되고 정리·종료를 중복 실패시키지 않아야 한다. 두 종료 순서에서 실제로 결정한 종료 원인·상태·코드가 일치하고 미처리 예외·정리 실패·무한 대기가 없는지 확인한다.
- [ ] 종료 뒤 늦은 연결·단절 알림이 종료 결과를 되돌리거나 Connected를 만들지 않는지 확인한다. B3의 늦은 접속 완료 시험은 변경 영향이 없으면 유효한 기존 근거를 활용한다.
- [ ] 변경 영향이 있는 앞선 시험만 회귀하고 README·증거 목록에 A1~C3b의 정상·실패·대기 제한·취소·KeepAlive·Broker 종료·무응답 결과와 최종 코드 버전에 대한 유효성을 연결한다.
- [ ] 실제 명령·환경·코드/라이브러리 버전·입력·적용 설정·Client ID·Broker/프록시 조건·장애 시작/감지 시각·측정 시간·예상·실제·판정·종료 코드·로그를 생성 예정 `evidence/COM-03/<새 실행ID>/`에 남긴다. 비밀정보·기존 C:\practice의 통과 결과는 복사하지 않는다.
- [ ] 기존 #4·#5·#6의 원래 완료조건별로 유효한 근거·미충족·미검증 범위를 정리한다. 모두 충족한 범위만 완료로 판단하고 과제1 전체·다른 COM 기능·기존 C:\practice의 상태를 자동 변경하지 않는다.

새 제품 기능·부하 시험·모든 동시 실행 순서의 전수 시험·운영 정책 확정은 이 단계에 포함하지 않는다. 영향 없는 과거 시험을 문서 정리 때문에 반복하지 않는다. #6의 전체 완료조건·미검증 범위를 확인한 뒤 [전체 작업 순서](README.md#solo-issues)의 COM02-A로 진행하며 선행 송수신·검사·큐 결과가 없으면 그 작업부터 완료한다.

## 목적

업무 메시지가 없어도 MQTT 연결이 유지되는지와 접속 후 Broker 종료·무응답을 감지하는지 확인한다. COM03-A~C의 정상·실패·취소·끊김 결과를 새 실습 코드의 실행 근거로 연결한다.

## 작업 범위와 대상

| 대상 | 현재 상태·작업 내용 |
| --- | --- |
| `src/Amr.Communication/Mqtt/` | 선행 A~B에서 생성·보완할 연결 코드에 접속 후 상태 변화·끊김 이유 전달과 중복 통지·종료 경합 처리 |
| `src/Amr.Communication.Console/Program.cs` | 선행 콘솔에서 연결 상실·종료 이유·결과를 관찰할 수 있도록 보완 |
| `tests/Amr.Communication.Tests/` | 기존 시험 프로젝트에 비정상 단절·중복 알림·늦은 알림·종료 경합 시험과 영향받은 회귀 추가 |
| `docker/`의 기존 설정과 생성 예정 최소 `tools/` | 프로젝트 전용 정의를 참고해 격리 Broker·시험용 프록시·필요한 진단 로그 준비. 대형 기존 검증 도구를 통째로 복사하지 않음 |
| `README.md`, `evidence/COM-03/<새 실행ID>/` | 실제 재현 절차·감지 기준·측정·검증결과와 A~C 근거 연결. 증거 경로는 생성 예정 |

라이브러리·콘솔·시험 프로젝트와 Docker 정의는 존재한다. 연결 코드·기능 시험은 이번 초안 조회 시 아직 없으며 착수 때 A~B의 실제 파일·설정과 대조한다.

- 업무 메시지 없이 적용된 KeepAlive 주기의 2배 이상 연결을 관찰한다. 제안값 5초를 적용했다면 최소 10초이며, PINGREQ/PINGRESP 또는 대응되는 라이브러리 진단·Broker 로그로 프로토콜 수준의 유지 근거를 확보한다. 단순 프로세스 실행·Connected 한 줄만으로 판단하지 않는다.
- 실제 격리 Broker 정상 종료와 접속 완료 후 서버 응답 전달 중단을 각각 시험한다. 연결 상실 상태·이유·시각을 출력하고, 한 단절당 한 번 상태 변화로 기록한다. 명시적 종료를 예상치 못한 단절로 중복 기록하지 않는다.
- 감지 시간은 실제 MQTTnet 버전·적용 KeepAlive·서버 응답·라이브러리 동작을 확인해 시험 전에 예상 기준과 관찰 상한·허용 오차를 기록하고 측정값과 비교한다. KeepAlive 2배는 유지 관찰 조건이며 모든 단절의 고정 감지 제한이 아니다. 최초 접속 제한 3초와도 구분한다.
- 콘솔의 실습 제안 동작은 예상치 못한 연결 상실을 기록하고 자원을 정리해 비정상 종료하는 것이다. 명시적 Ctrl+C 종료는 정상 종료로 구분한다. 둘이 근접하면 실제로 결정된 종료 원인·코드가 일치하고 종료가 가능해야 하며, 늦은 알림이 종료 상태를 다시 Connected로 바꾸지 않아야 한다.
- Broker 재기동 자체를 자동 복구로 표시하지 않는다. 새 프로세스의 명시적 접속 성공과 고유 Client ID로 복구 확인을 구분한다. 자동 재접속·재구독은 구현하지 않는다.

끊김 시험은 별도 이름·루프백 임시 포트를 사용하는 격리 시험용 Broker에서 수행한다. 준비한 Compose 설정·설치된 Docker·Mosquitto 이미지를 재사용하고, 실제 사용한 프로젝트명·포트·설정·생성 자원을 기록한다. 기존 사용자 Broker 및 다른 실행이 사용하는 Broker를 중단·초기화하지 않는다. 프록시는 접속 승인 후 응답 전달을 중단하고 TCP 연결을 즉시 닫지 않는 조건을 만들며, PC 방화벽·보안 설정은 바꾸지 않는다. 시험을 위해 생성한 자원은 확인한 범위에서 정리한다.

## 제외 범위

자동 재접속·재구독·대기 명령 처리(COM-06), 개별 AMR Heartbeat Timeout(COM-02), MQTT 업무 메시지 송수신, 실제 운행 State·Alarm 변경, GUI·Core·DB 및 운영 SLA·실제 장비 안전성 검증.

실제 Broker 종료·무메시지 연결 유지·접속 후 응답 중단 결과를 단위 대역 시험으로 대체하지 않는다. 시간 측정은 접속 완료·장애 시작·감지 시각을 연결하고 같은 실행의 경과 시간을 남긴다. 필요한 진단을 얻지 못하면 실제 확인 범위·미검증 이유를 기록한다.

## 산출물과 검증 기록

- 연결 감시 보완 코드·시험·재현 절차와 선택한 최소 격리 시험 도구.
- `evidence/COM-03/<새 실행ID>/`에 코드 버전·환경·적용 설정·Client ID·Broker/프록시 조건·장애 시작·감지 시각·측정 시간·예상·실제·판정·콘솔/Broker 로그를 남긴다.
- 기존 A~B의 근거가 최종 코드에도 유효한 이유와 필요한 회귀 결과를 기록한다. 영향받지 않은 시험을 문서 정리 목적으로 반복하지 않는다. 기능 자동 시험 개수와 실패·미실행 항목을 실제 결과대로 집계한다.
- 모든 완료조건을 실제 근거로 충족할 때 이번 COM-03 실습 범위를 완료로 판단한다. 미충족·미검증 항목이 있으면 부분 결과와 남은 작업을 기록한다. 기존 C:\practice 추적기·다른 COM 기능·과제1 전체 완료를 자동으로 변경하지 않는다.
