### 적용할 Heartbeat 계약

- Topic은 대소문자를 구분하는 `amr/{amrId}/heartbeat`의 정확한 3개 구간이다. ID는 비어 있거나 공백·제어 문자·`/`·`+`·`#`를 포함할 수 없다. Unicode ID는 허용하고 정규화하지 않는다.
- Payload는 strict UTF-8 JSON object다. 필드명은 대소문자를 구분하고 `id`, `ts`, `status`만 허용하며 모두 필수다. 추가·중복 필드, 주석, 후행 쉼표를 거부한다.
- `id`: 비어 있거나 공백만인 문자열·null 불허. Topic ID와 정확히 일치해야 한다.
- `ts`: signed Int64 JSON 정수. 문자열·소수·지수 표기는 거부한다. 송신 시 생성한 UTC Unix 밀리초라는 개발 계약을 사용하며, Int64 전체 범위의 값을 그대로 보존한다. 자릿수로 단위를 추측하거나 현재 시각으로 덮어쓰지 않는다.
- `status`: 필수 문자열 `"OK"`. 업무 State나 Online/Offline 판정으로 사용하지 않는다.
- 최대 Payload 크기 65,536 bytes, 최대 JSON 깊이 16을 적용한다. 개발용 제한이며 운영 확정값이 아니다.
- 검사는 MQTT에서 받은 전체 Payload를 대상으로 한다. 크기 제한을 먼저 확인하며, 기존 256바이트 `PayloadPreview`나 대체문자로 디코딩한 진단 문자열을 검사 입력으로 사용하지 않는다.
- 수신 UTC 시각은 MQTT 콜백에서 확보하고 정상 검사 후 모델과 함께 전달한다. 검사기의 입력 오류와 수신자 자체의 처리 오류를 혼동하지 않는다.
- 실패는 Code·Field·Reason으로 기록하고 정상 수신자를 호출하지 않는다. 오류 로그에 원문 Payload·비밀정보를 포함하지 않는다.
- 실제 MQTT 시험은 기존 개발 환경 `127.0.0.1:1884`, 발행·구독 QoS 0, 발행 Retain=false, 실행별 Client ID를 사용한다.

## 진행 순서

1. 정상 입력과 필수 필드가 빠진 입력을 비교하며 JSON 해석과 계약 검사의 차이를 확인한다.
2. Heartbeat 검사기·성공/실패 결과·모델을 작은 단위로 설계하고 MQTT 없이 자동시험한다.
3. 기존 구독부에 전체 Payload 검사와 정상 모델 전달을 연결한다. 처음부터 범용 프레임워크를 만들지 않는다.
4. 실제 Broker에서 오류 입력 다음 정상 입력을 보내고, 이후 정상 전달과 Ctrl+C 종료를 확인한다.
5. 변경·시험·남은 범위를 기록하고 이 Issue의 PR을 검토·병합한 뒤 COM04-B로 진행한다.
