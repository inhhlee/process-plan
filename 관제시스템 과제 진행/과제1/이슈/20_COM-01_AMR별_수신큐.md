## 목적

AMR별 도착 순서를 유지하며 느린 처리·큐 초과·종료를 제어한다.

## 근거와 선행 조건

- 근거: 기능명세 v0.7 COM-01, 요구사항정의 v0.5 R-04, 공통규칙 v0.4, 공통데이터명세 v0.4 과제1 개발 계약, 검토 및 결정사항 v0.5. 작업 분할·실습 순서는 신입 1인 개발을 위한 제안이다.
- 선행 작업: [COM01-B](19_COM-01_다중AMR_유형별전달.md)의 해당 결과 반영. 추천 진행 순서는 Issue 목록을 따른다.
- 먼저 익힐 내용: 큐는 처리를 기다리는 메시지 목록이다. 한 AMR 처리가 느려도 다른 AMR 수신을 막지 않게 한다.

## 작업 범위와 대상

- 개발 위치: `C:\amr-control-system-demo`. 대상: Mqtt/의 수신 큐와 처리 로그 경계(생성 예정), 기존 시험 프로젝트.
- 라이브러리·콘솔·시험 프로젝트는 준비돼 있다. 제품 소스는 현재 없으므로 위 모듈은 새로 만들거나 선행 작업에서 생성한 파일을 보완할 예정이며, 착수 시 실제 구조·기존 변경을 대조한다.
- DN-09 수신 큐 계약을 따라 AMR별 비동기 큐와 단일 소비자를 구성한다. 장비마다 전용 스레드를 만들지 않는다.
- 개발 제한(대기 256개/AMR·세션 64 AMR), 가득 찰 때 새 입력 거부, 처리 오류 뒤 계속 처리, 연결 종료 시 취소·잔여 폐기를 적용한다. 시험에서는 작은 제한을 주입한다.
- 처리 중 취소를 무시하는 대역도 종료 대기 제한으로 보고하고 늦은 완료를 관찰한다. 입력 오류·QueueFull·AmrLimitReached·HandlerFailed·종료 폐기를 구분한다.

## 진행 순서

1. 선행 결과와 이번 기준을 읽고 정상 입력 하나·예상 출력부터 확인한다.
2. 위 작업 범위를 순서대로 구현하거나 정리한다. 처음부터 범용 프레임워크를 만들지 않는다.
3. 아래 사례로 결과를 확인하고 실행 방법·남은 범위를 기록한다. 한 작업이 너무 크면 실제 진행 결과에 따라 나머지 범위를 분리한다.

## 완료조건

- [ ] 같은 AMR의 네 유형은 도착 순서를 지키고 다른 AMR은 독립적으로 처리된다.
- [ ] 큐/AMR 한계 초과에서 MQTT 수신부가 무한 대기하지 않고 이유가 남는다.
- [ ] 처리자 예외 뒤 다음 입력을 처리하며 취소 후 새 전달은 시작하지 않는다.
- [ ] 종료 대기 한계를 넘으면 오류를 알리고 자원 정리 결과를 남긴다.
- [ ] 실제 변경·확인 결과·미검증 범위를 README와 Issue·PR에 연결한다.
