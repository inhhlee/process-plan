### 순서와 독립성

1. 기존 Validator를 통과한 불변 메시지만 큐에 넣는다. 큐의 키는 `ReceivedMessage.AmrId`다. id 없는 ACK도 Topic으로 대상을 구분하며 모델의 `Id=null`, SUCCESS/FAILURE·reason과 수신 시각을 변경하지 않는다.
2. 같은 연결 세션의 같은 AMR은 네 유형이 **하나의 큐**를 공유하고 **소비자 하나**가 처리 완료를 기다린 뒤 다음 메시지를 처리한다. 순서는 수신부가 메시지를 접수한 순서다. Payload ts로 정렬하거나 모든 AMR의 전역 순서를 보장하지 않는다.
3. 다른 AMR의 소비자는 별도 비동기 작업으로 진행한다. AMR마다 전용 스레드를 만들지 않는다. 시험 처리자는 취소 토큰과 서로 다른 AMR의 동시 호출을 지원한다.
4. MQTT 수신 콜백에서는 검증·짧은 큐 접수만 한다. 기존 `Action<ReceivedMessage>`에 `async` 람다를 연결하지 않는다. 실제 비동기 처리는 완료·예외를 관찰할 수 있는 Task 반환 처리자에서 수행한다.
5. 처리자 안에서 자기 연결의 종료를 기다리지 않는다. 종료가 필요하면 연결 소유자에게 요청한다. 콜백·처리 로그는 빠르게 반환하며, 로그 구현의 예외 경계를 문서화한다.

### 과부하와 오류 구분

- 기본 제한은 **AMR당 대기 256개 + 처리 중 최대 1개**, **연결 세션당 AMR 64개**다. 시험에는 작은 제한을 주입할 수 있게 한다.
- 큐는 세션 종료까지 유지한다. 잠시 비었다고 AMR 등록을 지우거나 제한을 초기화하지 않는다. 새 연결 세션에는 새 큐를 사용한다.
- 큐가 가득 차면 **새 입력을 즉시 거부**한다. MQTT 수신부에서 빈자리를 기다리거나 이미 대기 중인 메시지를 밀어내지 않는다.
- 입력 검사 실패는 기존 `Code·Field·Reason`으로 기록한다. 유효한 입력의 `QueueFull`·`AmrLimitReached`, 비동기 처리자의 `HandlerFailed`, 종료로 인한 잔여 폐기는 별도 처리 결과로 구분한다. 이를 JSON 검사 실패인 `Rejected`로 바꾸지 않는다.
- 처리자 예외는 단계·예외 형식 등 추적 가능한 정보로 기록하고 다음 입력을 처리한다. 원문 Payload·입력이 포함될 수 있는 예외 Message는 오류 로그에 남기지 않는다. 자동 재전달하지 않는다.
- 기존 Diagnostic·Received·Rejected 콜백 실패와 새 비동기 처리자 실패를 구분한다. 큐 접수 성공은 실제 업무 처리 성공을 의미하지 않는다.

### 종료와 연결 끊김

- 종료·연결 끊김 시 새 입력 접수를 막고 실행 중 처리자에 취소를 요청한다. 대기 중 메시지는 폐기하고 AMR별 개수·사유를 기록한다.
- 취소 후 다음 처리자 호출을 시작하지 않는다. 취소와 전달 시작이 겹치는 경계를 시험으로 확인한다. 이미 시작한 호출은 취소에 협조해야 하며 강제 중단한다고 표현하지 않는다.
- 정상 종료는 소비자의 종료를 기다리되 DN-09에 따라 기존 연결 제한 시간을 적용한다. 현재 `MqttConnectionSettings.ConnectTimeout` 기본값은 3초다. 구현 때 큐 대기와 구독·연결 해제의 제한 시간 적용 범위를 명시하고 시험에서는 짧은 값을 사용한다.
- 취소를 무시하는 처리자는 대기 한계에서 종료 오류를 알리고, 나중에 완료되거나 실패하는 결과를 관찰한다. 아직 실행 중인 작업과 정리 완료한 자원을 구분해 기록하고, 사용 중인 자원을 너무 일찍 폐기하지 않는다.
- 기존 구독 해제·이벤트 제거·연결 해제·Client 정리가 실패 경로에서도 이어지게 한다. 자동 재접속·자동 재구독은 추가하지 않는다.

## 진행 순서

1. 선행 코드와 DN-09를 대조하고 **큐 접수 → 한 AMR의 순차 처리 → 다른 AMR의 독립 처리**를 정상 입력으로 설계한다.
2. 순서·독립성부터 구현하고 MQTT 없는 자동시험으로 확인한다.
3. 작은 큐·AMR 제한으로 과부하와 처리자 예외를 확인한다.
4. 정상 종료·연결 끊김·취소 협조/무시 대역으로 종료 경계를 확인한다.
5. 실제 MQTT로 두 AMR·네 유형 연결과 종료·새 세션을 확인하고 README·Issue·develop 대상 PR에 실행 근거를 연결한다.

처음부터 범용 프레임워크를 만들지 않는다. 한 단계가 예상보다 커지면 실제 진행 결과와 남은 완료조건을 제시해 범위 분리를 검토한다. 이번 게시 단계에서는 구현을 시작하지 않는다.

## 완료조건

- [ ] 같은 AMR의 네 유형이 접수 순서대로 처리되고 다른 AMR은 독립적으로 진행된다. 대상·모델·최초 수신 시각과 id 없는 ACK의 값이 보존된다.
- [ ] 큐/AMR 한계 초과 시 MQTT 수신부가 빈자리를 기다리지 않고 새 입력을 거부한다. QueueFull·AmrLimitReached를 입력 오류와 구분해 기록한다.
- [ ] 처리자 예외를 HandlerFailed로 기록한 뒤 다음 입력을 처리한다. 취소 후 새 전달은 시작하지 않으며 잔여 폐기 수량을 기록한다.
- [ ] 종료 대기 한계를 넘으면 오류와 정리 결과를 알리고 늦은 완료·실패를 관찰한다. 정상 종료·연결 끊김·새 세션에서 이전 큐가 재사용되지 않는다.
- [ ] 기존 검사·수신부 회귀와 실제 MQTT 연결 결과를 확인하고, 실제 변경·확인 결과·미검증 범위를 README와 Issue·PR에 연결한다.

| 불량 입력 → 정상 입력, 처리자 예외 → 다음 정상 입력 | 검사 오류와 HandlerFailed 분리, 오류 뒤 정상 처리, 원문·예외 Message 미기록 |
| 대기·처리 중 정상 종료/연결 끊김, 취소에 협조하는 처리자 | 새 접수 차단·취소 요청·잔여 폐기 수량 일치·새 전달 없음·자원 정리 |
| 취소를 무시하는 처리자가 늦게 성공하거나 예외 발생 | 대기 한계 내 종료 오류 보고, 늦은 결과 관찰·안전한 최종 정리, 다음 메시지 미전달 |
| 접수/전달 시작과 종료가 겹치는 대역 시험 | 종료 경계 뒤 새 접수·처리 시작 없음, 이미 시작한 호출과 폐기 수량 구분 |
| 실제 MQTT 두 AMR·네 유형, 느린 비동기 대역, Ctrl+C·새 세션 | 큐가 실제 수신 경로에 연결됨, 순서·독립성·정상 정리, 이전 세션 메시지 재전달 없음 |
| 기존 자동시험 전체 | 네 유형 검사·콜백 오류·구독 정리의 기존 계약 유지; API 변경 시 시험 변경 이유 명시 |

## 제외 범위

- 전체 메시지 무손실·exactly-once 보장, 자동 재전송, 영속 큐·SQLite 저장.
- 실제 Core 상태 변화·알람 업무·Command/ACK 업무 성공 판단.
- Heartbeat Timeout·Offline 판단(COM-02), Command 발행(COM-05), 자동 재접속·재구독(COM-06).
- 운영 큐 크기·과부하·QoS 정책 확정, AMR별 전용 스레드.

## 산출물과 완료 범위

- 변경 코드·필요한 시험·실행 안내와 `evidence/COM-01/<새 실행ID>/` 기록. 코드/계약 버전·환경·입력·예상·실제·판정·로그를 연결한다.
- MQTT 없는 자동시험만으로 실제 Broker 연동 완료를 표시하지 않는다. 취소 무시·경합 등 대역으로 확인한 범위, 실제 MQTT로 확인한 범위와 미검증 항목을 구분한다.
- 기존 실행 증거는 보존하고 재실행은 새 실행 ID로 남긴다. 기존 실습 저장소의 소스·과거 통과 기록을 이번 완료 근거로 복사하지 않는다.
- COM01-C 완료와 COM-01 전체 완료를 구분한다. COM-01 전체에는 Command 송신 결과도 필요하다.
