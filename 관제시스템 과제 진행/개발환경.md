## 3. 사용할 개발환경

이 절과 4절의 명령은 기존 `C:\practice` 환경에서 확인한 내용이다. 새 대상의 환경은 미확인으로 두고, 코드 공간에서 해당 저장소의 지침과 프로젝트 파일을 확인한 뒤 적용할 값을 갱신한다.

버전은 최신 권장값을 새로 고른 것이 아니라 현재 저장소와 PC에서 확인한 값이다.

| 항목 | 확인한 구성 | 판정과 확인 범위 |

### 3.1 로그·MQTT 시험 도구와 Dot 활용

2026-10-20 사용자가 Seq(Serilog 구조화 로그 조회)와 MQTT Explorer(MQTT 시험)를 사용하기로 지정했다. 이는 새 코드 저장소 C:/amr-control-system-demo에 적용할 도구 선택이며, 설치·기동·로그 연동 완료를 의미하지 않는다. 위 표의 2026-10-05 기존 환경 점검 기록은 당시 이력으로 보존한다.

| 도구 | 사용할 역할 | 현재 확인과 후속 확인 |
| --- | --- | --- |
| Serilog | 애플리케이션의 구조화 이벤트 작성 및 Seq 전송 연동 | 현재 src/tests 프로젝트의 직접 PackageReference에는 없음. 적용 Issue에서 로그 경계·속성·전송 실패·종료 시 정리를 설계하고 시험 |
| Seq | 구조화 로그 검색·필터·시나리오 타임라인 확인 | 기존 설치 기록은 보존. 새 프로젝트의 서비스 접근·로그 유입은 이번 작업에서 미검증. 새 실행의 이벤트가 속성으로 검색되는지 확인 |
| MQTT Explorer | 시험 Broker의 Topic/Payload 관찰, 정상·불량 시험 메시지 수동 발행 | 사용 도구로 선택. 현재 설치·접속은 미점검. 기존 계약의 입력과 관제 수신·거부 결과를 함께 확인 |
| Dot | 접근 가능한 로그·시험 기록·Issue/PR을 대조해 결과 요약, 원인 가설·다음 확인 항목 및 리뷰 질문 작성 | 연결·자동화 미구성. 사용 가능한 Seq 조회 경로 또는 제공된 로그 파일과 코드·문서 접근을 먼저 확인 |

기본 구분은 애플리케이션 로그 작성(Serilog), 로그 수집·검색(Seq), MQTT 메시지 관찰·수동 입력(MQTT Explorer), 근거 대조·설명(Dot)이다. Explorer에 메시지가 보이는 사실만으로 관제 애플리케이션의 검증·처리·저장 성공을 판정하지 않는다. Seq의 진단 Log와 SQLite의 업무 History는 [C-10](명세/공통규칙.md#c-10-기록) 및 [D-10](명세/검토%20및%20결정사항.md#d-10-loghistory-저장과-조회)의 구분을 유지한다.

후속 설치·연동 작업에서 기존 서비스·포트·데이터 위치를 확인한 뒤 재사용 또는 프로젝트 구성을 선택한다. 현재 도구 선택만으로 서비스를 시작·중단하거나 전체 로그 코드를 바꾸지 않는다. 실행 ID·세션·AMR·요청 식별자 등 추적 속성은 실제 이벤트에 필요한 범위로 정하며, 메시지 계약에 새 필드를 임의로 추가하지 않는다.

#### Dot에 맡길 작업 예시

아래는 사용자가 Dot에 전달할 예시이며 자동화 생성이나 실행 지시가 아니다. 정기 실행은 대상·시각·시간대·알림 조건을 지정하는 후속 요청에서 설정한다. 로컬 자료가 필요한 경우 연결된 PC가 온라인이고 해당 폴더에 접근할 수 있어야 한다. GUI 자동 제어 가능 여부를 가정하지 않는다. Seq는 사용 가능한 조회 API/도구 또는 제공된 로그 파일을 활용하며, 수집 전용 API 키가 조회 권한도 제공한다고 가정하지 않는다.

- 시험 후 분석: 지정한 실행 ID와 시간 구간의 Seq 로그 또는 제공된 로그 파일을 MQTT Explorer 관찰 기록·관제 콘솔 로그와 대조한다. 정상·거부·실패·취소를 구분하고 사실·원인 가설·추가 시험을 분리해 요약한다. 접근할 수 없는 자료와 누락 구간을 표시한다.
- PR 준비: 실제 diff와 시험 근거를 대조하여 중요한 설계 선택·대안·예상 질문 2~3개·미검증 범위를 정리한다. 제품 시험을 실행하지 않았다면 재검증 통과로 표시하지 않는다.
- 업무 초안: Git/Issue/PR과 실제 실행 증거에서 완료·진행·막힘을 정리한다. 기존 날짜별 일일업무를 활용하고, 새 원인이나 처리 완료를 추정하지 않는다.

복사용 예시:

> 내 AMR 과제의 이번 시험을 검토해줘. 먼저 접근 가능한 코드·명세와 내가 지정한 실행 ID/시간 구간의 Seq 로그 또는 제공한 로그 파일, MQTT Explorer 관찰 기록을 확인해줘. 입력 → 수신 → 검증 → 큐 처리 → 종료 흐름을 증거가 있는 단계까지만 대조하고, 정상·거부·실패·취소를 구분해줘. 확인 사실, 원인 가설, 추가 확인 방법과 설계 리뷰 질문 2~3개를 정리해줘. 이번 요청은 분석까지이며 코드 수정·메시지 발행·서비스 재시작·외부 전송은 포함하지 않아.

## 4. 실행 순서

Visual Studio에서 위 솔루션을 연다. 일반 준비·검증은 코드 저장소의 표준 진입점을 사용한다.

```powershell
Set-Location C:\practice
.\init.cmd check
.\init.cmd verify
```

실제 MQTT 작업 시 Docker Desktop과 개발 Broker를 확인한다. Broker가 준비되지 않았다면 다음 표준 명령을 사용한다.

```powershell
.\init.cmd broker
.\init.cmd start -DurationSeconds 5
```

위 `start`는 **연결만 확인**한다. 메시지 수신은 아래처럼 옵션을 추가한다.

```powershell
.\init.cmd start -Heartbeat
```

`Connected`와 네 Topic의 `Subscribed` 출력을 확인한다. 이 수신 모드는 기존 Heartbeat 감시도 함께 켜고 명령을 자동 발행하지 않는다. 발행·수신·오류 입력 절차와 판정은 [과제1 계획](과제1/과제계획.md#com01-test)을 따른다. `verify-broker`는 Broker 장애 등 별도 시험용이며, 문서 정리만으로 반복 실행하지 않는다. 근거는 2026-10-06에 읽은 코드 저장소 [진행 로그](<C:/practice/claude-progress.md>)와 [init.ps1](<C:/practice/init.ps1>)이다.

### 3. 역할과 오류 처리

1. Heartbeat 발행자는 기존 `Amr.TestClient/Program.cs`다. `MqttPublisher`는 이미 Command 발행을 담당하므로 빈 골격으로 취급하거나 Heartbeat를 옮기는 구조 변경을 추가하지 않는다.
2. `MqttSubscriber`는 `AmrMessageDispatcher`를 통해 입력 검사·Heartbeat 관측·AMR별 큐 전달을 수행한다. `IncomingMessageProcessor`의 검증과 정상 전달 경계를 유지하고 별도 JSON 처리로 우회하지 않는다.
3. `IncomingMessageProcessor`는 정상 메시지만 `IIncomingMessageSink`에 전달한다. 이번 수신자는 콘솔 출력 대역이다. 실제 Core·GUI·DB 업무 상태를 변경하지 않는다.
4. 잘못된 입력은 검증 실패 결과로 기록하고 정상 수신자에게 전달하지 않는다. 다음 정상 메시지는 계속 처리해야 한다.
5. 연결 실패·구독 거부·예상하지 못한 예외는 입력 검증 실패와 구분한다. 오류를 빈 `catch`로 숨기거나 성공 종료로 바꾸지 않는다. 이번 시험에서는 실패를 기록하고 수동 재실행한다.
6. `CancellationToken`, `using`·`await using`과 이벤트 해제 방식을 유지한다. Ctrl+C 종료를 일반 장애와 구분한다. I/O 대기를 `.Wait()`·`.Result`로 바꾸지 않는다.

### 4. 로그와 시간

| 상황 | 기록 기준 |
| --- | --- |
| 발행 | 기존 시험 클라이언트의 `Published`와 시험용 Topic·Payload 확인. 발행 출력만으로 수신 성공을 판정하지 않음 |
| 정상 수신 | 기존 `Received Heartbeat: AMR_001 ts=...` 출력에서 ID와 보낸 `ts` 보존 확인 |
| 검증 실패 | 기존 `IValidationLog`의 Topic·Code·Field·Reason 사용. 수신한 원문 Payload와 인증정보를 오류 로그에 추가하지 않음 |
| 연결과 구독 실패 | 기존 연결 상태·종료 코드·오류 출력을 보관. 업무 History로 기록하지 않음 |
| 시간 | 계약의 `ts`는 `long`/Int64 Unix 밀리초. 수신 시각으로 덮어쓰거나 AMR 생존 Timeout 판정에 그대로 사용하지 않음 |

검증 실패 로그 기준은 기존 [CONTRACT.md](<C:/practice/src/Amr.Communication/Validation/CONTRACT.md>)를 이번 실습에 유지한다. SQLite History·Seq 구성은 후속 기능에서 다룬다.
