## 1. 공통 데이터와 메시지 계약 후보

### 1.1 공통 데이터의 의미

아래 항목은 기존 기능명세의 후보를 정리한 것이다. 데이터의 의미와 최종 JSON 필드명·필수 여부·자료형·허용값은 구분하여 D-02~D-05에서 결정한다.

| 항목 | 의미와 구성 후보 | 결정 상태 |
| --- | --- | --- |
| AMR ID | 시스템 내 장비 식별자; Topic의 대상과 Payload의 ID를 연결 | 형식·필수 필드 미정, [D-01](검토%20및%20결정사항.md#d-01-미등록-amr-처리)·[D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책) |
| Position | 2D X/Y 위치 | 기존 설계 제안; 단위·범위·축·Map 변환 미정, [D-02](검토%20및%20결정사항.md#d-02-좌표속도화면-대응) |
| Speed | 위치와 분리한 이동 속도 | 기존 설계 제안; 단위·범위 미정, [D-02](검토%20및%20결정사항.md#d-02-좌표속도화면-대응) |
| State | IDLE·BUSY·STOPPED·FAULT 후보 | 기존 설계 제안; 전이와 명령 허용 조건 미정, [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환) |
| Alarm | 장비·Code·Level·발생/해제 상태·내용·발생 시각 | 기존 설계 제안; 식별·중복·해제 기준 미정, [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환) |
| Command | 대상 장비·CommandId·유형·매개변수·발생 시각; MOVE·STOP·RESET 후보 | 기존 설계 제안; 생성 책임·허용 조건 미정, [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환)~[D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외) |
| ACK | 대상 요청을 식별하는 CommandId와 처리 결과·시각 | 기존 설계 제안; 접수·동작 완료 의미와 예외 미정, [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외) |
| Heartbeat | 장비의 생존 확인 메시지와 발생 시각 | 감시 기능은 원문 요구; 상세 형식·주기 미정, [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)·[D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당) |
| Timestamp | 발생 시각은 Int64 Unix Timestamp 후보, 수신 시각은 별도 관리 | 밀리초는 기존 임시 채택; 필드·표시 기준 미정, [D-03](검토%20및%20결정사항.md#d-03-시간-계약) |

IDLE은 정상 대기, BUSY는 동작 수행 중, STOPPED는 정지 동작 후 상태, FAULT는 정상 운행이 어려운 장애 상태라는 기존 의미를 후보로 사용한다. Alarm Level의 INFO·WARN·ERR·FATAL도 기존 후보이다. 이 값만으로 확정된 명령 허용표나 장애 해제 정책이 있다고 판단하지 않는다.

### 1.2 MQTT Topic과 Payload 의미 후보

Topic은 기존 v0.3의 예시이며 JSON은 기존 설계 제안이다. 원문은 MQTT 통신을 요구하지만 아래 Topic 문자열과 필드명을 직접 확정하지 않는다. Payload 항목은 의미를 기술한 것이며 최종 스키마는 D-04에서 정한다.

| 유형 | Topic 후보 | 방향 | Payload 의미 후보 |
| --- | --- | --- | --- |
| Telemetry | `amr/{amrId}/telemetry` | AMR → 관제 | 장비 식별, 발생 시각, 위치, 속도, 운행 상태 |
| Alarm | `amr/{amrId}/alarm` | AMR → 관제 | 장비 식별, Code, Level, 발생/해제 상태, 내용, 시각 |
| Heartbeat | `amr/{amrId}/heartbeat` | AMR → 관제 | 장비 식별, 시각, 생존 정보 |
| Command | `amr/{amrId}/command` | 관제 → AMR | 요청 식별, 유형, 시각, 매개변수 |
| ACK | `amr/{amrId}/ack` | AMR → 관제 | 요청 식별, 결과, 시각; 대상은 Topic·요청과 연결 |

스키마에는 필수·선택 필드, 자료형, 단위, 허용값, 대상 일치 조건 및 오류 처리 기준을 함께 작성한다. 전체 시스템의 QoS·Retain·중복 정책은 미정이다. 이번 Heartbeat 실습의 적용값은 2절로 한정한다.

### 1.3 임시값과 예시의 구분

| 항목 | 기존 초안의 값 | 현재 처리 |
| --- | --- | --- |
| Timestamp 단위 | 밀리초 | 임시 채택 유지; 계약과 예시 정합성 검토 필요 |
| Heartbeat Timeout | 5초 | 임시 채택 유지; [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)에서 최종 기준 결정 |
| 감시 확인 주기 | 0.5초 | 임시 채택 유지; Heartbeat 송신 주기와는 구분 |
| 시뮬레이터 AMR 수량 | v0.3의 2대 가정 | 시험 예시이며 고정 수량 요구가 아님 |
| Alarm 거리·횟수 조건 | v0.3의 장애 예시 | 예시이며 확정 임계값으로 사용하지 않음 |

### 송수신과 필드

| 항목 | 이번에 적용할 내용 |
| --- | --- |
| 방향 | 가상 AMR 시험 클라이언트 → Mosquitto → 관제 수신 콘솔의 검사기·출력 대역 |
| 발행 Topic | `amr/AMR_001/heartbeat` — 일반형 `amr/{amrId}/heartbeat` |
| 구독 Topic | `amr/+/heartbeat` — `+`는 구독 필터에만 사용 |
| 연결 | 로컬 `127.0.0.1:1883`, MQTT 5, 개발용 연결 |
| 발행·구독 QoS | 0 — 이 실습에서 수신 로그로 도착 확인. 재전송·중복 보장 정책으로 확대하지 않음 |
| 발행 Retain | false — 과거 Heartbeat를 새 생존 메시지로 재사용하지 않음 |
| 시험 발행 주기 | 기존 클라이언트의 발행 완료 후 약 1초 대기. 정밀 주기 보장이나 AMR Timeout 기준이 아님 |
| JSON | UTF-8 object, 필드명 대소문자 구분. `id`, `ts`만 허용 |
| `id` | 필수 string. 비어 있지 않고 Topic ID와 정확히 일치. Topic ID에 공백·제어문자·`/`·`+`·`#` 불허 |
| `ts` | 필수 signed Int64 JSON 정수. 송신자가 메시지를 생성한 시각의 UTC Unix 밀리초. 문자열·소수·지수 표기 불허 |
| 시간 검증 경계 | 기존 검증기는 Int64 범위·형식만 검사. 과거·미래 여부로 생존을 판정하지 않음. 수신 시각·Timeout 판단은 COM-02에서 결정 |
| 추가 제약 | 추가·중복 필드 불허, 최대 65,536 bytes·JSON 깊이 16. 기존 내부 계약의 개발용 제한 유지 |
| 정상 처리 | 검증한 ID·ts를 `IIncomingMessageSink`로 전달하고 기존 콘솔에 `Received Heartbeat` 출력 |
| 오류 처리 | `Rejected`와 실패 Code·Field·Reason 기록, 정상 수신자 전달 없음. 이후 정상 메시지 계속 처리 |

### 함께 사용할 입력 예제

아래 입력은 모두 Topic `amr/AMR_001/heartbeat`로 보낸다. 고정 `ts`는 계약·전달 확인용 예시이며 현재 시각이나 최신 생존 증거를 뜻하지 않는다. 주기 발행 클라이언트는 매번 현재 UTC Unix 밀리초를 생성한다.

| 예제 | 파일 | 기대 결과 |
| --- | --- | --- |
| 정상 | [heartbeat-valid.json](과제1/산출물/COM-01_Heartbeat_예제/heartbeat-valid.json) | `Received Heartbeat: AMR_001 ts=1791195767000` |
| 필수 시각 누락 | [heartbeat-missing-ts.json](과제1/산출물/COM-01_Heartbeat_예제/heartbeat-missing-ts.json) | `Rejected`, `MissingField`, `$.ts`. 정상 수신 출력 없음 |
| ID 불일치 | [heartbeat-id-mismatch.json](과제1/산출물/COM-01_Heartbeat_예제/heartbeat-id-mismatch.json) | `Rejected`, `IdMismatch`, `$.id`. 정상 수신 출력 없음 |

```json
{"id":"AMR_001","ts":1791195767000}
```

위 판정은 기존 코드에서 확인한 **예상 결과**다. 이번 문서 준비에서 실제 발행·수신을 새로 실행한 결과가 아니다. 시험 순서와 기록은 [과제1 계획](과제1/과제계획.md#com01-test)에 따른다.
