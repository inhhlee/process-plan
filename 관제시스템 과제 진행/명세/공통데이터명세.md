## 1. 공통 데이터와 메시지 계약 후보

### 1.1 공통 데이터의 의미

아래 항목은 기존 기능명세의 후보를 정리한 것이다. 전체 시스템의 최종 의미·운영 정책과 현재 개발용 JSON 계약은 구분한다. 기존 채택 범위는 [과제1 개발 계약](#task1-contracts), 남은 결정은 D-02~D-05에서 확인한다.

| 항목 | 의미와 구성 후보 | 결정 상태 |
| --- | --- | --- |
| AMR ID | 시스템 내 장비 식별자; Topic의 대상과 Payload의 ID를 연결 | 과제1 개발 형식은 [3절](#task1-contracts), 실제 등록 정책은 [D-01](검토%20및%20결정사항.md#d-01-미등록-amr-처리)·[D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책) |
| Position | 2D X/Y 위치 | 과제1 개발 단위는 3절, 과제2 첫 실행본은 [4절](#task2-motion-data). 운영 범위·축·Map 변환은 [D-02](검토%20및%20결정사항.md#d-02-좌표속도화면-대응)에서 미정 |
| Speed | 위치와 분리한 이동 속도 | 과제1 개발 계약은 3절, 과제2의 설정 속도·현재 속도 구분은 [4절](#task2-motion-data). 운영 범위는 [D-02](검토%20및%20결정사항.md#d-02-좌표속도화면-대응)에서 미정 |
| State | IDLE·BUSY·STOPPED·FAULT 후보 | 기존 허용 문자열은 3절, 첫 실행본의 최소 전이는 [4절](#task2-state-data). 명령·장애 전이는 [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환)에서 미정 |
| Alarm | 장비·Code·Level·발생/해제 상태·내용·발생 시각 | 기존 설계 제안; 식별·중복·해제 기준 미정, [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환) |
| Command | 대상 장비·CommandId·유형·매개변수·발생 시각; MOVE·STOP·RESET | Core의 ID 생성·발행 전 기록은 [6절](#provider-command-contract) 채택. 전체 명령 허용 조건은 [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환) 후속 |
| ACK | 대상 요청을 식별하는 CommandId와 최종 처리 결과·시각 | [7절](#ack-processing-contract)의 최종 결과·추적 기준 채택. Timeout 수치·별도 미선택 상세는 [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외) 후속 |
| Heartbeat | 장비의 생존 확인 메시지와 발생 시각 | 감시 기능은 원문 요구; 개발 계약은 [2절](#heartbeat-contract), 운영 주기·상태는 [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)·[D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당) |
| Timestamp | 발생 시각은 Int64 Unix Timestamp 후보, 수신 시각은 별도 관리 | 밀리초는 기존 임시 채택; 필드·표시 기준 미정, [D-03](검토%20및%20결정사항.md#d-03-시간-계약) |

IDLE은 정상 대기, BUSY는 동작 수행 중, STOPPED는 정지 동작 후 상태, FAULT는 정상 운행이 어려운 장애 상태라는 기존 의미를 후보로 사용한다. Alarm Level의 INFO·WARN·ERR·FATAL도 기존 후보이다. 이 값만으로 확정된 명령 허용표나 장애 해제 정책이 있다고 판단하지 않는다.

### 1.2 MQTT Topic과 Payload 의미 후보

Topic은 기존 v0.3의 예시이며 JSON은 기존 설계 제안이다. 원문은 MQTT 통신을 요구하지만 아래 Topic 문자열과 필드명을 직접 확정하지 않는다. Payload 항목은 의미를 기술한 것이며 최종 스키마는 D-04에서 정한다.

| 유형 | Topic 후보 | 방향 | Payload 의미 후보 |
| --- | --- | --- | --- |
| Telemetry | `amr/{amrId}/telemetry` | AMR → 관제 | 장비 식별, 발생 시각, 위치, 속도, 운행 상태 |
| Alarm | `amr/{amrId}/alarm` | AMR → 관제 | 장비 식별, Code, Level, 발생/해제 상태, 내용, 시각 |
| Heartbeat | `amr/{amrId}/heartbeat` | AMR → 관제 | 장비 식별, 시각, 생존 정보 |
| Command | `amr/{amrId}/command` | 관제 → AMR | 요청 식별, 유형, 시각, 매개변수 |
| ACK | `amr/{amrId}/ack` | AMR → 관제 | 요청 식별, 결과, 시각; 대상은 Topic·요청과 연결 |

스키마에는 필수·선택 필드, 자료형, 단위, 허용값, 대상 일치 조건 및 오류 처리 기준을 함께 작성한다. 개발용 송수신에는 QoS 0·Retain=false를 적용하고, 전체 시스템의 전달 보장·중복·복구 정책은 미정으로 유지한다. Heartbeat 예제는 2절, 다른 유형의 현재 계약은 3절을 따른다.

### 1.3 임시값과 예시의 구분

| 항목 | 기존 초안의 값 | 현재 처리 |
| --- | --- | --- |
| Timestamp 단위 | 밀리초 | 임시 채택 유지; 계약과 예시 정합성 검토 필요 |
| Heartbeat Timeout | 5초 | 임시 채택 유지; [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)에서 최종 기준 결정 |
| 감시 확인 주기 | 0.5초 | 임시 채택 유지; Heartbeat 송신 주기와는 구분 |
| 시뮬레이터 AMR 수량 | v0.3의 2대 가정 | 시험 예시이며 고정 수량 요구가 아님 |
| Alarm 거리·횟수 조건 | v0.3의 장애 예시 | 예시이며 확정 임계값으로 사용하지 않음 |

### 송수신과 필드

| 항목 | 이번에 적용할 내용 |
| --- | --- |
| 방향 | 가상 AMR 시험 클라이언트 → Mosquitto → 관제 수신 콘솔의 검사기·출력 대역 |
| 발행 Topic | `amr/AMR_001/heartbeat` — 일반형 `amr/{amrId}/heartbeat` |
| 구독 Topic | 이번 입력은 `amr/+/heartbeat`. 현재 콘솔 수신 모드는 Telemetry·Alarm·ACK도 함께 구독. `+`는 구독 필터에만 사용 |
| 연결 | 로컬 `127.0.0.1:1883`, MQTT 5, 개발용 연결 |
| 발행·구독 QoS | 0 — 이 실습에서 수신 로그로 도착 확인. 재전송·중복 보장 정책으로 확대하지 않음 |
| 발행 Retain | false — 과거 Heartbeat를 새 생존 메시지로 재사용하지 않음 |
| 시험 발행 주기 | 기존 클라이언트의 발행 완료 후 약 1초 대기. 정밀 주기 보장이나 AMR Timeout 기준이 아님 |
| JSON | UTF-8 object, 필드명 대소문자 구분. `id`, `ts`, `status`만 허용하며 모두 필수 |
| `id` | 필수 string. 비어 있지 않고 Topic ID와 정확히 일치. Topic ID에 공백·제어문자·`/`·`+`·`#` 불허 |
| `ts` | 필수 signed Int64 JSON 정수. 송신자가 메시지를 생성한 시각의 UTC Unix 밀리초. 문자열·소수·지수 표기 불허 |
| `status` | 필수 string, 허용값 `"OK"`. 개발용 생존 신호이며 운행 State·최종 Online/Offline 판정과 다름 |
| 시간 검증 경계 | 검사기는 Int64 범위·형식만 검사. COM-02는 검증된 Heartbeat의 관제 수신 시각을 사용하며 Payload `ts`의 과거·미래 여부로 생존을 판정하지 않음. [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당) 참조 |
| 추가 제약 | 추가·중복 필드 불허, 최대 65,536 bytes·JSON 깊이 16. 기존 내부 계약의 개발용 제한 유지 |
| 정상 처리 | 검증한 ID·ts를 `IIncomingMessageSink`로 전달하고 기존 콘솔에 `Received Heartbeat` 출력 |
| 오류 처리 | `Rejected`와 실패 Code·Field·Reason 기록, 정상 수신자 전달 없음. 이후 정상 메시지 계속 처리 |

### 함께 사용할 입력 예제

아래 입력은 모두 Topic `amr/AMR_001/heartbeat`로 보낸다. 고정 `ts`는 계약·전달 확인용 예시이며 현재 시각이나 최신 생존 증거를 뜻하지 않는다. 주기 발행 클라이언트는 매번 현재 UTC Unix 밀리초를 생성한다.

| 예제 | 파일 | 기대 결과 |
| --- | --- | --- |
| 정상 | [heartbeat-valid.json](../과제1/산출물/COM-01_Heartbeat_예제/heartbeat-valid.json) | `Received Heartbeat: AMR_001 ts=1791195767000` |
| 필수 시각 누락 | [heartbeat-missing-ts.json](../과제1/산출물/COM-01_Heartbeat_예제/heartbeat-missing-ts.json) | `Rejected`, `MissingField`, `$.ts`. 정상 수신 출력 없음 |

## 3. 과제1에서 재사용할 개발 계약

2026-10-06에 기존 코드 저장소 HEAD `47ee27b`의 계약과 `feature_list.json`의 채택 기록을 대조했다. 근거 구분은 **기존 개발용 임시 결정의 연결**이다. 원문 재판독·신규 정책 채택·제품 실행 결과가 아니다. 이 문서 저장소의 데이터 요약은 아래를 사용하며 세부 제약의 변경은 연결된 코드 계약과 함께 검토한다.

| 대상 | 현재 적용할 계약과 의미 | 상세 기준·결정 |
| --- | --- | --- |
| Telemetry | 필수 `id`, `ts`, `pos{x,y}`, `sp`, `state`. X/Y는 유한 숫자, 속도는 0 이상. 개발 단위 m·m/s. State는 `IDLE/BUSY/STOPPED/FAULT`; 실제 운행 전이 정책은 별도 | [수신 계약 v3](<C:/practice/src/Amr.Communication/Validation/CONTRACT.md>), DN-02 |
| Alarm | 필수 `id`, `ts`, `code`, `level`, `alarmState`; 선택 `message`. Level `INFO/WARN/ERR/FATAL`, AlarmState `ACTIVE/CLEARED`. 발생·해제 업무 정책은 별도 | 같은 수신 계약, DN-02 |
| Heartbeat | 필수 `id`, `ts`, `status`; 위 2절의 정상·오류 예제 적용 | 같은 수신 계약, DN-02 |

### 4.2 위치·속도·계산 비교 기준

- 위치는 2D X/Y, 거리 단위는 m, 속도 단위는 m/s다. 경과 시간은 이동 계산에서 초로 해석한다.
- 경과 시간은 0 이상의 유한한 숫자여야 한다. 0초이면 위치·State·현재 속도를 유지한다. 음수·유한하지 않은 값은 계산 전에 거부하며 오류 처리 중에도 위치·State·현재 속도를 변경하지 않는다. 오류 반환과 이유 출력은 [AMR-02](기능명세.md#amr-02-command-수신과-동작-수행)를 따른다.
- 이동 속도 설정값은 실행 중 보존한다. 현재 속도는 초기 생성·최종 도착 시 0, 경로 이동 중에는 설정한 이동 속도다. 후속 Telemetry의 `sp`에는 현재 속도의 의미를 적용한다.
- 도착은 [AMR-02](기능명세.md#amr-02-command-수신과-동작-수행)의 목표 좌표에 맞추는 처리로 판정한다. 일정 반경에 들어온 사실만으로 도착시키지 않는다.
- 자동시험에서 예상 좌표와 계산 좌표를 비교하는 허용 오차는 0.000001m다. 각 축의 절대 오차가 이 값 이하여야 한다. 이는 계산 비교 기준이며 도착 반경이나 실제 로봇의 위치 정확도를 뜻하지 않는다.

### 4.3 첫 실행본의 운행 상태

| 시점 | State | 현재 속도 |
| --- | --- | --- |
| 설정 로드·초기 생성 | IDLE | 0 |
| 경로 이동 시작·진행 중 | BUSY | 설정한 이동 속도 |

모든 경유점이 초기 위치와 같으면 이동 없이 IDLE·현재 속도 0으로 완료한다. 최종 도착 후 추가 갱신에도 좌표·상태·현재 속도를 유지한다. 이번 자동 경로 이동은 기존 IDLE·BUSY 문자열을 사용하며 STOPPED·FAULT의 명령·장애·복구 전이는 후속 D-05에서 정한다. 실제 전이 처리와 초기·이동·도착 로그는 [AMR-02](기능명세.md#amr-02-command-수신과-동작-수행)를 따른다.

## 5. 단일 AMR 격자 최단 경로 비교 데이터

근거는 [사용자 추가 요구](요구사항정의.md#grid-pathfinding-scope)와 [D-02·D-12의 범위 한정 결정](검토%20및%20결정사항.md#grid-pathfinding-decision)이다. 아래는 실습 계약이며 운영 지도·실제 장비의 안전 주행 기준이 아니다. 추가 기능은 미구현·미검증이다.

### 5.1 지도와 좌표의 의미

| 항목 | 의미·검사 |
| --- | --- |
| 지도 크기 | 가로·세로가 각각 양수 정수인 유한 격자. 셀 인덱스는 col=0..width-1, row=0..height-1 |
| 한 칸 거리 s | 모든 인접 셀 이동에 동일하게 적용하는 양수 유한 숫자, 단위 m. 반드시 명시하며 자동 기본값을 넣지 않음 |
| 좌표 대응 | 실습 격자 외곽의 좌하단을 (0,0)m, col 증가를 +X, row 증가를 +Y로 둔다. 셀 중심은 X=(col+0.5)×s, Y=(row+0.5)×s. 브라우저 화면 Y 변환은 표시 계층에서 수행 |
| 고정 장애물 | 통행 불가 셀의 집합. 모든 좌표는 범위 안 정수이며 탐색·이동 중 지도 스냅샷을 바꾸지 않음. 중복 장애물 좌표는 같은 셀로 취급 |
| 출발·목적지 | 범위 안 정수 셀이며 장애물과 겹치면 입력 오류. 한 대의 AMR은 출발 셀 중심에서 시작 |
| 인접·거리 | 상하좌우의 통행 가능한 인접 셀만 연결. 대각선·장애물·지도 밖 이동 불가. 간선 거리는 모두 s, 최단거리=최소 이동 횟수×s |
| 기존 설정과의 관계 | 기존 #32 경유점 JSON은 그대로 유지한다. 격자 모드의 파일 구조·필드명·실행 옵션은 구현 착수 시 명시하고 기존 로더와 구분한다. 기존 strict 필드 검사에 무단으로 항목을 추가하지 않음 |

정수가 아닌 크기/셀 좌표, 0·음수·비유한 한 칸 거리, 범위 밖 셀, 장애물 위 출발/목적지, 인덱스·좌표·거리 계산 범위를 넘는 입력은 항목·이유가 있는 오류로 이동 전에 거부한다. 지도 최대 크기·메모리 상한은 운영 확정값이 아니며 구현 착수 시 실제 구조·환경을 확인해 문서화한다. 오류 입력을 자동 보정하지 않는다.

### 5.2 경로와 결과

- 경로는 출발·목적지를 포함한 순서 있는 셀 목록이다. 인접한 두 셀의 맨해튼 차이는 1이고 모든 셀은 통행 가능해야 한다. 같은 최단거리를 가진 경로가 여럿이면 어느 하나를 허용한다. 두 알고리즘의 경로 모양 일치를 요구하지 않는다.
- 정상 경로는 각 셀 중심의 경유점 목록으로 변환한다. 이동 모델에는 출발 셀 이후의 각 인접 셀 중심을 순서대로 주어 장애물 모서리를 가로지르는 직선 단축을 하지 않는다. 기존 m·m/s·경과 초·IDLE/BUSY·최종 속도0 계약을 재사용한다.
- 출발=목적지: 경로는 출발 셀 하나, 이동 횟수0·거리0인 성공이다. 기존 설정의 경유점 1개 이상 조건과 맞추어 같은 셀 중심을 유일 목표로 전달하고 IDLE·현재 속도0으로 완료한다. 빈 경로 오류와 구분한다.
- 통행 불가: NoPath와 빈 경로, 거리 없음(null)의 의미로 반환한다. 거리0인 성공과 구분하고 AMR 이동·BUSY 전환을 시작하지 않는다. InvalidInput은 NoPath와 별도 오류다. 위 이름은 결과 의미이며 실제 직렬화/API 명칭은 구현 시 명시한다.
- 탐색·이동은 동일한 지도 스냅샷과 실행 식별로 연결한다. 지도/시작점/목적지 변경 후 이전 탐색 경로·수치를 현재 결과로 표시하지 않는다.

### 5.3 알고리즘과 비교 수치

- 다익스트라는 누적 이동 횟수 g로, A*는 g+h로 우선순위를 정한다. A*의 h는 |현재col-목적col|+|현재row-목적row|인 맨해튼 거리(칸)다. 거리(m)는 결과 이동 횟수에 s를 곱한다. 이 고정 4방향·동일 비용 계약에서 휴리스틱은 실제 남은 최소 이동 횟수를 초과하지 않는다.
- 두 알고리즘은 동일 지도·출발/목적지·s로 각각 새로운 탐색 상태를 사용한다. 지도·이웃 순서·동률 처리·측정 환경은 실행 근거에 기록한다. 비교 탐색 뒤 사용자가 선택한 결과 하나만 AMR 한 대의 이동에 사용한다.
- 공통 결과는 알고리즘, 성공/NoPath/입력 오류, 셀 경로, 이동 횟수, 총거리(m), 탐색 확정 셀 수, 계산 시간(ms)다. 탐색 확정 셀 수는 우선순위 큐에서 유효 결과로 꺼내 확정한 고유 셀 수(출발·성공 시 목적지 포함), 오래된/중복 큐 항목은 제외한다.
- 계산 시간은 단조 시계로 탐색 시작부터 경로 복원 완료까지 측정하고 지도 그리기·네트워크·AMR 이동·의도적 대기를 제외한다. 같은 입력을 같은 환경에서 반복해 실행별 값·반복 조건을 보관한다. 시작=목적지의 조기 성공은 확정 셀1개로 기록한다.
- 최단거리의 동일성과 독립적인 알려진 정답 거리를 합격조건으로 삼는다. 탐색 셀 수·계산 시간은 관찰값이며 A*가 매번 더 작거나 빠르다는 합격조건/미확인 성능 목표를 두지 않는다.
- 참고: [Stanford 다익스트라·A* 강의](https://web.stanford.edu/class/archive/cs/cs106b/cs106b.1176/lectures/25-Dijkstra_AStar/25-Dijkstra_AStar_Notes.pdf). 기술 근거이며 프로젝트 요구의 승인 근거는 사용자 요청이다.

| Core 업무 모델 | `AmrDevice`의 현재 상태, `CommandRecord`의 요청·발행·응답 관찰 기록 | 업무 규칙이 갱신. 수신 DTO를 그대로 GUI의 변경 가능한 장비 객체로 노출하지 않음 |
| `AmrSnapshot` | AMR ID, 위치(m), 속도(m/s), 운행 State, Broker 연결 관측, AMR 생존 관측, 마지막 정상 Heartbeat 수신 시각, 마지막 Telemetry 수신 시각 | 읽기 전용 값 사본. 미관측 값은 없음/미확인으로 표현. `IDLE/BUSY/STOPPED/FAULT` 유지, 연결 이상만으로 FAULT로 바꾸지 않음 |

| `CommandSubmission` | Core 접수 여부, 접수 시 CommandId, 거부 시 사유 | Core 접수는 AMR 접수·발행·실행 성공이 아님. 업무 거부와 호출 실패·취소를 구분 |
| `CommandRecord`·`CommandSnapshot` | AMR ID·CommandId·명령·요청 시각, 발행 관찰, ACK 원본 결과/사유·발생/수신 시각, 대기 기한 경과, 실제 결과 해석·응답 충돌 관찰 | 발행 결과·응답 대기 상태·로봇 실행 결과를 별도 값으로 보존. 기한 경과 뒤 결과를 확인해도 과거 Timeout을 지우지 않음. 단계·예외는 7절 참조 |
| 공급자 정보 | `Mode=Mock/Actual` 등 실행 출처 | 화면에 출처 표시. Mock 데이터는 실제 MQTT·장비·DB 검증 결과로 기록하지 않음 |

좌표·장비 ID처럼 의미가 같은 작은 값은 필요에 따라 공유하되 모델 전체의 무조건 중복 정의를 요구하지 않는다. 발생 시각은 기존 Int64 Unix 밀리초를 보존하고 수신·요청 관측 UTC와 구분한다. UI 표시 형식과 경과 시간 측정은 C-03·D-03을 따른다.

### 6.2 조회·통지 인터페이스

`IAmrDataProvider`는 읽기·변경 통지, `ICommandDispatcher`는 GUI의 업무 명령 접점으로 나눈다. **조회+비동기 스트림을 채택**하며 아래 논리 서명의 역할·반환 의미를 Mock과 실제 공급자에 동일하게 적용한다. 정확한 클래스·필드·예외 타입은 구현 상세다.

| 접점·멤버 | 논리 반환형 | 관찰할 동작 |
| --- | --- | --- |
| `IAmrDataProvider.GetDevicesAsync(token)` | `Task<IReadOnlyList<AmrSnapshot>>` | 현재 장비 목록의 읽기 전용 스냅샷. 장비 없음은 빈 목록 |
| `GetDeviceAsync(amrId, token)` | `Task<AmrSnapshot?>` | 지정 장비 조회. 유효한 ID의 미등록 대상은 null, 입력 오류·조회 실패는 별도 실패 |
| `GetAlarmsAsync(query, token)` | `Task<IReadOnlyList<AlarmSnapshot>>` | 조건에 맞는 현재 알람 조회 |
| `GetHistoryAsync(query, token)` | `Task<HistoryResult>` | 조건에 맞는 저장 이력 조회. D-10의 조회 정책과 연결 |
| `GetCommandAsync(amrId, commandId, token)` | `Task<CommandSnapshot?>` | 복합 식별자로 요청 상태 조회. 조회 범위·보존 기간은 D-10에서 결정 |
| `WatchAsync(token)` | `IAsyncEnumerable<AmrChange>` | 첫 항목은 현재 장비·알람·추적 중 명령의 초기 스냅샷, 이후 상태·위치·알람·연결·명령 변경 통지 |
| `ICommandDispatcher.DispatchAsync(request, token)` | `Task<CommandSubmission>` | 업무 검증·요청 기록·ID 부여 후 Core 접수 결과 반환. 실행 완료를 기다리는 API로 사용하지 않음 |

- 변경 통지: 각 항목은 종류·대상 ID·변경 후 읽기 전용 스냅샷을 제공하고 명령 변경은 CommandId도 포함한다. **초기 스냅샷 → 이후 변경**의 등록 경계에서 누락·역전이 없어야 한다. 비동기 스트림 타입만으로 이 보장이 생기지는 않으며 전송망 전체 순서·무손실 보장으로 확대하지 않는다. 늦게 도착한 조회 결과가 최신 통지를 덮지 않도록 한다. 첫 Mock의 동기화·버전 표식은 6.4절을 따르며 실제 공급자에도 같은 관찰 보장이 필요하다.
- 수명: 열거 취소·`DisposeAsync`는 해당 구독을 해제한다. 해제 완료 뒤 새 통지를 전달하지 않고, 이미 처리 중인 항목과 취소 작업을 정리한다. 공급자의 전체 `DisposeAsync`는 이를 생성한 시작 지점이 소유하고 모든 구독·관리 작업의 종료를 기다린다. 화면 일부를 닫는 폼·컨트롤이 공유 공급자 전체를 종료하지 않는다.
- 버퍼·느린 소비자: **유한 버퍼**를 사용하고 초과 시 재동기화 필요를 소비자에게 알린 뒤 최신 스냅샷을 다시 받도록 한다. 초과를 정상 통지처럼 숨기지 않는다. 화면 통지는 현재 상태 갱신용이며 모든 알람·명령 사건의 보존은 Core 이력이 담당한다. **운영 버퍼 상한과 종료 Timeout 수치는 미정**이다. 첫 Mock의 개발용 상한·초과 예외·재개 절차·예외 매핑은 6.4절에 한정해 구현했다.
- 공급자는 UI 스레드를 보장하지 않으며 GUI가 UI 스레드 전환과 화면 갱신 빈도를 관리한다.
- DI: 실제 모드에서는 Core 조회/명령 서비스와 연결된 구현, Mock 모드에서는 같은 계약의 목록·이동·알람·명령 결과·거부·Timeout 시나리오 구현을 선택한다. Windows Forms의 폼·컨트롤이 사용하는 계약과 화면 로직은 구현체 교체 때문에 바뀌지 않도록 한다.

### 6.3 GUI 명령과 MQTT 발행의 구분

- **실제 Core가 CommandId를 한 번 생성하고 요청 기록을 발행 전에 등록한다.** 빠른 ACK도 등록된 요청과 대조하며 Communication·AMR은 ID를 재생성하지 않는다. 현재 콘솔의 `CMD-` + Guid 형식·시각 생성은 기존 구현 사실이며 실제 Core의 형식·재시작 간 유일성·보존 범위는 D-06 후속 상세다.
- `DispatchAsync`는 명령 허용 조건을 Core에 위임한다. 접수 뒤의 발행·응답 대기 작업은 Core 서비스/시작 지점이 추적·종료하며 관찰하지 않는 작업으로 버리지 않는다. 동일 AMR의 수신과 GUI 명령이 동시에 들어와도 요청 등록·상태 반영이 경쟁하지 않도록 구현한다. BUSY 중 추가 명령의 허용·대기 정책은 D-05·D-07 미정이다.
- Core가 정의할 `IAmrCommandTransport.PublishAsync(command, token) → Task<PublishOutcome>`는 별도 출력 포트의 논리 서명이다. MQTT 연결 계층이 Core 입력을 기존 Command DTO로 변환하여 CommandPublisher를 호출한다. GUI용 ICommandDispatcher와 같은 역할로 취급하지 않는다. Core 수신 포트·저장 포트의 정확한 서명은 해당 Core 기능 착수 때 정한다.
- 접수 전 취소와 접수 후 대기 취소를 구분한다. 이미 접수·발행된 명령은 GUI 호출 취소로 로봇 동작 취소가 되지 않는다. 취소와 접수의 경합은 요청 기록·조회로 확인할 수 있게 설계하고, 실제 정지는 별도 STOP 요청으로 다룬다. 접수 사실·식별자를 확인할 수 있어야 하며 첫 Mock의 취소 반환·조회 경계는 6.4절을 따르며 실제 비동기 발행·저장 경계는 D-11 후속이다.

### 6.4 최소 Core 계약·Mock 첫 구현 (2026-10-25)

- 근거·범위: 사용자가 승인한 단순한 시작 구조와 최소 Core 계약·Mock·확인용 Windows Forms 구현 요청을 적용했다. 아래는 첫 Mock의 구현 상세이며 운영 정책·실제 Core 구현 완료가 아니다. [계획·결과](../과제3/과제계획.md#gui-first-result)와 코드의 `BUILDING.md`에서 실행 근거를 연결한다.
- 파일: `src/Amr.Core/` 루트의 `IAmrDataProvider.cs`·`ICommandDispatcher.cs`·`AmrSnapshot.cs`·`CommandModels.cs`·`QueryModels.cs`·`AmrChange.cs`. 기존 메시지 DTO는 Communication에 유지한다. GUI는 Core만 참조한다.
- 조회: 6.2절의 메서드명·반환 역할을 적용한다. 조건은 `AmrQuery(AmrId, From, To, Type)`, 값은 불변 record와 `ImmutableArray`로 전달한다. 유효한 미등록 ID는 null, 알람/이력은 빈 자료다. ID 형식 오류·기간 역전·빈 유형은 `ArgumentException`, 호출 취소는 `OperationCanceledException`, 종료 뒤 접근은 `ObjectDisposedException`이다. 빈 결과로 오류를 숨기지 않는다.
- 변경: `AmrChange`에 종류·AMR ID·CommandId·공급자 내 증가하는 `Revision`과 전체 장비/알람/명령 스냅샷을 넣는다. 작은 첫 화면에서는 전체 스냅샷이 복구·검증에 유리하므로 변경분만 보내는 방식보다 단순하게 구성했다. 등록과 초기 사본 생성, 상태 변경과 요청 등록을 같은 잠금으로 보호한다. GUI는 선택 요청 순번과 Revision으로 늦은 조회·오래된 통지가 최신값을 덮지 못하게 한다.
- 유한 버퍼: `Program.cs`에서 구독별64항목을 명시한다. 초과한 구독만 큐를 정리하고 `AmrResyncRequiredException`으로 종료한다. GUI는 새 구독을 열어 최신 초기 스냅샷을 받는다. 다른 구독은 유지한다. 이 수치는 Mock 개발 설정이며 운영 기본값이 아니다.
- 명령: `CommandRequest`는 대상·Kind·X/Y, `CommandSubmission`은 접수 여부·ID·거부 코드·사유다. 지원 대상은 MOVE이며 미등록·미지원(STOP/RESET 포함)·비유한 좌표·보관 한도는 각각 거부 사유로 반환한다. Mock이 `MOCK-`+Guid ID를 생성·기록한 뒤 접수를 반환한다. 앱 실행당128건을 명시적으로 보관하고 한도에서 새 요청을 거부한다. 재시작 보존 정책이 아니다.
- 결과: 접수 직후 `Publish=MockOnly`, `Result=Unconfirmed`다. 후속 시험 버튼/메서드가 같은 대상·요청의 성공/실패를 지정한다. `CommandSnapshot`에는 목표 좌표·요청 UTC·발행 관측·결과·기한 경과·ACK 원본/발생/수신 시각·충돌·Revision을 분리해 둔다. Mock 성공/실패는 ACK 원본을 만들거나 장비 위치·State를 완료로 변경하지 않는다. 실제 ACK 수신·Timeout 동작은 미구현이다.
- 취소 경계: 접수 잠금 안의 토큰 확인 이전에 취소되면 요청을 기록하지 않는다. 그 확인 이후 접수된 요청은 ID를 반환하고 조회 가능 상태로 유지한다. 호출 취소가 이미 접수된 요청의 취소·로봇 정지 완료를 뜻하지 않는다. 경합·사전/사후 취소는 자동 시험으로 확인했다.
- 수명: 구독별 열거 취소/정리는 다른 구독에 영향을 주지 않는다. Mock은 주기·발행 작업을 만들지 않아 전체 DisposeAsync는 버퍼 정리·대기 독자 해제로 끝난다. 폼은 자신의 구독·진행 조회/버튼 작업을 취소하고 모두 기다린 뒤 닫는다. 공유 공급자는 Program이 정리한다. Windows Forms UI 전환은 InvokeAsync를 사용한다. 시험별 대기 제한은 시험 중단 방지용이며 운영 종료 기한이 아니다.
- 한계·확장 조건: 두 장비와 제한된 명령 자료로 확인했다. 장비 수·갱신 빈도가 커지면 전체 사본 비용을 측정해 변경분 통지와 화면 갱신 빈도를 검토한다. 실제 알람/이력·운영 보관/정렬/페이지·Core 발행/저장/재시작 일관성·상태 허용표는 D-05·D-07·D-10·D-11 후속이다.

### 6.5 Mock 대시보드·Map의 첫 표시 (2026-10-25)

- 사용자 구현 요청에 따른 표시 상세다. 기존 AmrSnapshot·AmrChange·명령 계약과 상태값은 유지하며 MainForm에서 같은 현재 스냅샷의 통신·생존·운행·알람/명령을 각각 집계한다. 미관측은 미확인으로 표시하고 통신 이상을 FAULT로 치환하지 않는다.

## 7. Command·ACK 처리 기준

### 7.1 현재 계약과 관찰 범위

- 유지할 계약: Command·ACK의 `cmdId`는 이미 모델에 있으며 새 필드 추가 대상이 아니다. ACK의 `result`는 `SUCCESS/FAILURE`, 필수 `cmdId/result/ts`, 선택 `id/reason`을 그대로 사용한다. 유효한 FAILURE도 형식 검사를 통과한 정상 ACK 데이터다.
- ACK의 Payload `id`가 없으면 원본 모델에 임의로 채우지 않는다. 전달 봉투의 Topic AMR ID와 CommandId를 Core 대조에 사용한다. `id`가 있으면 Topic ID와 일치해야 한다.
- 현재 Communication의 발행 반환은 AMR 도착·동작 완료를 증명하지 않는다. 현재 콘솔은 `Delivery=Unconfirmed Execution=NotTracked`, 발행 도중 실패·취소·기한 경과는 전송됐을 가능성을 포함해 `Delivery=Unknown`으로 구분한다. 이 값은 현재 콘솔의 관찰이며 실제 Core 상태 구현은 아니다.
- 운행 State·Broker 연결·AMR Heartbeat·명령 추적 상태는 별도다. Telemetry의 BUSY/IDLE 전환만으로 특정 CommandId의 완료를 추정하지 않는다. 마지막 정상 Heartbeat와 마지막 Telemetry 수신 시각도 합치지 않는다.

### 7.2 채택한 최종 결과 ACK와 Core 처리

- 적용 근거: [2026-10-22 사용자 승인](검토%20및%20결정사항.md#provider-ack-decisions)에 따라 이번 데모는 **최종 결과 응답 방식**을 채택한다. SUCCESS는 해당 요청의 동작 완료, FAILURE는 수행 거부·실패·중단의 최종 결과다. 접수·진행 ACK는 사용하지 않고 기존 스키마에 `phase` 등 새 필드를 추가하지 않는다.
- 이 선택은 논리적인 응답 단계의 계약이다. MQTT의 중복·유실이 없거나 물리적으로 한 번만 도착한다는 보장이 아니다. 긴 MOVE의 접수·진행 상태를 ACK만으로 확인할 수 없는 한계는 유지한다.

| 입력·조건 | 채택한 처리·출력 | 남은 상세·수치 |
| --- | --- | --- |
| GUI 업무 요청 | Core 검증 → CommandId 부여·발행 전 기록 → Core 접수 결과 → 추적되는 발행 작업 | ID 형식·재시작 간 범위·접수/취소 경합의 반환 |
| 발행 반환·오류·취소·기한 경과 | 발행 관찰과 전달 불확실성을 기록. 발행 반환만으로 AMR 접수·실행·완료를 생성하지 않음 | 발행 Timeout 수치·정확한 오류 코드 |
| 정상 ACK 수신 | `(Topic AmrId, CommandId)`가 등록 요청과 일치할 때 원본 응답과 최종 결과를 연결 | 재시작 전 요청의 조회/보존 범위 |
| 다른 AMR·미지 CommandId의 ACK | 진단에 남기고 기존 다른 요청의 상태·완료 결과는 변경하지 않음 | 진단·보관 범위 |
| 같은 요청의 중복·충돌 ACK | 동일 최종 결과로 업무 처리·이력을 반복하지 않음. 서로 다른 결과는 기존 결과를 자동 덮어쓰지 않고 충돌 표시 | 중복 비교의 정확한 필드·보존 기간·충돌 해소 절차 |
| 응답 기한 경과 | 발행 제한과 결과 대기 제한을 분리. 결과 대기는 **최초 발행 시도부터 단조 시계**로 측정. Timeout과 실행 미확인을 별도 보존하고 로봇 실패·FAULT·실행 취소로 자동 치환하지 않음 | 발행/명령별 결과 대기 Timeout 수치 |
| Timeout 뒤 늦은 ACK | 기한 경과 이력을 보존하고 늦게 확인된 실행 결과로 연결. 이미 다른 최종 결과가 있으면 충돌 기준 적용 | 늦은 응답·요청 보존 기간 |
| 연결 끊김·재접속 | 발행된 명령의 실행 결과 불확실성과 기존 대기 기산점을 보존. 자동 재전송하지 않음 | 발행 전 대기 명령의 처리·재접속 방식은 D-08 후속 |

결과 대기 Timeout은 명령별 경로·속도·시연 조건에 맞춘 설정값으로 정하고 실제 시험 조건에 기록한다. **버퍼 상한과 발행·결과 대기·종료 Timeout 수치는 모두 미정**이다. 기존 Heartbeat Timeout이나 현재 콘솔 발행 제한을 새 Core의 실행 완료 제한으로 복사하지 않는다.

| 명령·조건 | 최종 응답 기준 | 남은 동작 상세 |
| --- | --- | --- |
| MOVE | 목적지 도착을 완료하면 SUCCESS. 수행 거부·실패·중단이면 FAILURE와 사유 | BUSY 중 추가 MOVE·전체 명령 허용표 |
| STOP | 실제 정지 수행 완료 후 STOP의 CommandId로 SUCCESS. 수행 거부·실패면 FAILURE | 허용 상태·정지 후 운행 State·재출발 조건 |
| STOP이 진행 중 MOVE를 중단 | 원 MOVE의 CommandId에는 FAILURE와 중단 사유, STOP은 별도 CommandId의 결과. 이미 끝난 MOVE를 중단 결과로 덮어쓰지 않음 | 중단 사유의 정확한 문자열·도착/정지 경합 판정 |
| RESET | 정의한 복구 조건을 충족한 뒤 SUCCESS. 수행 거부·실패면 FAILURE | Alarm·FAULT 해제 조건·복구 후 State는 D-05에서 정함 |

접수만 응답하는 방식과 접수·진행·최종 결과를 나누는 방식은 검토 대안으로 보존한다. 후자는 단계별 관찰이 명확해지지만 송수신 스키마·검사기·Simulator·Core·Mock의 동시 변경이 필요해 이번 데모에는 채택하지 않았다. 장기 명령의 접수 확인·진행 표시가 필수가 되면 별도 계약 변경으로 재검토한다.
