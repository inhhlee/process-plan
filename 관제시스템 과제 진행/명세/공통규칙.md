## 1. 프로젝트 공통 규칙

기존 요구사항 초안의 11개 규칙을 C-01~C-11로 연결했다. 근거 요구사항은 필요성을 연결하는 항목이며 규칙의 모든 세부 표현이 책임님 원문에 그대로 명시되어 있다는 의미는 아니다.

2026-10-06 과제1 적용 범위 정리: 아래 ‘설계 제안·사용자 검토 대기’는 프로젝트 전체 규칙의 검토 상태다. 과제1의 기존 코드에서 C-01·03·05·06·08·09·10에 해당하는 식별·시간·검사·ID 보존·감시·오류 로그는 [DN-01·02·08·09·10의 개발용 임시 채택](검토%20및%20결정사항.md#com01-readiness)을 적용한다. 해당 범위를 다시 미정으로 취급하지 않으며 세부 필드·값은 [공통데이터명세](공통데이터명세.md#task1-contracts)에서 관리한다. 운영 상태·외부 연동·업무 History까지 확정한 것은 아니다.

### C-01 장비 식별

- 규칙 초안: 설정·메시지·Core·GUI·이력은 같은 AMR ID를 사용한다. Payload에 ID가 있으면 Topic의 대상 ID와 일치해야 한다.
- 근거 요구사항: [R-01](요구사항정의.md#r-01), [R-04](요구사항정의.md#r-04), [R-06](요구사항정의.md#r-06)
- 적용 범위: 모든 모듈
- 필요한 이유: 다른 장비의 데이터와 명령 결과가 섞이는 것을 방지한다.
- 근거 구분과 결정 상태: 전체 규칙은 설계 제안·사용자 검토 대기. 아래 첫 실행본 ID 검사 연결은 2026-10-21 사용자 승인으로 확정
- 관련 결정 항목: [D-01](검토%20및%20결정사항.md#d-01-미등록-amr-처리), [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)
- 첫 실행본 적용: [설정의 AMR ID 검사](공통데이터명세.md#task2-settings-data)를 기존 통신 계약의 ID 형식과 맞춘다. [2026-10-21 사용자 승인](검토%20및%20결정사항.md#task2-review-followup)에 따른 검사 기준 연결이며 실제 장비 등록 정책을 확정한 것은 아니다.

### C-02 좌표와 속도

- 규칙 초안: 위치는 2D X/Y로 표현하고 속도는 별도 항목으로 전달한다. 단위·축 방향·Map 대응을 공유한다.
- 근거 요구사항: [R-02](요구사항정의.md#r-02), [R-05](요구사항정의.md#r-05)
- 적용 범위: AMR, Core, GUI
- 필요한 이유: 위치의 생성·해석·화면 표시를 일치시킨다.
- 근거 구분과 결정 상태: 전체 규칙은 설계 제안·사용자 검토 대기. 아래 첫 실행본 적용 범위는 2026-10-20 사용자 승인으로 확정
- 관련 결정 항목: [D-02](검토%20및%20결정사항.md#d-02-좌표속도화면-대응)
- 첫 실행본 적용: 2026-10-20 사용자 승인 범위는 [과제2 위치·속도·계산 비교 기준](공통데이터명세.md#task2-motion-data)과 [AMR-02의 이동·도착 처리](기능명세.md#amr-02-command-수신과-동작-수행)를 따른다. 운영 좌표·Map 정책은 후속 결정 범위다.

- 2026-10-21 승인한 격자 비교 범위: [격자 좌표·거리·알고리즘 비교 계약](공통데이터명세.md#grid-pathfinding-data)을 과제2 계산·과제3 표시에서 동일하게 사용한다. 두 알고리즘에 같은 지도 스냅샷을 주고 최단거리와 실제 이동을 구분해 검증한다. 운영 Map·실제 장비 좌표 정책 전체의 확정은 아니다.

### C-03 시간

- 규칙 초안: 메시지 발생 시각과 관제 수신 시각을 구분하고 공통 형식·단위를 사용한다. 구체적인 형식·단위·임시 채택값은 [공통데이터명세](공통데이터명세.md)에서 관리한다.
- 근거 요구사항: [R-04](요구사항정의.md#r-04), [R-06](요구사항정의.md#r-06)
- 적용 범위: 모든 모듈
- 필요한 이유: 시각 표시와 감시·응답 시간 계산의 의미를 맞춘다.
- 근거 구분과 결정 상태: 발생·수신 시각 구분과 공통 시간 사용은 설계 제안; 사용자 검토 대기. 형식·단위의 결정 상태는 공통데이터명세를 참조한다.
- 관련 결정 항목: [D-03](검토%20및%20결정사항.md#d-03-시간-계약)

### C-04 상태의 의미

- 규칙 초안: 운행 State, Alarm 상태, 통신 연결 상태 및 명령 처리 상태를 구분한다. 연결 이상만으로 실제 운행 상태를 단정하지 않는다.
- 근거 요구사항: [R-02](요구사항정의.md#r-02), [R-04](요구사항정의.md#r-04), [R-06](요구사항정의.md#r-06)
- 적용 범위: AMR, Communication, Core, GUI
- 필요한 이유: 서로 다른 상태의 의미와 판단을 혼동하지 않도록 한다.
- 근거 구분과 결정 상태: 전체 규칙은 설계 제안·사용자 검토 대기. 아래 첫 실행본 적용 범위는 2026-10-20 사용자 승인으로 확정
- 관련 결정 항목: [D-05](검토%20및%20결정사항.md#d-05-statealarm명령-전환), [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외), [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)
- 첫 실행본 적용: 2026-10-20 사용자 승인으로 [자동 경로 이동의 최소 State·현재 속도](공통데이터명세.md#task2-state-data)를 범위 한정 적용한다. 전체 명령·장애·복구 전이와 Heartbeat 생존·통신 상태는 별도로 판단한다.

### C-05 메시지 계약

- 규칙 초안: 메시지별 송수신 방향·Topic·필수 필드·자료형·허용값을 생산자와 소비자가 함께 사용한다.
- 근거 요구사항: [R-01](요구사항정의.md#r-01), [R-04](요구사항정의.md#r-04)
- 적용 범위: AMR, Communication, Core
- 필요한 이유: 독립적으로 개발한 모듈이 같은 데이터를 주고받게 한다.
- 근거 구분과 결정 상태: 설계 제안; 사용자 검토 대기
- 관련 결정 항목: [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)

### C-06 입력 검증

- 규칙 초안: Communication은 메시지를 검사하고 유효한 데이터만 Core로 전달한다. 실패 원인을 기록하고 해당 메시지를 폐기한 뒤 이후 수신을 계속한다.
- 근거 요구사항: [R-04](요구사항정의.md#r-04)
- 적용 범위: Communication, Core
- 필요한 이유: 비정상 입력이 업무 상태를 변경하거나 후속 수신을 막지 않도록 한다.
- 근거 구분과 결정 상태: 검증 기능은 원문 요구, 실패 처리 상세는 설계 제안; 사용자 검토 대기
- 관련 결정 항목: [D-04](검토%20및%20결정사항.md#d-04-메시지-필드와-전달-정책)

### C-07 책임과 접근 경로

- 규칙 초안: AMR은 시뮬레이션 상태와 결과를 생성한다. Communication은 전달·검증, Core는 업무 처리, GUI는 공급자를 통한 조회·명령 요청과 표시를 담당한다. 실제 공급자는 Core를 사용한다.
- 근거 요구사항: [R-01](요구사항정의.md#r-01), [R-05](요구사항정의.md#r-05), [R-06](요구사항정의.md#r-06)
- 적용 범위: 모든 모듈
- 필요한 이유: 판단과 저장 책임을 구분하고 GUI의 Mock 실행과 실제 연결을 지원한다.
- 근거 구분과 결정 상태: 핵심 서비스 계층·DataProvider는 원문 요구. 조회/명령 역할·실제/Mock 교체·UI/구독/전체 종료 책임은 2026-10-22 후속 승인으로 확정. Windows Forms와 프로젝트 배치는 2026-10-25 사용자 선택을 적용하며 세부 클래스·오류·수치 등은 후속
- 관련 결정 항목: [D-06](검토%20및%20결정사항.md#d-06-commandid-생성-책임), [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당), [D-11](검토%20및%20결정사항.md#d-11-dataprovider와-화면-계약)
- 2026-10-22 적용: [프로젝트 참조·연결 책임 제안](#module-dependencies)은 현재 구조 유지 범위의 후보로 보존하고, [조회·명령 계약](공통데이터명세.md#provider-command-contract)의 채택 원칙을 적용한다. 채택 근거와 남은 상세는 [후속 사용자 결정](검토%20및%20결정사항.md#provider-ack-decisions)을 따른다.
- 2026-10-25 적용: 앞선 물리 배치 후보는 [Windows Forms·간소화 구조 선택](검토%20및%20결정사항.md#winforms-structure-decision)으로 구체화했다. 기존 코드 이동 없이 최소 Core 계약·ControlGui·GUI 시험 프로젝트를 생성했다. [첫 작업 결과](../과제3/과제계획.md#gui-first-result)와 [구현 상세](공통데이터명세.md#gui-first-contract)를 따른다.

### C-08 명령과 결과

- 규칙 초안: 요청마다 고유 CommandId를 사용하고 전달·응답에서 보존한다. 대상 AMR과 원래 요청에 결과를 연결하며 발행 완료와 동작 완료를 구분한다.
- 근거 요구사항: [R-02](요구사항정의.md#r-02), [R-04](요구사항정의.md#r-04), [R-06](요구사항정의.md#r-06)
- 적용 범위: AMR, Communication, Core, GUI
- 필요한 이유: 응답 순서가 달라도 올바른 요청에 결과를 반영한다.
- 근거 구분과 결정 상태: 이번 데모의 Core ID/발행 전 기록·최종 결과 ACK·명시된 추적 원칙은 2026-10-22 후속 승인으로 확정. 수치·미선택 상세·운영 정책은 후속
- 관련 결정 항목: [D-06](검토%20및%20결정사항.md#d-06-commandid-생성-책임), [D-07](검토%20및%20결정사항.md#d-07-ack-의미와-명령-예외)
- ACK의 현재 식별·허용값과 채택한 업무 처리 기준은 [ACK 처리 계약](공통데이터명세.md#ack-processing-contract)에서 구분한다. 발행 반환·ACK 수신·실제 동작 완료를 같은 상태로 취급하지 않는다.

### C-09 통신 감시

- 규칙 초안: Broker 연결 상태와 개별 AMR Heartbeat를 구분한다. AMR 감시는 마지막 정상 Heartbeat 수신 시각을 기준으로 판단한다.
- 근거 요구사항: [R-04](요구사항정의.md#r-04)
- 적용 범위: Communication, Core, GUI
- 필요한 이유: Broker 연결과 특정 AMR의 생존 여부를 구분한다.
- 근거 구분과 결정 상태: 감시 기능은 원문 요구, 판단 방식은 설계 제안; 사용자 검토 대기
- 관련 결정 항목: [D-09](검토%20및%20결정사항.md#d-09-heartbeat-판정과-담당)

### C-10 기록

- 규칙 초안: 장애 분석을 위한 Log와 관제 업무 History를 구분한다. 상태 변경·알람·명령 결과·운행 이력은 원문의 저장 범위에 연결한다.
- 근거 요구사항: [R-06](요구사항정의.md#r-06), [R-07](요구사항정의.md#r-07)
- 적용 범위: Communication, Core, SQLite, GUI
- 필요한 이유: 시스템 오류 기록과 업무 이력의 목적을 구분한다.
- 근거 구분과 결정 상태: 업무 이력 저장은 원문 요구, Log 분리·상세 저장 정책은 설계 제안; 사용자 검토 대기
- 관련 결정 항목: [D-10](검토%20및%20결정사항.md#d-10-loghistory-저장과-조회)

### C-11 설정과 시험 데이터

- 규칙 초안: AMR 시험 조건은 설정 파일로 변경한다. Mock과 실제 공급자는 같은 데이터 의미를 사용하며 Mock 결과임을 구분할 수 있어야 한다.
- 근거 요구사항: [R-03](요구사항정의.md#r-03), [R-05](요구사항정의.md#r-05), [R-07](요구사항정의.md#r-07)
- 적용 범위: AMR, Core, GUI, 통합 시험
- 필요한 이유: 시험을 재현하고 Mock 실행에서 실제 연결로 전환할 때 의미를 유지한다.
- 근거 구분과 결정 상태: 설정 변경·Mock 실행은 원문 요구. 실제/Mock의 조회·통지·명령 반환 의미와 출처 표시는 2026-10-22 후속 승인으로 확정. 아래 첫 실행본의 필수 설정·오류 처리 범위는 2026-10-20 승인으로 확정하며 전체 Mock 시나리오·표현 상세는 후속
- 관련 결정 항목: [D-11](검토%20및%20결정사항.md#d-11-dataprovider와-화면-계약), [D-12](검토%20및%20결정사항.md#d-12-시뮬레이터-설정과-재현)
- 첫 실행본 적용: 2026-10-20 사용자 승인으로 [필수 설정·유효성](공통데이터명세.md#task2-settings-data)을 명시하고, [AMR-01](기능명세.md#amr-01-설정-로드와-amr-생성)에서 오류를 자동 보정하지 않고 이동 시작 전에 거부한다. 다중 AMR·장애·Mock의 전체 조건은 후속 범위다.
- Mock 계약 적용: 2026-10-22 후속 승인으로 실제/Mock의 조회·스트림·명령 반환 의미와 출처 표시를 [데이터 6절](공통데이터명세.md#provider-command-contract)에 따라 동일하게 적용한다. 전체 Mock 시나리오·다중 AMR·장애 구현 완료를 뜻하지 않는다.

- 격자 비교의 설정·관찰 기준: 사용자 추가 요구는 [요구사항정의 1.4절](요구사항정의.md#grid-pathfinding-scope)을 따른다. 재현 가능한 지도·출발/목적지·한 칸 거리·알고리즘·비교 측정 조건을 기록하고, 탐색 경로·실제 이동 좌표·MQTT 수신 좌표의 출처를 구분한다. 기존 경유점 설정·메시지 계약은 유지한다.

## 프로젝트 참조 방향과 연결 책임

- 근거·상태: [2026-10-22 최초 검토](검토%20및%20결정사항.md#integration-boundary-review)와 [조회·명령 채택](검토%20및%20결정사항.md#provider-ack-decisions)에 이어 [2026-10-25 사용자 선택](검토%20및%20결정사항.md#winforms-structure-decision)으로 Windows Forms·간소화 프로젝트 배치를 계획에 반영한다. 상세 파일 목록과 기존·추가·보존 구분은 [과제3 전체 구조](../과제3/과제계획.md#winforms-file-structure)에서 관리한다. 2026-10-25 최소 계약·Mock·확인용 폼은 구현·시험했으며 전체 화면과 실제 연결은 후속이다.
- 현재 구조: `Amr.Communication`·`Amr.Communication.Console`·`Amr.Simulator`가 존재하며, Simulator와 콘솔은 Communication을 참조한다. 메시지 모델은 Communication에 유지한다. `Amr.Core`의 최소 계약과 `Amr.ControlGui`의 확인용 폼·Mock은 존재하며 `Amr.Infrastructure`는 추가 예정이다. 한편 Contracts 추출은 현재 계획에 포함하지 않는다. `tools/Amr.Simulator.Map`은 보존 브랜치의 별도 시연 도구로 정식 Windows Forms GUI와 구분한다.

아래 `A → B`는 **프로젝트 참조 방향**이며 실행 중 데이터 흐름과 다르다. 기존 참조와 추가 예정 참조를 구분하며 후속 참조 계획을 이미 구현된 참조로 표시하지 않는다.

| 역할·프로젝트 | 기존·추가 예정 참조 방향 | 담당과 경계 |
| --- | --- | --- |
| `Amr.Communication` [기존] | Core·GUI·Infrastructure 프로젝트 참조 없음 | 기존 메시지 모델·MQTT 접속·송수신·필드 검사·수신 큐 유지. 업무 상태 판단·DB 저장은 담당하지 않음 |
| `Amr.Communication.Console` [기존] | Console → Communication | 통신 확인용 실행 프로그램 유지 |
| `Amr.Simulator` [기존] | Simulator → Communication 유지 | 시뮬레이션 상태·명령 실행·메시지 생성. Core·관제 GUI·SQLite에 의존하지 않음 |
| `Amr.Core` [기존·첫 계약 구현] | MQTT·SQLite·GUI 구현 프로젝트 참조 없음 | 첫 작업은 조회/명령 인터페이스·읽기 전용 형식을 루트에 배치. 실제 업무 규칙·수신/저장 계약과 폴더 분리는 해당 기능 때 추가 |
| `Amr.Infrastructure` [추가] | Infrastructure → Communication·Core | Mqtt 폴더는 DTO 변환·기존 통신 연결, Sqlite 폴더는 Core 저장/조회 계약 구현. 업무 판단은 Core에 위임 |
| `Amr.ControlGui` [기존·첫 Mock 구현] | 첫 작업은 ControlGui → Core. 실제 연결 때 시작 지점의 조립에 Infrastructure 참조 추가 | Windows Forms·Mock 공급자를 루트에 배치. 폼·컨트롤의 화면 로직은 Core 공개 계약만 사용하며 MQTT·SQL에 직접 접근하지 않음 |
| 앱 시작 지점 `Program.cs` | 실제/Mock과 필요한 서비스 조립 | 연결·공유 공급자·작업의 전체 수명을 소유. 화면의 구독 수명과 구분 |

- 연결 방식 제안: `MQTT → MessageSubscription·검사기 → 기존 AmrReceiveQueue → 연결 계층 → Core 수신 인터페이스`를 사용한다. 현재 콘솔의 시험 수신자를 실제 Core 연결로 확장하는 경계이며 같은 수신을 중복 구독하거나 큐를 중복 생성하지 않는다. 동일 AMR 순차 처리·AMR 간 독립·취소·과부하 통지의 기존 보장 범위를 유지한다.
- Core는 상태 갱신과 업무 이벤트 생성·저장 요청을 담당한다. 느린 저장·저장 실패의 처리·일관성은 D-10에서 정하며 MQTT 콜백에 DB 작업을 직접 넣지 않는다. 수신 큐의 접수 성공을 업무 처리·저장 성공으로 표시하지 않는다.
- 인터페이스는 Core의 공개 경계에 두되 처음에는 프로젝트 루트에 배치한다. Models·Abstractions·Services·Providers 같은 내부 폴더는 필요가 생길 때 추가한다. 별도 Abstractions 프로젝트와 Contracts 추출은 실제 의존성 분리 필요가 생길 때 검토한다. MQTT DTO·Core 업무 모델·GUI 스냅샷의 구분은 [데이터 6절](공통데이터명세.md#provider-command-contract)을 따른다.
- [2026-10-25 후속 결정](검토%20및%20결정사항.md#winforms-simple-start-decision)에 따라 첫 작업은 Core·ControlGui·GUI 시험 프로젝트부터 시작한다. Infrastructure와 화면별 Controls는 실제 외부 연결·영역 분리 단계에 생성한다. 내부 폴더를 줄여도 조회/명령·UI/업무·구독/전체 종료 책임은 유지한다.
- UI 스레드 전환과 화면 갱신은 Windows Forms GUI 책임이다. Core·Communication에는 Windows Forms 컨트롤이나 UI 스레드 처리의 참조를 추가하지 않는다. 화면을 닫을 때 해당 구독을 정리하고, 공유 공급자의 전체 종료는 시작 지점에서 소유한다.
- 이전의 `Amr.Infrastructure.Mqtt`·`Amr.Infrastructure.Sqlite` 별도 프로젝트 안은 검토 대안으로 보존한다. 이번 계획은 관리할 프로젝트 수를 줄이도록 단일 Infrastructure의 두 폴더를 사용한다. 독립 재사용·외부 라이브러리 분리가 필요해지면 별도 프로젝트를 재검토한다. 폴더 구분 자체가 참조 제한을 강제하지 않으므로 코드 리뷰에서 역할 경계를 확인한다.
